## 判断

**需求与契约**：符合。
- 文件：`packages/engine/{package.json,tsconfig.json,src/{index,eval,table,types,format,last-acts}.ts,test/*}` 齐全；eval、table 是 rename（相似度 98%/99%），唯一改动是 `import type { Card, Street } from './types'`。`apps/desktop/src/main/engine/` 已删除，`.rivo` 以外 grep `main/engine`、`engine/eval`、`engine/table` 没有残留。
- 导出：`index.ts` 全量 re-export，`Table`、`Legal`、`LogEntry`、`ActionType`、`SeatState`、`PotWin`、`best`、`equity`、`outs`、`FULL`、`shuffle`、`Rng`、`handName`（未改名，符合“本任务不改名”）、`Card`、`Street`、`fmt`、`signed`、`lastActs`、`LastAct` 都在。
- desktop：`shared/types.ts` 以 type 重导出 `Card`、`Street`；`shared/format.ts` 重导出 `fmt`、`signed`，函数体与起点逐字相同；`disp`、`txt`、`cardsText` 留在 desktop。runner、text、view、runner.test 的 import 改为 `@river/engine`。
- 依赖方向：`packages/engine/src` 中除 `./` 相对路径外没有任何 import，package.json 没有 dependencies/peerDependencies；desktop 只在 `devDependencies` 加了 `"@river/engine": "workspace:*"`，`dependencies` 不变；lockfile 只多了这条 link 和 `packages/engine: {}` importer。符合 ADR-007。
- `lastActs` 实现（`last-acts.ts`）逐条对照契约：只取 `e.street === street` 的座位记录；`return` 跳过；`allIn` 为真记 `'allin'`（含全下盲注）；未全下的盲注跳过；其余按 `type` 取值。按顺序覆盖，得到的是最后一条有效记录。符合 task 与 plan。
- `electron.vite.config.ts`、desktop 的 tsconfig 均未改；我实测构建后 `out/main/index.js` 里没有 `@river/engine`，符合步骤 5。

**工程质量**：良好。
- 改动很小，没有多余抽象。`helpers.ts` 抽出的是原 engine.test 里原样存在的工具函数，不是新写的。
- text.test 用自带的简化 rng 而不是跨包引用 engine 的测试 helper，这个取舍是对的：跨包 import 测试文件会让 desktop 测试依赖 engine 的内部目录。
- engine 的 tsconfig 为了测试读 poker.js 开了 `types: ["node"]`，并把 src 和 test 一起 include。这样 src 里误用 Node API 时 typecheck 不会报错，而 engine 按计划要在浏览器里跑（F3，可选）。

**测试迁移**：没有丢失覆盖。
- 用例清单：起点 engine.test 共 37 个 `it`；现在 engine/test/engine.test.ts 31 个，加上 desktop/test/text.test.ts 7 个，共 38 个。按名称逐条比对，只有两处差别，而且都是计划要求的拆分：差分用例的名称去掉了 “disp”；新增“52 张牌的 disp 与原型一致”。
- engine.test.ts 的 diff 只有三处：删掉搬走的工具函数、删掉三组 text 用例、从差分循环里去掉 disp 断言。其余用例体没有改。poker.js 的路径 `../../../.rivo/...` 从 `packages/engine/test` 出发是正确的，而且测试确实读到了文件。
- disp 对照原来在 2000 组随机牌里每组查 `hole[0]`，现在直接遍历 52 张，覆盖更完整。
- text 用例改用简化 rng：原来的 `rigged(n, 0, 空)` 只用第一个随机数定按钮，洗牌部分会生成一个固定牌序，但这些用例的断言都和牌面无关（`当前牌型：` 只检查前缀；往手摘要只匹配“行动：…”；位置只看按钮）。新 rng 的第一个值用的是同一个公式定按钮，后面恒为 0.5，只是换了一副确定的牌。原来的意图（位置、称呼、盲注和投入文本）都保留下来，断言一字未改。

**lastActs 测试能否区分错误实现**：能。我把实现复制到 scratchpad，做了 8 个变异，每个都至少有一个用例失败：

| 变异 | 失败用例 |
|---|---|
| M1 不跳过 return | 退回用例、随机压测 |
| M2 未全下盲注也计入 | 盲注用例、随机压测 |
| M3 不按街过滤 | 换街用例、随机压测 |
| M4 只有盲注全下才记 allin（call/raise 全下按 type 记） | 仅随机压测 |
| M5 全下盲注不计 | 盲注用例、随机压测 |
| M6 取第一条而不是最后一条 | 仅随机压测 |
| M7 跳过 fold | 退回、换街、随机压测 |
| M8 按“最后一条发牌记录之后”取、忽略 street 参数 | 换街用例、随机压测 |

性质检查的期望函数 `expected` 基本是实现的复述（同样的循环和过滤，只是把条件写成了一个 `||` 链）。它和手写用例配合能挡住上面这些错误，但它和实现用的是同一个“本街”定义（`e.street === street`），所以无法独立验证 plan 里“取值范围与 view.ts 相同”的说法（见 F1），也从不查询 `'showdown'` 这一街。手写用例没有单独覆盖“跟注全下”“加注全下”，这两种情况只靠随机压测挡住（M4）（F2，可选）。

**验收证据**：基本完整，有一处缺口。
- typecheck、test、build、grep 我都重跑了，结果与 commands.md 一致（见“实际验证”）。用例数的算术（137 = 132 − 37 + 31 + 4 + 7）与我数出的数字相符。
