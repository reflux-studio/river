## 判断

### 需求与契约

- **i18n 包**：`Locale`、`resolveLocale`（`/^zh/i`）、`dict`、`presets`（`Record<Locale, PersonaSeed[]>`）、`en: typeof zh`（dict、poker、prompts 三处）都与契约一致。英文没有空词条，也没有留汉字（有测试保证）。`prompt` 命名空间目前只有 `coaches`，这是 task 允许的（其余提示词在 T5 补）。`PersonaSeed` 定义在 i18n 中，desktop 的 `Persona extends PersonaSeed`。
- **依赖方向**：i18n 的 src 只有 `poker.ts` 里一处 `import type { Street } from '@river/engine'`，其余都是包内引用。`package.json` 只依赖 `@river/engine`（`workspace:*`），没有第三方依赖。desktop 把 i18n 放在 devDependencies，main/shared 引用 i18n，符合 ADR-007。
- **中文预设和常量逐字一致**：我用 `git show a31d4f5:apps/desktop/src/shared/personas.ts` 取出 8 行 `PERSONAS`，与 `presets.zh` 的 8 行逐行 `diff`，没有差异。`COACHES`、`STREET` 与 `promptZh.coaches`、`pokerZh.street` 也一致。i18n 测试里另有 sha256 断言守住这一点。
- **预选值确实读原始 kv**：`getKv<T>(key, fallback)` 在 fallback 是对象时返回 `{ ...fallback, ...value }`，所以 `getKv('settings', {})` 拿到的就是原始值。`loadCaches` 根据 `!saved.locale` 判断，没有 locale 时只写内存 `settingsCache`，不写库。老用户（`onboarded=true`）得到 `'zh'`，与 plan 一致。
- **`completeOnboarding` 与 plan 伪代码一致**：已完成引导时原样返回 → 组 patch → 如果选 en 且币种是 cny，就改成 usd 并把 fxRate 置空 → `updateSettings` → `setOnboarded(true)` → 按新语言重新 `loadPersonas`。实现在 db 模块，`ipc.ts` 只转发。多出的一步是非法 locale 校验（见下文和 F1）。
- **`settings.update` 的守卫在 ipc**：`'locale' in patch` 时抛出 `'locale is fixed after onboarding'`。我检查了渲染进程所有 `updateSettings(...)` 调用（Settings、Appearance、CoachPanel 共 9 处），都只传单个字段，不会带上 locale 而被误拒。
- **种子与比较**：`loadPersonas`、`savePersona`、`deletePersona` 都改用 `seeds() = presets[settingsCache.locale]`，保存时与同一语言的种子比较，“是否改过”的判断逻辑没变。测试覆盖了“英文下保存与种子相同的字段存为空”和“恢复默认回到英文”。
- **结束引导的路径（逐一对照 `Onboarding.tsx`）**：页面上实际有“跳过”（`onClick={onFinish}`）、“稍后再说”（`onFinish`）、“去配置”（`await onFinish(); go('settings')`）、“带我打一手”（`await onFinish(); await startGuided()`）；Esc 和点击遮罩走 `Dialog onOpenChange(false) → finish()`。6 条路径都调用 `finishOnboarding(picked ?? settings.locale)`。另外核对了 `rulesOpen:false` 的其他写入点（`startTable` 里的 163/164/169 行），它们只能在引导结束后触发（弹窗是模态的），不会绕过写入语言。
- **重新打开规则介绍时没有语言页**：`Pages` 在挂载时用 `useState(!onboarded)` 固定 `withLang`。关闭时 Radix 会卸载内容，所以重新打开会重新计算。挂载时固定还能避免关闭动画期间 `onboarded` 先变成 true、导致页码错位。截图 06 是“Rules · 1 / 6”，没有语言页。
- **老用户**：`locale` 为 zh，种子、币种和已有断言都不变。已有测试只在 3 处设置字面量里补了 `locale: 'zh'`，没有大面积改写，符合“测试默认中文”的约定。
- **`STREET`、`COACHES` 的使用方**：`rg -n 'PERSONAS|COACHES|STREET' apps/desktop/src` 只剩 `STREET_MS`（无关）。coach.ts、runner.ts、text.ts、CoachPanel、Settings、Replays 都改为 `dict('zh')`，符合“本任务只取中文值”的要求。
- **`Bootstrap.packaged` / `AppInfo.packaged`**：`index.ts` 传入 `app.isPackaged`，`app.getLocale()` 在 `whenReady` 回调里读取，符合契约。

### 偏差是否可以接受

- **`useT()` 用的是 store selector，没有用 React Context**：plan 写的是“一个 React context 提供 `t`，值随 `settings.locale` 变化”。现在的实现 `dict(useRiver(s => s.settings.locale))` 语义相同：全局只有一个 store，语言在运行期间不变，组件也会随 `settings` 更新而重新渲染。它还省掉了 Provider，也不会出现“忘了包 Provider”的问题。**可以接受**，建议把 plan 的措辞改成“`useT()` hook”，免得 T6 的执行者去找 Context（见 F3）。另外，`useT` 目前没有调用方：引导页需要用本地选中的语言，所以直接调用 `dict(locale)`。等 T6 用上它就不是死代码了，不单独记为问题。
- **非法 locale 校验**：新增的 `if (!(locale in presets)) throw` 只在未完成引导时执行，目的是防止非法值写进库后，之后每次加载预设都失败。它守的是信任边界（IPC 输入），方向合理，可以接受。但 `in` 会查原型链，有漏洞，见 F1。
- **主进程没有互斥**（实现者自己报告的）：渲染进程的 `finishOnboarding` 会同步检查并先设置 `state.onboarded`，所以同一个窗口最多只发出一次 `onboarding.done`。就算真的并发，两次调用写入的 locale 相同，结果一样。可以接受。
- **可能被顺带写库的预选值**：主进程里 `updateSettings` 的调用方只有 `completeOnboarding`，渲染进程的调用只发生在引导结束之后（引导期间弹窗是模态的）。老用户保存设置时会把 `locale:'zh'` 写进库，这个值和推导出来的值相同，没有害处，plan 已接受。
- **没有其他未列出的行为变化**：英文系统的新用户在引导完成前，大厅里就显示英文预设（截图 09 背景中的 Foxy、Rock）。这是 `seeds()` 跟随内存预选值带来的，与 plan 中“种子来自 `settings.locale`”一致；如果选了中文，完成引导后会重建。可以接受。

### 工程质量

- 改动集中，没有多余的抽象。注释都在解释“为什么”（如 getKv 合并、只在内存、挂载时固定 withLang）。
- 引导结束后，`onboarding.done` 没有 `runner.broadcast()`，也没有 `emit('personas')`。渲染进程用返回值更新 store，此时也没有牌桌，所以不需要广播。
- `finishOnboarding` 失败时渲染进程已经标记为 onboarded，而库里没有写入。这是旧行为（旧代码同样先 setState 再 invoke），不是本次引入的。

### 验收证据

- **单元测试**：task 列出的 5 项都有对应用例，而且检验的是目标行为。例如“新库按系统语言预选”：如果改用合并后的 `getKv`，`reopen('en-US')` 会得到 zh，断言就会失败。如果 `completeOnboarding` 不重建预设，`name: 'Foxy'` 这条断言会失败。守卫在引导完成前后都做了断言。
