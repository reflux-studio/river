## 新发现的问题

### N5-1 公屏结构化的范围不完整，`act` 字段名与现有字段冲突

我逐一列出了 runner 写入公屏的地方（`runner.ts`），方案的 `sys` 联合类型只覆盖了 `hand`、`rebuy`、`street` 三种，下面这些没有覆盖：

- **入座**（125 行）：`入座 · sb/bb · N 人桌 · 教练局/自由局`。
- **赢得**（544 行）：`X 赢得 N · 牌型`。其中的牌型也需要改用 `handCat`。
- **赛后发言**（598 行）：这条是 `kind: 'msg'`，但 `text` 带着中文前缀 `[第 N 手赛后]`。它既显示在界面上，也会经 `newChat` 和 `chatBlock` 喂给 Agent，属于表格里"两边共用"的那一类。前缀应该改成结构化字段（例如 `postHand: number`），由各使用方自己渲染。
- **`act` 字段名冲突**：`ChatMessage.act` 目前是字符串，存的是按中文生成的行动文案（`runner.ts:294,320`）。`ChatPanel.tsx:51,60` 直接显示它，`text.ts:106` 的 `chatBlock` 也把它喂给 Agent。方案说"行动消息新增结构化的 `act`"，如果真的把现有字段改成对象，界面显示和 Agent 输入会同时出错。建议另起字段名（例如 `action: { type, amount, to, allIn, blind }`），`act` 保留原文作兜底。
- **`chatBlock`、`speaker` 的写死文字**（`text.ts:105-111`）："新发言""系统""玩家""？"都写死在代码里，要改成按锁定的语言生成。它们已经归入表格里"进入 Agent 的一切"这一行，但 plan 里要单独列出来。

其他影响的核对结果：

- **落库**：公屏消息不写数据库，只存在 runner 内存里和 `Bootstrap` 的快照中（`db/index.ts` 里没有 chat 相关代码），所以结构化改动不涉及落库，也没有新旧数据的兼容问题。
- **`Thread`**：`Thread` 只保存已经渲染好的观察文本和工具结果，本身不受 `ChatMessage` 结构变化的影响。但 `pushTool` 的结果 key（`{ 实际, 公屏 }`，见 `runner.ts:293`）和 digest 里的 `（想：`、`；说：`、`赛后说：`/`赛后没说话`（`runner.ts:292,597`）也是给 Agent 看的中文，同样要按锁定的语言生成。
- **`ChatPanel`**：它的 `who()` 把 `hero` 写死成了"你"（第 12 行），改成用 `t` 渲染即可。`from: 'hero'` 本来就是现有约定，不需要改。

### N5-2 runner 优先读取实时人设缓存，切换语言后会绕开本桌锁定

- `runner.ts:259,580` 的写法是 `personaOf(pid) ?? this.snapshots.get(pid)`，优先读全局的 `personasCache`。原本的用意是让牌局中途对人设的修改立即生效。
- 按新方案，切换语言会重建人设缓存。重建之后，本桌对手的名字和提示词会立刻变成新语言，与"进入 Agent 的一切按本桌锁定"相矛盾。验证第 4 条第 2 项要求"Agent 在下一桌才切换"，这个用例会失败。
- 需要在方案里写明：runner 按本桌锁定的语言解析人设，例如缓存只保存原始覆盖值，由 `resolve(persona, locale)` 按需解析；或者本桌只使用开桌时的快照。选哪一种，取决于"牌局中途修改人设是否立即生效"这一现有行为要不要保留。
- 同类问题：开桌快照里的玩家名"你"（`runner.ts:112`）会进入 `TableView` 的座位名，而表格里没有写座位名跟随哪种语言。建议补一行，写明座位名跟随本桌锁定的语言，或者由界面按 `hero` 渲染。

### N5-3 i18n 的 `handLabel(rec)`、`posLabel(rec)` 不能直接接收 `HandRecord`

- `HandRecord` 定义在 desktop 的 `shared/types` 里，按依赖方向，i18n 不能引用 desktop 的类型。
- 建议把签名改成只接收基本字段，例如 `handLabel(t, { handCat?, handName })`；或者把这两个函数放在 desktop，由 desktop 调用 i18n 的字典。

### N5-4 无汉字检查的范围要覆盖"发给模型的全部消息"

- 方案列出的检查对象是"提示词、局面描述、`TableView` 状态文字、公屏文本"，不包括 `Thread` 的工具结果和 digest（N5-1 列出的 `实际`、`公屏`、`赛后说` 等），也不包括 `COACH_ASKS`。
- 测试里已经有 `mock-model.ts`。建议直接在模型调用的入口处截取完整的 `system` 和 `messages`，再断言其中不含汉字，这样就不必逐项列举检查对象。

## 人设迁移的正确性

- **现有数据**：`savePersona` 本来就会把与中文种子值相同的字段存成 NULL 或 `''`（`db/index.ts:276,282`），所以现有数据里等于种子值的字段很少，迁移基本不会改动什么，风险很低。现有数据都是在中文界面下保存的，按中文种子值置空不会丢失用户的改动，这个推理成立。
- **只能执行一次**：迁移必须放进现有的版本化 `MIGRATIONS` 数组（`db/index.ts:24` 起）。如果每次启动都执行，用户在英文界面下特意保存为"阿狸"（这个值与英文种子不同，所以会被存下来）的名字，下次启动时会被当成中文种子值清空。
- **列的约束**：`prompt` 列是 `NOT NULL`（第 27 行），迁移时要把它置为 `''`，不能置为 NULL。这与 `resetPersona` 的写法一致。
- **新规则下的场景**：我逐一推演了下面这些情况，结论都符合预期。
  - 英文界面只改提示词：名字等于英文种子，存为空，两种语言下各显示各自的种子名。
  - 中文界面改名为"Foxy"：存下"Foxy"，两种语言下都显示 Foxy。
  - 英文界面特意填"阿狸"：存下"阿狸"。
  - 老K的 `ini` 中英文种子都是 `K`：两种语言下结果相同。
- **"已改动"的判断**：改成"有任何非空字段"即可，和读取规则保持一致。
