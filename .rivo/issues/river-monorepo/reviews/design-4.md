# river-monorepo 方案审阅 · 第 4 轮（i18n 追加需求）

- **对象**：重读 `.rivo/issues/river-monorepo/discussion.md` 全文。本轮新增"@river/i18n 与 desktop 双语"一节，并更新了决定表、依赖图、验证和"本期不做"。
- **基线**：`main` @ 1ece50c。
- **前轮**：`reviews/design-3.md`，结论为通过。本轮只核查 i18n 带来的变化，前三轮已结案的项不再重复。
- **结论：需修改**。阻塞 1 项，非阻塞 7 项。

## 决定的来源

- 用户追加的需求是"i18n，site 和 desktop 都做"。实现方式、Agent 双语、历史记录、语言设置这几项都是 AI 提出、用户采纳的，决定表里已经如实标明。
- "Agent 语言按牌局锁定、长期印象不翻译"标为**待用户确认**。本轮的阻塞项 B4-1 与这一项直接相关，建议两者一起拿给用户确认。

## 阻塞

### B4-1 哪些主进程文本跟随即时语言、哪些跟随本桌锁定语言，没有划分清楚；公屏系统消息的处理会破坏 ADR-006 的现有行为

方案把主进程生成的文本分成两类：

- `TableView` 状态文字、系统消息、报错：下一次推送时就改用新语言；
- Agent 的提示词和局面描述：本桌锁定，下一桌才改。

但有几类文本同时服务于界面和 Agent，或者在开桌时就已经固定下来，方案没有给它们定归属。

- **公屏系统消息既给人看，也给 Agent 看。**
  - `runner.ts:620-626` 的 `newChat()` 会把公屏里的 `sys` 消息筛出来，放进对手和教练的观察内容。筛选条件是中文正则 `/^第 \d+ 手 · |重新买入/`。
  - 按方案，系统消息跟随即时语言。那么切换到英文之后，或者整桌本来就是英文时，"第 N 手"分隔和重新买入提示匹配不上这条正则，会被悄悄丢掉。
  - 这样 Agent 就分不清公屏上的发言属于哪一手，违背 ADR-006 以及 `newChat` 注释写明的意图："人能看到发言属于哪一手，模型也要能看到"。
  - 反过来，如果中途切换了语言，新的英文系统消息会混进一桌锁定为中文的对话线。这正是方案锁定语言想要避免的"同一对话线中英混用"。
- **开桌时已经固定的文本。**
  - `runner.ts:111-113` 在开桌时写死了玩家名 `'你'`，人设名、tag、ini 也在这时快照；`Thread.enter` 的往手摘要里写死了 `[第 N 手]`、`你本手`。
  - 方案说界面文案"立即切换"，但 `TableView` 里的座位名来自开桌时的快照，所以切换后本桌座位上仍然显示"你"和中文人设名。
- **教练的 system 提示词在调用时才读 `settingsCache`**（`coach.ts:14-16`）。要锁定语言，锁定值必须从 runner 传进去，不能再读全局设置。

需要在方案里写明以下三点：

- 每类文本的语言来源：本桌锁定，还是即时语言。
- `newChat` 改为按结构判断，而不是按文案匹配。例如给 `ChatMessage` 加一个 `sysKind`，或者带上 `hand` 字段。
- 系统消息和座位名跟随哪一种语言。

在方案里写明这些，不需要推翻"按桌锁定"的设计。

对协调员第 3 问的回答：**`TableStart` 不需要带 `locale`**。当前生效的语言由主进程计算，`runner.start()` 开桌时直接快照即可；渲染进程另传一份反而可能出现两边不一致。锁定的语言应该存在 runner 的实例上，再传给 `Thread`、`text.ts` 和各个 Agent。`Thread` 目前没有语言参数，需要改构造函数。这些都和现有结构相容。

## 非阻塞

### N4-1 `handName` 改成返回 `HandCat` 后，影响面比方案列出的更大

调用方包括：

- `table.ts:239`，即 `winners()[].handName`；
- `view.ts:61,78,128`：赢家状态行和结果横幅；
- `runner.ts:548`：写入 `HandRecord`；
- `runner.ts:662`：`TableView.nums.handName`，教练面板 `CoachPanel.tsx:20` 直接显示这个值；
- `text.ts:94,122`：局面描述和亮牌摘要；
- `Replays.tsx:93`。

这些地方都要改成"key 经字典翻译"。另外还有两点：

- `text.ts:122` 和 `Replays` 读的是老记录。老记录里存的是中文，新记录里存的是 key，所以需要一个统一的函数：值属于 `HandCat` 就翻译，否则原样显示。
- `TableView.nums.handName` 的类型要改。方案没有提到这个跨进程契约的变化。

测试方面：

- `engine.test.ts` 的 84–91、302–330 行断言的是中文牌型，要改成断言 key。
- 460 行的差分对照拿引擎结果和 `poker.js` 的 `P.handName` 比较，而后者返回中文。
  - 如果测试借用 `@river/i18n` 的中文字典来比较，就形成了 engine → i18n 的依赖。i18n 本身又依赖 engine 的类型，workspace 里会出现循环依赖（即使只是 devDependencies）。
  - 建议在测试里放一张本地的 key→中文映射表，只用于对照；或者把差分测试挪到不属于 engine 的位置。需要在方案里写明选哪一种。

### N4-2 `HandRecord.handName` 复用同一个字段，和"旧版本读新记录不会出错"的说法不符

- 方案把 `label`、`pos` 留作兜底，却把 `handName` 直接改存 key。
- 如果旧版本读到新记录，`Replays` 会直接显示 `pair`、`flush` 这样的 key，`text.ts:122` 也会把 key 喂给教练。确实不会报错，但显示和提示词都是错的。
- 新版本自己也只能靠"值是否属于 `HandCat`"来区分新旧记录。
- 建议与 `posKey` 的做法对称：新增一个 `handCat` 字段，`handName` 继续按录制时的语言写入。
- 另外，`river_reviews` 里的复盘文本同样按录制时的语言保存、不做翻译，方案只提到了 `river_memory`。建议补一句，把用户预期说清楚。

### N4-3 "通过已有的 settings 事件通知界面"：这个事件不存在

- `Events`（`shared/types.ts`）里没有 settings 事件。现在设置是通过 `settings.update` 命令的返回值同步到界面的。
- 如果语言设为 `'system'`，只有主进程能拿到 `app.getLocale()` 的解析结果。渲染进程需要从 `Bootstrap` 和 `settings.update` 的返回值里拿到**生效后的** `Locale`，或者新增一个事件。
- 另外，`app.getLocale()` 必须在 `ready` 之后调用，和知识库里关于 `getPath` 的那条约束一样。

### N4-4 内置人设的"等于任一种子即视为未改"：与现有逻辑相容，但要改三处，并有一个语义限制

需要改的三处：

1. `loadPersonas`（`db/index.ts:242-254`）合并字段时，如果值等于任一种子，要当作 null 处理；`edited` 的判断（253 行）也要改用同一个谓词。否则英文界面下保存的种子值会被误标为"已改动"，界面上出现"恢复默认"。
2. `savePersona` 的 `diff`（276 行）目前只和中文种子比较。英文界面的表单预填的是英文种子，用户只改了 prompt，name 却会以 `'Foxy'` 写入数据库。好在读取规则能把它识别为"未改"，显示上不出错，但写入时就应该同时和两种语言的种子比较，免得存进冗余数据。
3. `personasCache` 是全局缓存。切换语言时必须重建，`personas` 事件也要重新推送。

**语义限制**：用户在中文界面里把"阿狸"改名为"Foxy"，这个值等于英文种子，会被判为"未改"，于是在中文界面下仍然显示"阿狸"。也就是说，用户的修改被悄悄丢掉了。

- `ini` 字段也有同样的问题，例如老K的中英文种子都是 `K`，不过两者相同，结果无害。
- 这是规则本身带来的取舍，应该写进方案并告知用户；另一种做法是在库里加一个"已编辑"标记。
- 此外还有一种混合情况：只改了 prompt 的内置人设，名字会随界面语言变化，prompt 却固定为用户写的那种语言。这一点可以接受，但建议写明。

### N4-5 i18n 与 ui、官网的关系：方向正确，还有一个未决项可以关闭

- 依赖方向：i18n 只引用 engine 的类型，主进程可以引用它，ui 不依赖它。ui 的 `labels: { pot, sb, bb }` 由两个应用从 `@river/i18n/poker` 取值后传入，ui 仍然保持"不含文案"。这个边界是正确的。
- 前面几轮留下的"`FELTS` 名称由调用方映射，或拆成中英两套，实施时二选一"，现在可以直接定为：名称放在 i18n 里、按 key 取。建议就此关闭这个未决项。
- 官网改为直接使用 app 的内置人设和提示词，这样 app 的英文提示词就成了唯一来源。设计稿里的 `PROMPT_EN`、`dEn` 以及 `river-site.js` 里的 `PERSONAS` 可以作为英文初稿，建议在方案里注明这一点。
- 设计稿 `HAND_EN` 用的是 `Trips`、`Quads` 这类词，最终写入字典的英文术语以 i18n 为准。

### N4-6 规模风险与交付顺序

- 按"非注释、含汉字的代码行"统计：`src/main` 约 134 行，`renderer` 约 264 行，`shared` 约 21 行，另外还有 8 份人设提示词和 3 种教练风格。
- 测试里含中文的行也不少，其中 `runner.test.ts` 152 行、`engine.test.ts` 100 行、`db.test.ts` 47 行、`agents.test.ts` 44 行、`thread.test.ts` 34 行。
- 这相当于在迁移和拆包之外，又叠加了一次覆盖全仓的改动。
- 建议在方案或 plan 里写明交付顺序：先完成迁移和拆包，通过打包验证后，再做 i18n。这样一旦打包出问题，不会和 i18n 的改动缠在一起。
- 另外说明测试默认使用 `zh`，现有的中文断言保持不变。

### N4-7 i18n 的验证缺少自动化

- `en: typeof zh` 只能发现字典缺词，发现不了代码里残留的硬编码中文。第 4 条验证全靠人工跑两种语言各一桌，很容易漏掉低频路径，比如退回、摊牌分池、stalled 报错、离桌、重新买入。
- 建议加一条成本很低的自动检查：在 `en` 下，对 `system()` 提示词、`text.ts` 的各个输出、`buildTableView` 的状态文字和结果横幅，用引擎随机压测跑若干手，断言输出里不含 CJK 字符。
- 再加一条 `newChat` 在英文下的测试，用来防止 B4-1 描述的回归。

- 中文行数是用正则粗略统计的，只能说明规模的量级。
- 没有核实 electron 在各个平台上 `app.getLocale()` 的具体返回值。
