## 判断

### 需求与契约：满足

对照 plan 的伪代码，逐个分支核对 `checkNow`：

```
checkNow(u = updater)
 ├─ ready 非空 ─────────────────────► { ready, version }      ✔ 与 plan 一致，且排在 !u 判断之前
 ├─ u 为空（dev 未初始化）───────────► throw 'updater not initialized'   （plan 未写，见 F3）
 └─ await u.checkForUpdates()
     ├─ 抛错 ───► log ──────────────► { error, t.checkFailed }  ✔ 不推送 update:error
     ├─ r 为 null / !isUpdateAvailable ► { latest }             ✔
     └─ isUpdateAvailable
          ├─ r.downloadPromise?.catch ─► log + emit update:error(t.downloadFailed) ✔
          └─────────────────────────► { downloading, r.updateInfo.version } ✔
```

- 契约与 task 表一致：
  - `UpdateCheck` 四种状态；
  - `Commands['update.check']: () => UpdateCheck`；
  - `Events['update:error']: { message }`；
  - `Bootstrap.packaged` 沿用 T4 的 `app.packaged`（ipc.ts:52），index.ts 传入的是 `app.isPackaged`。
- electron-updater 6.8.9 源码核实：
  - `checkForUpdates()`（AppUpdater.js:253）：
    - 未打包，且没有设置 `forceDevUpdateConfig` 时，resolve 为 `null`；
    - 已有检查在进行时，直接返回同一个 `checkForUpdatesPromise`，也就是**合并同时发起的检查**；
    - 检查失败时先 `emit('error')`，然后 rethrow。所以手动检查失败会同时走 `error` 事件（只写日志）和 catch（返回 error），不会重复提示。
  - `doCheckForUpdates()`（:400）：
    - 没有更新时返回 `{ isUpdateAvailable: false, updateInfo }`，没有 `downloadPromise` 字段；
    - 有更新时返回 `downloadPromise: this.autoDownload ? this.downloadUpdate(token) : null`。由于 `autoDownload = true`，有更新时一定有 downloadPromise。
  - `downloadUpdate()`（:435）：如果已经有下载在进行，直接返回同一个 `this.downloadPromise`，也就是**合并下载**，不会重复下载。失败时先 `dispatchError`（触发 `error` 事件），然后 reject；`CancellationError` 不触发事件。
  - 因此 plan 所说的“不需要自己加锁”和“重复点击不会重复下载”成立。代码用的 `r?.isUpdateAvailable` 和 `r.downloadPromise?.` 与库的返回值形状吻合。
- 后台行为与 d1eac45 对比，保持不变：
  - `autoDownload`、`autoInstallOnAppQuit` 仍为 true；
  - 10 秒后首次检查，之后每 6 小时检查一次；
  - `error` 事件只写日志；
  - `update-downloaded` 事件设置 `ready` 并推送 `update:ready`；
  - `update.install` 仍然先检查 `runner.table`，也就是只在不在牌桌上时安装（ipc.ts `update.install` 没有改动）；
  - `isPackaged` 判断从 updater 内部移到了 index.ts 的调用点，行为等价；
  - `installUpdate` 增加的 `!updater` 判断在运行时是冗余的，因为 `ready` 只可能由 updater 的事件设置，但它能让类型收窄，无害。
- 界面：
  - 版本行显示版本号和按钮；
  - `packaged` 为 false 时按钮置灰，说明文字换成“开发版本不检查更新”；
  - 请求进行中 `checking` 为 true，按钮禁用；
  - 四种结果都用 toast 展示，`update:error` 在 river.ts 里订阅后用 `toast.error` 展示。
- 文案：中文 7 条与 task 表逐字相同。英文 5 条除撇号外逐字相同：dict 用的是弯撇号 `’`（You’re、Couldn’t），这与 dict 里已有的英文写法（Can’t）一致，不视为偏差。`check`、`devOnly` 两条是表外的按钮和说明文字，措辞合理。

### 工程质量：良好

- 改动小而直接。`Updater = Pick<AppUpdater, …>` 只取用到的成员，替身容易构造。懒取 `electronUpdater.autoUpdater` 的原因写在注释里，而且确实是非显然的约束（这个 getter 取值时就会实例化）。
- 没有新增抽象，也没有新增依赖。
- 模块级的 `emit` 和 `updater` 状态沿用了原来模块级 `ready` 的写法，风格一致。

### 验收证据：自动部分充分，手动部分有缺口

- 单元测试覆盖了 task 要求的 6 种情形，另外加了 null 结果和定时检查失败两条。测试断言的是可观察的行为（返回值、是否 emit、是否再调用 checkForUpdates），不是在复述实现。
- 我做了 5 个变异：
  - M1：error 事件里推送 update:error；
  - M2：忽略 isUpdateAvailable；
  - M3：检查抛错时也推送 update:error；
  - M4：后台检查也跟踪 downloadPromise；
  - M5：autoDownload 改为 false。
- 结果：M1、M2、M3 各有一条用例失败；**M4、M5 都存活**（见 F1）。
- dev 截图显示版本行为“0.2.1 / 检查更新”（置灰），说明文字是“开发版本不检查更新”，与 commands.md 的描述一致。
- 打包版的手动验证（已是最新、断网时检查失败）还没做，这是 task 明确要求的手动项（见 F2）。
