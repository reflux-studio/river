## 结论：需修改

方向成立。U1、U3、U5、A3、A5、A7 都忠实落地。上一轮 10 条修改清单大部分已覆盖，或因用户新决定合理失效（见“上一轮修改清单对照”）。A4 的锁定做法是对“每一步先听教练说”的合理解读，用一个“同一时刻最多一个教练调用”的不变式替掉了原来的队列和抢占逻辑，简化效果明显。

需要修改的原因有四点：
1. **A1 的事实前提不成立（F1）。** 以现在的 Agent 构造方式，Mastra 1.69 **默认不重试**。p-retry 的默认 2 次会被 Agent 级的 `maxRetries ?? 0` 覆盖成 0。我用 mock 模型实测：默认只调用 1 次；给 Agent 配 `maxRetries: 2` 后调用 3 次，耗时约 3 秒。note 第 76 行、方案 §2 第 29 行、审阅 1 的 F1 都把默认值写成了 2。方案必须显式配置重试次数，否则“Mastra 已有重试”在代码里并不存在。
2. **新引擎 API 撑不起 runner 的几项需求（F2）。** 非法动作怎么规范化、重新买入、停下时本手作废、教练局亮出弃牌者的底牌、行动记录的结构，§4.1 都没有给出对应接口或语义，执行者只能自己猜。
3. **几处 AI 推断没有标出来，其中两处推翻了既有决定或会增加用户成本（F3、F4）。** 一是每手必须复盘，复盘结束前不能发下一手，同时删掉了设计稿里的“每手复盘”开关。二是去掉 Mastra 存储：ADR-003 的依据是用户“使用 Mastra storage 的 SQLite”这一决定，方案没提 ADR，也没说要不要请用户确认。另外，“串行写设计不再需要”的说法不准确。
4. **用量记账和教练局时序还有契约缺口（F5、F6）。** 手牌 id 在一手结束前还不存在；作废的那手用量怎么记；提醒的时限和“跳过”没写；问答历史的上限没写；硬核模式在自由局里没有入口。models.dev 价格这条前提的退路写了，但可以更稳（F7）。

## 发现（按严重程度）

### F1【高】Mastra 1.69 在现有 Agent 配置下默认不重试，A1 的前提与事实不符

依据：
- `@mastra/core/dist/agent-DwtTO5Px.js` 第 25135 行确实是 `retries: modelSettings?.maxRetries ?? 2`。但这里的 `modelSettings` 是每一步解析后的设置。第 26681 行：`maxRetries: modelConfig.maxRetriesConfigured ? modelConfig.maxRetries : modelSettings?.maxRetries ?? modelConfig.maxRetries`。单模型 Agent 的 `modelConfig` 来自 `prepareModels`，其中第 38720 行是 `maxRetries: this.maxRetries ?? 0`。构造函数第 34812 行是 `this.maxRetries = config.maxRetries ?? 0`。所以只要 Agent 构造时和调用时都不传 `maxRetries`，每一步的 `maxRetries` 就是 0，`?? 2` 永远不会生效。
- 现有代码 `agents/opponent.ts` 第 48 行、`agents/coach.ts` 第 42 行构造 Agent 时都没传 `maxRetries`，`mastra.ts` 第 94–103 行调用时也没传 `modelSettings`。
- 实测（`/tmp/rv2/retry.mjs`、`retry2.mjs`，mock 模型前两次抛 `ECONNRESET`/`fetch failed`）：

  | 配置 | 模型调用次数 | 结果 |
  | --- | --- | --- |
  | 默认（与现有代码相同，包括动态 model 函数和注册进 `Mastra` 的写法） | 1 | `generate` 直接抛错；`stream` 在 `error` 上返回错误 |
  | `new Agent({ …, maxRetries: 2 })` | 3 | 约 3.0 秒后成功（退避 1 秒 + 2 秒） |
  | 调用时传 `modelSettings: { maxRetries: 2 }` | 3 | 同上 |

- 其余几点 note 写对了：`isRetryableModelError` 对 `APICallError` 按它的 `isRetryable` 判断（第 24963–24968 行），Mastra 自己的超时不重试，`Retry-After` 最多等 30 秒（第 17680 行 `DEFAULT_MAX_RETRY_AFTER_MS = 3e4`），外部 `abortSignal` 能打断退避。还有两点方案没写：
  - 重试只包住“发起请求”这一段（第 25108–25130 行 p-retry 包的是 `doGenerate/doStream`），流式输出开始之后的中途错误不会重试。这对教练问答的流式回答有影响。
  - 最终失败时，`generate` 会抛出错误，`stream` 则把错误放在 `error` 上返回。现在的 `callAgent` 两种情况都接住了，改写时不要丢掉。
- 审阅 1 的 F1 第 41 行也写成了“默认可重试 2 次”，同样没看到 Agent 级的覆盖。这是上一轮审阅的错误，本轮更正。

影响：照方案实现时，如果执行者相信“Mastra 默认就有重试”，一次网络抖动就会直接进入 stalled，U2 说的“出错自动重试”实际上不存在。

建议：§2 改成“对手和教练的 Agent 构造时显式设 `maxRetries: 2`，这就是用的 Mastra 自带重试，不另写一层”（这样仍符合 A1）。plan 里加一个用 mock 模型数调用次数的测试（参考 `test/mock-model.ts`）。更正 note 第 76 行和 §2 第 29 行的“默认 2 次”。

### F2【高】§4.1 的 `Table` API 撑不起 runner 的几项需求，执行者需要自己猜

逐项对照 runner 现在的做法和方案新增的需求：

| 需求 | 现状 | §4.1 的缺口 |
| --- | --- | --- |
| 模型给出非法动作（面对下注时 check、`to` 超出范围、不能加注时 raise、bet 和 raise 混用） | `normalizeAct`（`runner.ts` 第 746–748 行）加上 `apply` 的静默纠正（`poker.ts` 第 193–194、199 行：check 变 call，raise 越界夹紧到合法范围） | poker-ts 风格的 `actionTaken` 遇到非法动作一般会抛错。方案没写 runner 是先规范化（怎么规范化）还是直接 stalled。`act` 的 action 枚举也没给：现有工具只有 `fold/check/call/raise`（`tools.ts` 第 94 行），`legalActions` 却区分 `bet` 和 `raise` |
| 可以过牌时弃牌 | 引擎接受（实测 `eng.ts`：大盲有 option 时 `apply(fold)` 返回“弃牌”），runner 把模型的 fold 改成 check | `legalActions` 在可以过牌时是否包含 `fold`，没写 |
| 对手破产后重新买入、玩家重新买入 | 直接改 `stack`（`runner.ts` 第 211、227–231 行） | 只有 `sitDown`，没有 `standUp`、`addChips` 或 `setStack`；也没写破产座位下一手是自动跳过还是需要离座 |
| stalled 时离桌，本手作废，筹码恢复 | 没有这个功能 | 需要 `abortHand()`（按本手开始时的筹码回滚），或者 `seats()` 暴露 `startStack`。还要写明：作废的那手不落库、不写 `river_hands` |
| 教练局一手结束时亮出所有底牌，包括弃牌者 | `record()` 只存摊牌时的底牌（第 560 行） | `holeCards()` 是否返回弃牌者的牌，没写。poker-ts 的同名方法对弃牌者不保证。需要写明：引擎返回全部底牌，按视角裁剪由 view 层负责（ADR-001 的信息隔离不变） |
| 公屏、回放、VPIP/PFR 统计 | `LogEntry.label` 是中文文案，VPIP/PFR 用正则从文案里匹配（第 567–568 行） | `handLog()` 的条目结构没写。建议用结构化条目 `{street, seat, type, amount/to, allIn, board?}`，文案由 runner 生成，统计不再依赖正则 |
| 概率面板（胜率与所需胜率） | `pot(g)` 加上 `legal().toCall` | `pots()` 是否包含本轮尚未收进池的下注，没写（poker-ts 的 `pots()` 不含）；要么写明计算公式，要么提供 `totalPot()` |
| 所有人弃牌、只剩一人时怎么结束 | `progress()` 直接判胜（第 224 行） | §4.1 的循环只写了 `areBettingRoundsCompleted()` 之后调用 `showdown()`。弃牌结束时是否也要调用 `showdown()`、`winners()` 返回什么，没写 |

§4.2 本身的表述是准确的，我补了一条复现，能说明第三条的影响比表格写的更大：
- 大码全下 10000，短码 2000 跟注，其余弃牌。摊牌输掉的大码出现在 `winners` 里：`{"id":"p2","amount":8000,"handName":"高牌"}`（`eng.ts`，`poker.ts` 第 245–250 行只有一人有资格分的那一层被当成“赢得”）。现在的公屏会显示“p2 赢得 8,000 · 高牌”，赢家发言也可能选中它。
- 弃牌结束的手：加注到 300 后其余人都弃牌，`winners` 的金额是 450，包含自己的 300。
- 前两条（不完整加注、余数分配）审阅 1 已经复现过。这三条就是这次改写范围内的全部规则错误。没有列出的死按钮、盲注补缴，因为对手破产后立即重新买入，桌上几乎不会出现空位，不修也可以接受。

建议：在 §4.1 补上 `standUp`/`addChips`（只能在两手之间调用）、`abortHand()`、`holeCards()` 的可见范围、`handLog()` 的条目结构、`pots()` 的口径、弃牌结束的路径。在 §2 写明 runner 的规范化规则：`to` 夹紧到 `chipRange`；toCall 为 0 时 fold 或 call 视为 check；该用 raise 却说了 bet（或反过来）按当前是否已有下注改写；面对下注说 check 时，按现有做法当作 call，还是当作 fold，二选一写死。随机压测也要覆盖“规范化之后 `actionTaken` 一定接受”。

### F3【中高】A4 的扩展和去掉 Mastra 存储，是没标出来的 AI 推断，其中两处需要用户确认

用户原话（A4）：“取消自动下一手，纯手动；教练局每一步先听教练说，避免竞态。”（A2）：“长期记忆若 Mastra 没有开箱即用的方案，就自己简单维护一份文档；长期记忆可有可无，代码要简洁。”

| 方案内容 | 性质 | 评价 |
| --- | --- | --- |
| 删除设置“自动下一手”（§3 第 57 行） | A4 原话的直接结论 | 忠实 |
| 轮到玩家时锁定，等教练返回再解锁（第 47 行） | 对“先听教练说”的解读 | 合理。但没写时限，也没有“跳过”，见 F5 |
| 删除“暂停牌局”工具与暂停遮罩 | 锁定之后的连带结论 | 合理，操作本来就被锁着 |
| 提问只能在教练空闲时发（第 49 行） | 为保证“同一时刻只有一个教练调用”加的限制 | 合理，是 A4“避免竞态”的延伸 |
| **每手必须复盘，复盘结束前不能点“下一手”；同时删掉设计稿的“每手复盘”开关（§9 第 136 行）** | AI 推断 | 用户没说要每手复盘。复盘现在的时限是 45 秒（`mastra.ts` 第 19 行），教练局每一手都要多等一次模型调用，也多付一次复盘的费用，而且没法关。更简单的做法是保留“每手复盘”开关（设计稿第 1294 行），关掉时一手结束就能直接下一手；或者在复盘进行中提供“跳过”（中止本次调用）。两种做法都不会引入竞态 |
| **去掉 `@mastra/memory`、`@mastra/libsql` 和 Mastra 的存储（§2 第 28 行）** | 由 A2 推出的 AI 推断 | 技术上成立（见 F4 的核实），代码更简洁，符合 A2 的“代码要简洁”。但它推翻了 ADR-003。ADR-003 第 3 行写明“用户决定使用 Mastra storage 的 SQLite”，ADR-002 的背景里也记着用户希望“Mastra 用得完善”。方案没提 ADR，也没请用户确认 |
| 新版本首次启动时删除 `mastra_*` 表（§8 第 127 行） | AI 推断 | 这是不可逆的数据删除：旧的对手“牌桌印象”、教练“学员档案”和问答记录都会丢失。应该写明，并请用户知情 |
| 由 A6 推出“启动时联网拉 models.dev，不做手填单价”（§6 第 106 行） | 对用户前提的更正加 AI 推断 | 方案指出了“模型列表并不是联网拉的”，这一点做得好。但“应用每次启动都访问第三方网站”是用户没说过的新行为，见 F7 |

影响：用户确认时，可能以为这些都是自己 A4、A2 的原意。复盘必做和删除旧数据，都会直接影响用户的体验和数据。

建议：§3、§2、§8 里把上面标粗的三项写成“AI 推断，需用户确认”，每项给出更简单的备选（保留“每手复盘”开关，或者提供“跳过复盘”；保留旧表不删，或者把旧的教练 working memory 转成一条 `hero` 记忆）。“去掉 Mastra 存储”要补一份 ADR 取代 ADR-003（见 F4）。

### F4【中】去掉 Mastra 存储的事实核实：可行，但方案有一处说法不准，也漏了 ADR 与迁移细节

已核实成立：
- **不带 Memory、直接传消息数组作为对话历史：可行。** `Agent.generate/stream(messages: MessageListInput, …)`（`agent/agent.d.ts` 第 1230–1245、1354 行）。`MessageListInput` 可以是 `ModelMessage`、`UIMessage`、`CoreMessage` 的数组（`agent/message-list/types.d.ts` 第 15–19 行）。实测传入 `[user, assistant, user]` 三条，模型收到的 prompt 就是 system 加上这三条（`retry.mjs` 的最后一段）。
- **Agent 不需要 storage。** 独立的 Agent（不注册进 `Mastra`）可以正常 `generate`，`provider-test` 现在就是这么用的（`models/resolve.ts` 第 77 行）。如果仍然 `new Mastra({ agents })` 但不传 storage，Mastra 会退回内存存储，并打一条 WARN：“No `storage` configured … falling back to an in-memory store”（`mastra-C3fk5HTu.js` 第 1039–1046 行）。实测连续 30 次 `generate` 后，内存存储里的 workflow run 数为 0，不会越积越多（`mem.mjs`）。
- **删除 `mastra_*` 表：安全。** 在临时库上跑 `LibSQLStore.init()`，一共建了 44 张表，全部以 `mastra_` 开头；配套的索引名不带这个前缀，但会随表一起删掉；没有触发器，没有视图；`river_*` 表没有外键引用它们（`tables.mjs`；`db/index.ts` 第 19–29 行）。

需要改正或补充：
- **“上一轮的 BUSY 重建与串行设计也随之不再需要”（§2 第 28 行）只对一半。** `withRetry` 的换 client 逻辑（`db/index.ts` 第 45–73 行）确实是为了和 Mastra 争锁才加的，可以简化。但 `write()` 的串行写链（第 75–106 行）解决的是“读-改-写基于缓存，并发调用互相覆盖”，和 Mastra 无关，必须保留。另外 `@libsql/client` 的 sqlite3 客户端内部是连接池（`lib-esm/sqlite3.js` 第 323–335 行），`db/index.ts` 第 262 行的注释也提到了这一点。所以即便只剩业务层一个写入方，也不宜删掉 BUSY 处理，最多改成不再换 client。
- **WAL 模式：** 现在是 LibSQLStore 设的（实测新库在它 init 之后变成 `journal_mode = wal`，ADR-003 第 26 行也有记录）。老用户的库会一直保持 WAL（这个模式写在文件里），新用户的库会是默认的 rollback 日志。二者都能用，但应该写明：要么由业务层显式设 WAL，要么接受这个差异。
- **删表的做法要写成迁移步骤：** 从 `sqlite_master` 里按 `name LIKE 'mastra\_%' ESCAPE '\'` 枚举，逐个 `DROP TABLE IF EXISTS`，因为不同版本的 Mastra 建的表集合不同，而且 `_` 在 LIKE 里是通配符。删表放在一个带 `user_version` 的迁移里执行。可以另做一次 `VACUUM` 回收空间，也可以不做。要注明不支持降级：旧版本打开后会重建空的 Mastra 表，旧的记忆找不回来。
- **ADR：** 方案全文没有提到任何 ADR。ADR-003 需要一份新的 ADR 取代，写明“Mastra 不再使用存储，业务层独占 `river.db`，写纪律改成只保留串行写链”。ADR-002 第 15 行“印象与漏洞由 agent 通过 working memory 工具自行更新”已经不成立，需要加注。ADR-001 的决定不变，但第 20 行的理由（“工具在同进程直接读引擎”）在对手只剩 `act` 以后变弱了，可以加注说明。`river-v2/adr/` 目录目前是空的。
- 相关的删除项要列进 §2 的删除清单：`test/db-mastra.test.ts`，`mastra.ts` 里的 `appendThreadMessage`、`resetMemories`、`closeMastra` 的 storage 关闭，`AgentDeps.appendResult`，`db/index.ts` 第 50–57、108 行的注释。

### F5【中】教练局时序还剩几处缺口

- **提醒的时限与重试：** 方案只给了对手决策的时限（45 秒）。提醒现在的时限是 12 秒（`mastra.ts` 第 19 行）。F1 修好以后，提醒也会重试，锁定时间会更长。提醒的时限、是否重试，都要写明。建议提醒时限 12–15 秒、`maxRetries` 设为 1，并在锁定区放一个“不等了”按钮（中止本次调用并解锁）。这仍然满足“同一时刻最多一个教练调用”。
- **轮到玩家、提醒结束后提问：** 第 49 行说提问“发出后等回答完成”。这段时间内操作区是否再次锁定，没写。按 A4 的精神应该锁定，否则玩家可以一边等回答一边行动，回答就会晚到。
- **问答怎么调用：** 现在的问答有 `view_hero`、`estimate_equity`、`recent_hands` 三个工具，`maxSteps: 6`（`coach.ts` 第 66–76 行）。方案只写了提醒用 `maxSteps: 1`、把局面写进输入，问答保留哪些工具、局面是否也写进输入、是否仍用流式输出，都没写。
- **对话历史的内容与上限：** “本桌对话历史由 TableRunner 保存并在每次调用时传入”，没写上限。长桌打下来 token 会一直增长。提醒和复盘是否也算进历史，同样没写。建议只保留最近 N 轮问答（例如 6 轮），提醒和复盘不进历史。
- **提醒沉默时模型只回了文字：** `toolChoice` 为 `auto` 时，模型可能不调 `hint`，只输出一段文字。这段文字是丢弃，还是当成提醒显示，要写明。教学牌局“每步必提醒”在这种情况下怎么处理，也要写明。
- **玩家破产时：** 教练局复盘进行中，“重新买入”是否也要等复盘结束，没写。
- **硬核模式在自由局没有入口：** 硬核模式的开关只在教练栏里（`CoachPanel.tsx` 第 176 行），面板在开启时会隐藏概率（第 135 行）。自由局没有教练栏，如果全局开了硬核模式，自由局唯一的面板就被隐藏，而且在牌桌上关不掉。建议写明自由局不受硬核模式影响，或者在自由局的概率面板上放同一个开关。
- **回放页的复盘：** 自由局手牌在回放页能不能发起复盘，没写。A3 只说牌桌上不显示教练相关的内容。

### F6【中】用量记账的数据契约有漏洞

- **手牌 id 在一手进行中还不存在：** `river_hands.id` 是自增列，一手结束时 `insertHand` 才分配（`db/index.ts` 第 213–219 行）。对手决策和提醒都发生在这之前，所以 `river_usage` 的“手牌 id”在调用时拿不到。建议改成按 `(table_id, hand_no)` 关联（`river_hands` 本来就有这两列），或者一手结束时回填。
- **作废手的用量：** stalled 时离桌，本手作废、不落库，但这手里已经发生的调用确实花了钱。要写明这些调用计入总量，但不出现在每手的柱状图里。
- **“本桌 $x”需要 table id：** `river_usage` 的字段表（§8 第 125 行）里没有 table id。要么加上这一列，要么写明“本桌”只在内存里累计。
- **部分有价、部分无价：** 对手用有价格的模型、教练用 OpenAI 兼容接口时，顶栏和统计页怎么显示，没写。建议显示“$x + y token 未计价”，或者在旁边加一个标注。
- **计价的时间点与缓存 token：** 用量是按记录时的价格存下来，还是显示时再按最新价格重算，没写。`totalUsage` 里的 `cachedInputTokens` 是否按缓存价计，也没写。建议记录原始 token，显示时再计算，缓存部分先按输入价算，并注明是估算。
- **“清空记录”的语义：** 审阅 1 修改清单第 5 条要求写明“清空记录”要不要一并清掉用量统计，第 3 轮仍然没写。设计稿第 1308 行的说明是“清除手牌历史、复盘和统计”，而统计页另有“清零”按钮（第 1277–1278 行）。

### F7【中低】models.dev 价格：前提未实测，退路写了，但有更稳的做法

已核实：
- Mastra 自己的 `ModelsDevGateway` 就是请求 `https://models.dev/api.json`（`models-dev-DGhYpTYG.js` 第 11430 行）。它把顶层的键当作提供方 id，每个提供方下面是 `models[modelId]`（第 11435–11470 行）。包内 `provider-registry.json` 的提供方 id 就是这样生成的（`gateway: "models.dev"`），所以按“提供方类型 + 模型 id”查价，在 key 上是对得上的。
- 没能核实：`cost` 字段（每百万 token 的 input、output、cache_read，单位美元）。Mastra 的代码不读这个字段，本会话也连不上 models.dev（note 第 79 行）。

风险与退路：
- 方案已经写了“失败用缓存，还没有就只显示 token”（§6、§11），退路成立。但第一次启动时如果离线或被墙，就一直没有价格。而且每次启动都会访问一个第三方站点，这个行为用户没提过。
- 更稳的做法：CI 构建时拉一次 `api.json`，只截取 cost 字段，打进应用作为内置快照（体积很小）。运行时再拉一次作为刷新，失败就用快照。这样离线也有价格，也不依赖运行时访问第三方。
- 把“核实 `cost` 字段”写成首个实施任务的验收条件，note 第 79 行已经这样写了，plan 里也要写上。
- 设计稿里还有两处和价格相关的元素没处理：统计页的“≈ ¥”换算（第 1269 行，汇率写死为 7.1），以及说明文字“Token 按字符数估算……Haiku 4.5 输入 $1……”（第 1279 行）。现在改成了真实用量和 models.dev 价格，这两处都要改。

### F8【中低】对手记忆与角色快照的细节

- **记忆条数会很快被刷掉：** `note` 每次 `act` 都可以带，每个角色只保留最近 10 条（§2 第 27 行）。一手里对手可能行动 3–6 次，模型一旦每次都写，10 条只够记住最近一两手，谈不上“长期记忆”。建议在提示词里写“只有新的观察才写”，并在代码里限制每手最多追加 1 条（例如只取本手第一条或最后一条）。用户说过长期记忆“可有可无”，所以做到最小实现就够了。
- **快照和“提示词下一次决策就生效”互相矛盾：** §5 第 99 行说“入座时保存角色快照，删除只影响下一桌；编辑提示词从下一次决策生效”，快照里到底包不包括提示词，没说清楚。建议写成：决策时读角色表里最新的提示词，角色已被删除时用快照。设计稿对手页的副标题“改动下一手生效；本地引擎按四项倾向来打”（第 236 行）也要跟着改。
- `act` 的 `say` 超过 40 字截断、`note` 超过 30 字怎么处理，没写（截断还是丢弃）。
