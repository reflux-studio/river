## 结论：需修改

实现总体符合第 5 轮契约。引擎的三处规则修正正确，逐条推演和压测都没有发现错误。runner 的停下、重试、离桌作废、教练互斥、过期结果丢弃，以及信息隔离，读代码和写探针验证后都是对的。删除清单也执行干净：`src/main`、`src/shared`、`test` 中已没有托管、熔断、闲聊、Mastra Memory 或 LibSQLStore 的代码和注释，只剩两处提到旧字段的迁移说明，属于合理保留。

需要修改的有三类：

1. **测试保护不住关键路径（F1、F2）**。我对 runner 做了 13 个变异，只有 1 个被现有测试发现。其中“对手的输入改成玩家视角（能看到玩家底牌）”“教练局进行中亮出所有底牌”“对手读到 `holeAfter`”“提问期间不暂停牌局”都能让 15 条 runner 测试全部通过。plan §验证点名要求的场景，有一半没有被真正断言。
2. **用量归属有实现缺陷（F3）**。用量回调是全局的，每条记录归到“回调触发那一刻”所在的牌桌和手。玩家在有牌桌时去回放页发起复盘，这次花费会记到当前牌桌的当前手，并计入顶栏“本桌 $x”和那一手的柱状图。
3. **契约偏差没有记录（F4、F5）**：`river_hands.record.log` 仍然存中文文案，不是结构化条目；缓存输入 token 按缓存价计费，不是按输入价加“估算”标注。

### F3【需修改】用量归属依赖全局监听和回调时刻的牌桌状态

- **问题**：`llm.ts` 第 18–19 行只有一个模块级监听器 `onUsage`。`runner.ts` 第 84 行在构造时注册；第 559–566 行按回调触发时的 `this.table` 与 `handNumber()` 写入 `tableId`、`handNo`，并追加到本桌的 `this.usage`。所以：
  1. 玩家有桌时在回放页发起复盘（`runner.review`，第 450–460 行），这次用量会记到当前牌桌的当前手，计入顶栏“本桌 $x”，也会让当前手出现在柱状图里。App 的页面结构允许在保留牌桌的同时切到回放页（HEAD 的 `App.tsx` 第 17–19 行）。
  2. 离桌时被中止的调用，回调在 `table = null` 之后才到，于是 `table_id` 为空；如果紧接着入座新桌，还可能记到新桌的第 1 手上。
- **依据**：discussion §6“每次调用一行 `river_usage`：用途、`table_id`、`hand_no`…”；plan §关键流程“runner 附上 `tableId`、`handNo`”。
- **复现**：探针 P10。第 1 手结束、第 2 手开始后，模拟一次复盘用量回调，得到的记录是 `{"tableId":"c547…","handNo":2,"purpose":"recap",…}`。
- **建议**：发起调用时就确定归属。例如 `callModel` 增加一个 `tag: { tableId, handNo } | null` 参数并原样传给回调；runner 在发起对手、讲解、提问、复盘调用时传入当时的牌桌和手号，`review()` 传入被复盘那一手的 `tableId` 和 `hand_no`（可用 `river_hands` 查到），或者传 `null`。`this.usage` 只累加 `tag.tableId === this.tableId` 的记录。这样也不再需要全局可变的 `setUsageListener`。

### F4【需修改：实现，或写入 T5 结果】`river_hands.record.log` 仍存中文文案

- **问题**：§8 要求“`log` 改为结构化条目（旧记录保留文案字段，回放兼容显示）”。实际上 `handRecord`（`text.ts` 第 140–144 行）仍然只存 `{street, board, name, label, cards?}`，没有 `seat/type/amount/to/allIn`。VPIP/PFR 已经改为在落库前从结构化的 `handLog` 计算（第 173–174 行），但记录里不保留结构化数据。回放页将来如果要按条目显示筹码动效或另做统计，就只能回头解析文案。
- **建议**：在 `HandLogEntry` 上增加可选的 `seat`、`type`、`amount`、`to`、`allIn`，照常保留 `name` 和 `label`，这样旧记录仍能显示。如果决定不做，就在 T5 结果中写明偏差和理由，并同步修改 discussion 或 plan。

### F5【低；写入 T5 结果】缓存 token 计价与 §6 不一致

- **问题**：§6 写的是“缓存输入先按输入价计，注明‘估算’”。`prices.ts` 第 47–52 行在有 `cache_read` 价格时按缓存价计费，也没有“估算”标记，测试（`prices.test.ts` 第 28–34 行）断言的正是这种行为，所以是有意为之。T1 已确认 models.dev 有 `cache_read`，按缓存价更准确，可以接受，但需要记录。另外，`costOf` 假设 `inputTokens` 包含缓存部分（`input - cached`）。AI SDK 的 OpenAI 实现是这样，但 Anthropic 的 `inputTokens` 不含缓存读取，这时缓存部分会被 `min(cached, input)` 截掉而少算。当前应用没有显式启用提示缓存，影响很小。
- **建议**：在 T5 结果中写明这一偏差，以及不同提供方下 `inputTokens` 含义不同；如果统计页要保留“估算”字样，由 T7 处理。

### L1【低】`pots()` 不合并资格相同的相邻层，与 `winners().pot` 编号不一致

- **位置**：`table.ts` 第 287–300 行。`showdown()`（第 228–230 行）会合并资格相同的相邻层，`pots()` 只在资格为空时合并。
- **复现**：探针 P11，`pots()` 给出两个资格都是 `[0,1]` 的池（30 + 40），`winners()` 只有 `pot:0` 一个池。现在没有调用方使用 `pots()`；将来界面如果用它显示“边池”，会凭空多出一个边池。
- **建议**：`pots()` 按同样的规则合并（`last.eligible.join() === eligible.join()`），并补一条带弃牌者的测试。

### L2【低】死代码

`runner.ts` 第 596–602 行的 `lines()`、`board()` 注释写着“测试与调试用”，但仓库里没有任何调用方。`Table.numSeats()` 也没有被使用。建议删除（`standUp` 属于 §4.1 契约，保留）。另外，`private snapshots` 声明在第 127 行、两个方法中间，建议移到其他字段那里。

### L3【低】价格快照为空，提取逻辑写了两份

`src/main/models/prices.json` 是 `{"at":0,"prices":{}}`，首次启动且离线时会全部显示“token 未计价”。plan 写的是“仓库内提交一份初始快照，CI 覆盖”。`scripts/prices.mjs` 第 7–14 行与 `refreshPrices`（`prices.ts` 第 26–34 行）的提取逻辑完全相同。建议在有网络的环境跑一次 `node scripts/prices.mjs` 并提交结果（或在 T8 中确认 CI 构建前会执行它），并把提取逻辑合成一处（例如让脚本 import 一个纯 JS 的 `extract` 函数）。

### L4【低】回放页复盘不受牌桌互斥约束

`runner.review` 用 `AbortSignal.timeout(60_000)`，而 `coachRecap` 内部已经限时 45 秒，外层的 60 秒不会起作用。回放复盘也可能与牌桌上的教练调用同时进行。§3 的互斥只针对牌桌，这里不算违约。建议把外层超时去掉，或改为可以取消的 controller。

### L5【低】提问恰好发生在落库之前时，复盘可能不写入 `river_reviews`

一手刚结束、`insertHand` 还在等待时（`runner.ts` 第 506–515 行），`ask` 是允许的（`coachBusy === null`）。回答结束后 `runAsk` 立即开始复盘，此时 `lastRecord.id` 可能还是 `null`，复盘成功后也不会调用 `saveReview`。这个时间窗只有毫秒级，而回答要几秒，实际很难触发。建议 `runRecap` 在调用结束后读取最新的 `this.lastRecord.id`，而不是用开始时拿到的 `last`。

### L6【低】测试覆盖的其他缺口

- 最短显示时长、超时（45 s、20 s）没有测试；超时路径在 `llm.ts` 第 103–115 行，逻辑简单，可以不补。
