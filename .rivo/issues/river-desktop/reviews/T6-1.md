## 2. `lib/river.ts` 与 T5 约定

| 约定 | 实现 | 结论 |
| --- | --- | --- |
| 先注册监听，再调用 bootstrap | `init()` 先执行 `listen()`，再 `invoke('app.bootstrap')`；`main.tsx` 在模块顶层只调用一次（不在 StrictMode 的 effect 里） | 符合，不会重复订阅 |
| 公屏按 id 去重 | `chat:append` 先查 id；bootstrap 用快照覆盖 `chat` | 符合。主进程在最后一个 await 之后同步读取快照并返回，所以返回前到达的事件都已包含在快照中，覆盖不会丢消息 |
| `coach.ask` 的 requestId 缓存 | `early` Map 暂存返回前到达的 delta 和 done，`askCoach` 返回后取出并合并 | 符合。有一处小泄漏，见 F2 |
| 入座前清空 | `startTable` 在调用命令之前清空 `chat`、`coach`、`alert` 和 `early` | 符合 |
| 教学牌局后重读设置 | `if (opts.guided) await reloadSettings()`，即发送 `settings.update({})` 取回最新值 | 符合 |
| `table:view` 为 null 时回到大厅 | 监听器中 `!v && page==='table'` 时切回 lobby；`App` 还加了一层保护：`want==='table' && !hasTable` 时显示大厅 | 符合 |

内存与订阅方面：`useEvent` 在 effect 中订阅，卸载时通过 preload 返回的 remove 函数退订，没有泄漏；`useRiver` 基于 `useSyncExternalStore`，选择器都返回已有引用或原始值，不会无限重渲染。开发环境的 HMR 如果重新执行 `main.tsx`，全局监听会重复注册，但这只影响开发，不处理也可以。

## 发现

### F1（文案，建议本任务修改）：AI 对手页的说明写“三项倾向”，卡片却有四项

原型只有三条倾向条（紧度、攻击性、诈唬），所以写“按下面三项倾向来打”。现在加入了健谈度，读者会以为本地引擎按上面三项、或者按全部四项来打。实际上健谈度不影响出牌，只影响预设台词出现的概率；另外本地引擎的 `decide` 还用到了不显示的 `call` 字段（`poker.ts` 第 276–277 行）。

建议改为：“LLM 按它来决策、说话；本地引擎按紧度、攻击性、诈唬等倾向来打，健谈度决定说话多少。提示词可以直接改，下一手生效。”这只是改一行字符串。

### F2（低）：`early` 缓存可能残留无人认领的条目

`coach:delta` 和 `coach:done` 在找不到对应回答时一律写入 `early`，但只有 `askCoach` 会取出。以下两种情况会留下永远不会被取走的条目：

1. 重载时有回答正在进行：bootstrap 返回之前到达的 delta 进入 `early`，而 `coachThread` 快照的文本已经包含这部分内容，这些条目不会再被使用。
2. 入座新桌：`startTable` 先清空 `early`，随后主进程离开旧桌，中止进行中的提问，旧 requestId 的 `coach:done`（interrupted）在清空之后到达，又被写入 `early`。

每次只多出一两条，占用内存有限，不影响正确性。修法很小：只在 `coach.ask` 命令尚未返回时才暂存（维护一个计数或标志），其他时候丢弃未知 id 的事件。

### F3（低）：编辑提供方时可以改类型，旧 key 会被悄悄沿用

编辑模式下，只要 `keyTail` 存在，`needKey` 就为 false。于是把 openai-compatible 改成 anthropic（或反过来）时，可以不输入新 key 就保存，主进程的 `saveProvider` 会沿用旧密文。这样做很可能用错 key，报错也会出现在测试连接或牌桌上，比较难定位。建议在编辑模式下锁定类型选择；或者类型变化时把 key 设为必填。
