### 推定规则与偏差

| 偏差/推定 | 判断 |
| --- | --- |
| libsql 连接池使 `PRAGMA foreign_keys` 无效，`clearHistory` 显式删 reviews | 成立。0.18.0 的 `file:` 客户端是连接池（`ConnectionPool`，`concurrency` 默认大于 1），PRAGMA 只作用于执行它的那条连接；SQLite 默认关闭外键。显式删除比 `concurrency:1` + PRAGMA 更可靠（连接失效重建后 PRAGMA 会丢）。注释写的是“为什么”，合格 |
| 外键失效对未来路径的影响 | `ON DELETE CASCADE` 在本应用里实际永远不生效。当前 plan 只有“清空记录”一条删除路径，已覆盖。若将来加“删除单手”，必须在同一 batch 里显式删 `river_reviews`，否则留下孤儿评语（AUTOINCREMENT 不复用 id，不会挂到新手牌上，只是泄漏）。建议在 T3“结果”中记一句，见 A2 |
| `getSettings` 同步 | 合理：`resolveModel` 需要同步读取，且缓存由 `initDb` 与所有写路径维护 |
| 编辑不带 key 保留原 key | 与 plan 设置页只显示“已保存 ····末 4 位”一致，编辑时 UI 不可能回填明文，必须如此 |
| 非 openai-compatible 无 key 报错 | 与 plan 407 行“仅 openai-compatible 允许为空”一致 |
| keyTail 无 key 时为 `null`、删除时清 tail | 合理；`ProviderPublic.keyTail: string \| null` 已写入类型 |
| `getProviderSecret` 解密失败抛出 | 与 task 264 行 T4 `modelReady`“解密失败时置 needsKey”分工一致 |
| `updateSettings` 对 `models` 浅合并，清角色需传 `undefined` | 可用：Electron IPC 的结构化克隆保留值为 `undefined` 的键。但 plan 的 `settings.update: Partial<Settings>` 按字面是顶层替换，嵌套合并是额外约定，T6 需要知道。见 A1 |
| `supportsRequired` 改 key/baseUrl 后不重置 | 应在 **kind 或 baseUrl 变化时重置为 null**。该值描述的是“这个端点是否接受 `toolChoice:'required'`”；换了端点，旧的 `true` 会让决策模式在新端点上以 required 调用被拒，按错误进入重试/熔断，旧的 `false` 则让本可 required 的端点退化为 auto。仅换 key（同一端点）可以保留。见 Q1 |
| `initDb` 未接入启动流程 | 可以接受，T5 负责接线；task T3 没要求接入 |
| T2 `poker.ts` 自定义 `Card/Street` | 与 `shared/types.ts` 结构相同，类型上兼容，不影响 T3。违背“共享类型定义在 shared/types.ts”的约定，应由 T2 改为从 shared 导入，见 S1 |

### 工程质量

- 实现紧凑，没有多余抽象；`kvUpsert` 被 batch 复用，合理。
- 注释四处（迁移事务、getKv 合并、clearHistory、keyTail、getProviderSecret）都在讲“为什么”，符合注释规则。
- `getSettings()` 返回缓存对象本身，调用方原地修改会绕过持久化；目前各写路径都是整对象替换，风险低，不单列。

### 测试是否检验目标行为

| 验收项 | 测试 | 能否区分通过和失败 |
| --- | --- | --- |
| 迁移可重复执行 | 写 bankroll → 关库重开 → 值还在、`user_version=1`、五张表 | 能 |
| 默认值读取 | 四个 kv 逐一比较 | 能 |
| settings 部分更新合并 | 两次 patch 后比较缓存与重启后值 | 大体能。`want` 由 `getSettings()` 派生，若合并误丢其他顶层字段，缓存与重启后值会同样丢失、测试仍通过；建议直接写出完整期望对象（Q2） |
| hands 插入与倒序、`handsForPersona` 过滤 | 覆盖倒序、limit、无匹配 | 能 |
| 删除被引用提供方后 models 清空 | 两角色分别引用两提供方，删一个后只清对应角色，并验证重启后持久化 | 能（仅串行场景） |
| `clearHistory` 余额与 reviews | 由于 id 不复用，若没删 reviews，`getReview(id)` 会非空 | 能 |
| 脱敏不含明文 | 替身密文为 `enc:<明文>`，若脱敏结果带上密文字段，`not.toContain` 会失败 | 能 |

没有覆盖：并发写（B1）、`getProviderSecret` 解密失败抛出、kind 变更后的 `supportsRequired`。

## 发现

| # | 类型 | 位置 | 描述 | 建议 |
| --- | --- | --- | --- | --- |
| B1 | 应修复 | `src/main/db/index.ts` `updateSettings`、`updateLobby`、`deleteProvider` | 读-改-写之间有 `await`：新值从旧快照计算，写库后才更新缓存（lobby 甚至每次异步从库读）。探针实测：`Promise.all([updateSettings({speed:2}), updateSettings({hard:true})])` 后 `speed` 仍为 1；`updateLobby({size:3})` 与 `updateLobby({blinds:2})` 并发后 `size` 仍为 6；`deleteProvider(a)` 与 `updateSettings({speed:0})` 并发后 `settings.models.opponent` 仍指向已删除的 a，这就是 T3 验收要防的状态。T5 的 IPC 处理器与内部调用（如删提供方同时保存设置）都可能并发触发 | 根因是“基于旧快照写”。最小修法二选一：① settings 在 `await` 之前同步算出 `next` 并赋给 `settingsCache`，`deleteProvider` 同样先同步更新缓存再写库；lobby 也改为内存缓存或同样处理；② 模块内用一条 Promise 链串行化所有读-改-写。补一条并发测试（上述 delete + update 组合即可） |
| Q1 | 应修复（小） | `saveProvider` | 编辑时 `kind` 或 `baseUrl` 变化仍沿用旧 `supportsRequired`，而且 upsert 的 `DO UPDATE` 也不写 `supports_required` | `kind`/`baseUrl` 变化时置 `null`，upsert 一并更新该列；仅换 key 可保留。补一条测试 |
| Q2 | 可选改进 | `test/db.test.ts` “settings 部分更新合并” | 期望值从被测结果派生，对“合并丢字段”不敏感 | 写出完整的期望 Settings 字面量 |
| A1 | 待对齐 | `updateSettings` 的 models 嵌套合并 | plan `settings.update: Partial<Settings>` 字面是顶层替换；当前是 models 按角色合并，清除某角色要传 `{models:{coach:undefined}}` | 在 T3“结果”中写明该语义，供 T5/T6 使用；或改回顶层替换（UI 手里本来就有完整 models），两者都可以，关键是记录 |
| A2 | 待对齐 | `river_reviews` 外键 | `ON DELETE CASCADE` 在连接池下实际不生效，任何删除 hands 的路径都必须显式删 reviews | 在 T3“结果”中记录这条约束（“修改已被其他任务使用的约定需记录”） |
| E1 | 证据缺口 | `getProviderSecret` | 解密失败抛出是 T4 needsKey 的依赖，但没有测试 | 用会抛错的 decrypt 替身补一条，或在 T4 覆盖 |
| S1 | 可选改进（归 T2） | `src/main/engine/poker.ts` 3、5 | 重复定义 `Card`、`Street` | T2 改为从 `../../shared/types` 导入 |
