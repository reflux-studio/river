## F2 `early` 缓存：已解决，没有违反 T5 约定

实现方式：`askCoach` 在 invoke 前把 `asking` 加 1，在 `finally` 里减 1。`coach:delta` 和 `coach:done` 只有在找不到对应回答、并且 `asking > 0` 时才写入 `early`。`askCoach` 取走自己 id 对应的条目后，如果 `asking === 0`，就清空 `early`。

先说明为什么清空不会误删：`asking` 统计的是 Renderer 这边还没有 resolve 的 `coach.ask` promise。所以 `asking === 0` 时，任何未知 id 都不可能再被某个 `askCoach` 取走。另外，invoke resolve 之后，`askCoach` 要经过几段 microtask 才能执行到 `setState` 插入回答，而 IPC 事件属于宏任务，不会插到这些 microtask 中间。因此不会出现回答已经返回、但事件既没进 `early` 也没被 `hasAnswer` 接住的空档。

逐个场景推演，并用探针验证：

| 场景 | 过程 | 结果 |
| --- | --- | --- |
| 1. 两个并发提问 A、B | 两个 invoke 都发出后 `asking=2`。A 先返回，`asking=1`：A 取走自己的条目，不清空，B 的暂存保留。A 返回后才到达的 B 的 delta 仍然写入 `early`。B 返回时 `asking=0`：B 取走自己的条目，然后清空 | 探针断言 A 的回答是 `text:'a1'`、`interrupted`，B 的回答是 `'b1b2'`、`pending`，随后 done 能接上。**没有误删在途提问的事件** |
| 2. 提问返回前事件先到 | 这时 `asking>0`，delta 和 done 都暂存。返回后合并到回答里，done 先到的情况会通过 `applyDone` 结束 pending | 符合 T5 约定（探针里 A 的 done 就是先到的） |
| 3. 重载时有回答在途 | 刚加载时 `asking=0`，bootstrap 返回前到达的 delta 直接丢弃，快照 `coachThread` 已经包含这部分文本。返回后的 delta 通过 `hasAnswer` 接到快照条目上 | 探针断言结果为 `'snapX'+'Y'`，没有重复拼接，也没有残留 |
| 4. 入座新桌后，旧提问的中断事件才到 | `startTable` 清空 `early` 和 `coach`。主进程 `leave()` 中止旧提问，`runAsk` 之后发出 `coach:done(interrupted)`。这时 `hasAnswer` 为假，`asking=0`，事件被丢弃 | 探针断言新桌的 `coach` 为空。之后一个复用同一 id 的提问不会带出旧文本，说明 `early` 确实是空的 |
| 5. 两个提问之间出现无人认领的 id（比如主进程 preempt 旧提问后发出的 done） | 如果到达时 `asking>0`，会被暂存，等 `asking` 回到 0 时一起清空 | 探针里的 `stray` 条目最后被清掉了 |

`reject` 路径（未配置、熔断、没有牌桌）在主进程用 `setImmediate` 推迟 done，保证事件晚于命令返回，与本次改动配合正常。

## F3 编辑提供方时锁定类型：已解决

`ProviderDialog.tsx:75` 在编辑时（`!!provider`）把 Select 设为 `disabled`，标签旁提示“换类型请新建提供方”。这样 `kind` 保持为原来的值，“留空时沿用旧 key”就只会用在同一类型上。Form 放在 `DialogContent` 里，每次打开对话框都会重新挂载，所以 `kind` 的初始值每次都来自当前编辑的 provider，不会把上一次的状态带过来。

主进程的 `saveProvider` 仍然允许带 id 修改类型，限制只在界面这一层。Renderer 是本应用自己的代码，这不构成安全问题，也不需要再改。

## App.tsx：安全

`PAGES: Record<Page, React.ComponentType>` 的写法只在类型位置用了 `@types/react` 的全局 `React` 命名空间，typecheck 已通过，不需要引入值。六个页面组件都不接收 props，`<Page />` 调用和这个类型一致。以后如果某个页面需要必填 props，这里会直接报类型错误，不会悄悄放过。没有改变运行时行为。

## 观察

### O1（可选，极低）：`coach.ask` 抛错时不会清空 `early`

如果 invoke 抛错，`finally` 会把 `asking` 减 1，但异常直接往上抛，后面的 `if (!asking) early.clear()` 不会执行，期间暂存的无主条目要等下一次成功提问、`asking` 回到 0 时才会被清掉。主进程的 `ask()` 是同步返回 id 的，实际上只有 IPC 本身出故障才会抛错。条目数量有上限，也不影响正确性。如果想修，可以把清空也放进 `finally`，但不修也可以。
