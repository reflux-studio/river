## R1 关键顺序是否被破坏

| 项 | 核对 | 判断 |
| --- | --- | --- |
| 出错连接不再接到写入 | 业务写入经 `writeChain` 串行执行。每次尝试都在 `fn(db())` 里重新取 client，`fn` 只在同步调用里用到 `c`。重建 client 与出错在同一个 catch 里同步完成 | 成立 |
| 下一次写入之前关闭 | 关闭推迟到 `setImmediate`，下一次尝试至少在 100 ms 的 `setTimeout` 之后。**探针 P1**：给 `db-mastra` 场景插桩，每次尝试前检查“上次出错的 client 是否已关闭”以及“当前 client 是否曾经出错”。跑 3 次，每次 402 次尝试（其中 1 次 BUSY），两项违例计数都是 0 | 成立 |
| 最后一次失败（第 5 次） | 先重建 client 并登记关闭，再抛出；随后 `finally` 里的重载用的是新 client | 成立 |
| 提示：测试能守住什么 | **探针 P2**：把关闭推迟到 150 ms（晚于下一次写入），`db-mastra` 3/3 仍然通过。这与前轮 E3/E4 一致：真正必须满足的是“出错连接不再写入”（前轮 E5 去掉重建后 3/3 失败，这一点有测试守着），关闭时机本身不影响正确性。现在的 `setImmediate` 两者都满足，注释的表述也准确，不需要修改 | 提示 |

## generation 与 closeDb 并发的边界

| 场景 | 核对 | 判断 |
| --- | --- | --- |
| 旧写入正在退避 | 醒来后在循环开头检查到代数已变，直接抛出，不调用 `db()`，所以不会用到新 client | 正确（新用例覆盖） |
| 旧写入还排在旧写链上 | `closeDb` 把 `writeChain` 换成新的 resolved Promise，新代数的写入不会等旧链。旧链上排队的写入轮到自己时，进入 `withRetry` 就被代数检查拒绝，不会碰库。调用方要等旧链队首退避结束才收到拒绝，最多等约 800 ms，可以接受 | 正确 |
| 旧写入在 catch 里（代数已变） | `gen !== generation` 时直接抛出，不会用 `createClient` 覆盖新代数的 client。这一行的检查是防止“旧写入替换新 client”的关键 | 正确 |
| 旧写入的 catch/finally | 不置 `cacheStale`，不减 `pendingWrites`，不重载；`writeChain = p.catch(() => {})` 不会产生未处理的拒绝 | 正确 |
| 只 `closeDb`、不 `initDb` | 旧写入以 `db closed or reopened` 被拒绝；此后调用 `write` 时，`db()` 同步抛出 `db not initialized` | 正确 |
| 迁移 | `initDb` 先调用 `closeDb` 再迁移，迁移的 `withRetry` 默认取递增后的代数。两个 `initDb` 并发时，先开始的那个会被后开始的那个的代数拒绝，属于合理行为 | 正确 |
| 缓存重载进行中调用 `closeDb`/`initDb` | **探针 P3**：让写入立即失败（NOT NULL）以触发重载，在 0–15 层微任务深度调用 `initDb(另一个库)`，新库分“全新”和“已迁移”两种，共 32 组。结果全部正确：缓存与新库一致；随后 `updateLobby` 之后，缓存与库都是 3；旧库没有被写入；没有未处理的拒绝。唯一的副作用：旧重载失败时把 `cacheStale=true` 设到新代数上，只会让新代数第一次写完后多重载一次，结果仍然正确。这种情况只有在“别处代码在微任务里调用 `closeDb`”时才会出现，写入的调用方自己碰不到（它要等 `finally` 重载完才收到结果） | 提示，不需要修改 |
| 读取 | 读不经过代数检查。`closeDb` 之后，已发出的读可能收到 `CLIENT_CLOSED` 或 `db not initialized`，属于关闭语义，可以接受 | 正确 |
