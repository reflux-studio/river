# 设计审阅 1：River 桌面版方案

## 审阅对象

| 项 | 版本 / 位置 |
| --- | --- |
| 方案 | `discussion.md`（第 1 轮快照，179 行） |
| 调查与决定 | `note.md`；`adr/001`（提议）、`adr/002`（接受）、`adr/003`（接受） |
| 设计稿 | `design-source/River.dc.html`（918 行，逻辑 298–915 行；模板 1–297 行） |
| Mastra 依据 | 临时目录中的 `@mastra/core` 1.69.0、`@mastra/memory`、`@mastra/libsql` 的内置文档与 dist 源码 |
| 前轮审阅 | 无（首轮） |

## 结论：需修改

整体方向成立：主进程单一写入者、工具按 `requestContext` 裁剪视角、不用 Workflow、单个 SQLite 文件，这几项都能对上用户决定和 Mastra 的实际能力。核心决定也标明了是用户选的还是 AI 推导的，ADR-001 的“待确认”状态写得清楚。

需要修改的原因是，几条核心契约留给了执行者自己猜，而这些契约不定下来，主要场景就会出错：工具是直接改状态还是只登记意图；同一 persona 或教练的并发调用怎么串行；对手的记忆从哪里拿到一手牌的结果。另外有两处偏离用户原话的地方还没有经用户确认。

```
主要场景检查路径（6 人桌一手）
 startHand ─► AI 行动 ──────────► 玩家回合 ──────────► 公屏发言 ─────► 结束落库
               │ F2 act 契约        │ F2 pause_game 契约   │ F1 并发写      │ F3 结果不回流到对手
               │ F1 闲聊并发        │ F1 提问/主动并发     │ F5 与原话偏离  │ F7 退出时丢筹码
               └ F4 连续超时        └ F6 未配置时的教学局
```

## 发现（按严重程度）

### F1【高】同一 persona、同一教练的并发调用没有串行规则，working memory 会丢更新

证据：
- §5.2 只规定“闲聊模式挑选当前不在决策中的对手”，没有规定反方向。对手 X 的闲聊调用（最长 8 秒）还在跑时轮到 X 行动，TableRunner 会对同一个 `resource=opponent:X` 再发起一次决策调用。闲聊用哪个 thread 也没写，如果也用 `table:<tableId>:<personaId>`，两次调用会读同一份历史，结束时各自追加消息。
- 教练同样有这个问题。§5.3 中主动提醒在玩家回合开始时发起，玩家可以在它返回前提问（设计稿 `askCoach` 不检查 loading）。两次调用都在 `coach:<tableId>`、`resource=hero` 上。设计稿导航允许牌桌进行中切到回放页，复盘调用（`review:<handId>`，同为 `resource=hero`）也可能同时在跑。
- 核对结果：`@mastra/memory` 的 `updateWorkingMemory`（dist `src-zTE4189S.js` 约 31493 行）按 resource 加的是进程内 `Mutex`，只把写入串行化。方案选的是 Markdown 模板（§5.2“模板”），文档 `docs-memory-working-memory.md` 第 277 行写明模板是“replace semantics”。两次调用在开始时读到的是同一份 working memory，后写入的那份会整份覆盖先写入的，mutex 挡不住这种丢更新。

后果：阿May 在闲聊里写下的“上头”心情，或者教练在复盘里记下的“常见漏洞”，会被另一个同时进行的调用覆盖掉。这正好冲着用户要的“尽量拟人”的记忆去。消息历史的顺序也会交错。

需要方案定下的契约：同一个 memory resource 同一时刻最多一个调用。可以是按 resource 排队，可以是决策到来时中止闲聊，也可以是闲聊和提问用只读 working memory（Mastra 支持 `readOnly: true`，见上述文档第 382 行）。还要写明闲聊用哪个 thread。具体选哪种由用户决定。

### F2【高】工具的副作用契约没定：`act`、`say`、`hint`、`pause_game` 是直接改状态还是只登记意图

证据：
- §3 说 TableRunner 是“唯一写入者”，§5.2 又把 `act` 叫作“终止工具：提交 …”，§5.3 的 `pause_game` 会“暂停牌局”。方案没说工具的 `execute` 是直接修改牌局，还是只写进本次调用的结果槽、由 TableRunner 事后校验再提交。
- 核对结果：`generate` 的 `toolCallConcurrency` 默认值是 10（`reference-agents-generate.md` 第 97 行）。同一步里模型可以并行发出两次 `act`，或者 `act` 和 `say` 一起发。`stopWhen` 只在一步结束后才判断。
- §5.3 写的是“玩家已行动后返回的结果丢弃”。如果 `pause_game` 在工具执行时就置了 `paused`，等 generate 返回再丢弃结果已经晚了：玩家点了跟注，教练晚到的 `pause_game` 仍会让牌局在 AI 回合停住。设计稿是先返回 JSON、再核对 `heroKey`、最后才生效，不存在这个问题。
- 超时中止之后，已经发出的 `say` 可能照样写进公屏；离桌 `runId++` 之后，工具执行也可能晚到。

后果：可能重复行动、状态被改两次、暂停出现在不该出现的时候。“过期结果丢弃”这条规则在工具层会失效。

需要方案定下的契约：每个有副作用的工具在哪一刻生效、带哪个 key 做校验（`runId`、手号、`log` 长度或 `heroKey`），以及同一调用里多次调用 `act` 时以哪一次为准。

### F3【中高】对手记忆没有数据来源：拿不到一手牌的结果，就更新不了“被抓过的诈唬”“心情”

证据：
- §5.2 的 working memory 模板要记对玩家的印象（包括被抓过的诈唬）和当前心情。ADR-002 的理由是“印象与漏洞由 agent 通过 working memory 工具在下次调用时自行更新”。
- 但对手的工具只有 `view_table`（本手）、`estimate_equity`、`read_chat`、`say`、`act`。摊牌时的底牌、最终输赢、玩家亮出来的诈唬，都不会出现在对手的 thread 里。设计稿的公屏系统行只有“X 赢得 N · 牌型”（第 619 行），不含摊牌牌面。弃牌之后才结束的手，对手连赢家是谁都看不到。
- 教练有 `recent_hands`，对手没有对应的工具。

后果：用户点名要的三项记忆，其中两项缺少输入，模型只能凭空编。

需要方案补上的内容：一手结束后，对手通过什么途径拿到结果。比如给 `view_table` 增加“上一手摘要”，增加一个工具，或者在下次调用的输入里注入摘要。

### F4【中】连续超时或提供方不可用时没有降级，一手牌会拖到分钟级

证据：§4 规定每次决策超时 10 秒后回退并标“托管”，满足用户“超时回退本地并标记”的决定。但方案没有熔断规则：断网、提供方故障或限流时，6 人桌每个 AI 每次行动都要等满 10 秒，一条街可能要 50 秒。设计稿用 `modelBad` 和调用预算自动改用本地引擎（第 386–388 行、设置页第 874 行的说明）。方案删掉了预算，却没有补上替代机制。§10 只写了“托管率显示在设置页”。

后果：相关失败场景（对手 agent 超时）下，牌桌实际上没法玩。

需要方案补上的内容：连续失败时的降级规则，以及它怎么显示。这涉及用户能看到的行为，需要用户确认。

### F5【中】公屏回应规则偏离了用户原话，而且没有标成 AI 建议

证据：
- §1 记录的用户原话是“对手看到也可随时回”。§5.2 加了两条限制：回应人数按话痨程度取 0/1/2，所以“安静”档下玩家说话在对手自己的回合之前没人回；对手之间的发言不触发回应。设计稿是 `[1,2,3][chatty]`（第 603 行），“安静”也至少回 1 人。首启引导页还写着对手“也会互相调侃”（第 895 行）。
- §2 的“有意变化”表把这一项和其他 AI 自选项（删除用量显示、保留全部手牌、新增托管率显示、教练流式输出、复盘入库）和用户决定混在一张表里，没有区分哪些是 AI 建议。
- 设计稿里手牌结束时赢家会说获胜台词（第 620 行），弃牌和跟注时也有预设台词。方案没说一手结束时对手是否发言，也没说托管行动是否配台词。

后果：范围有收缩也有新增，但用户没有确认过。

需要方案做的事：把这些 AI 建议单独列出来，请用户确认，或改回设计稿行为。

### F6【中】未配置模型时，教学牌局和“带我打一手”失去核心价值

证据：§6 规定未配置时教练栏显示“配置模型后可用”。但引导页最后一页的“带我打一手”和大厅的“教学牌局”（第 291、176、817 行），都依赖教练每一步至少给一次 hint。首次启动还没配置模型时，用户走的正是这条路径。

后果：新用户点进教学局，看到的是一个不说话的教练。

需要方案补上的内容：这条路径的行为，例如入口处引导先配置模型，或用本地规则建议生成提示。

### F7【中低】中途退出应用时，牌桌上的筹码怎么处理没有写

证据：设计稿入座时从余额扣买入，离桌时退回（第 408、637 行）。桌面版如果在牌桌进行中退出，TableRunner 的内存状态就没了。§7 的 `river_settings` 只存余额，没存牌桌状态，也没说 `before-quit` 时要退回筹码。

后果：每次关窗口都会损失一次买入，统计里的净盈亏和余额也对不上。

### F8【中低】引擎移植的源码不在仓库里

证据：`design-source/` 下只有 `River.dc.html`。note 里只有 `poker.js` 的要点，没有源码。§9 的引擎测试写的是“移植后用固定牌例测试”，但移植要依赖 `newGame / legal / apply / runoutStep / equity / outs / decide / handName / disp / txt / fmt` 这些函数的真实实现，它们散落在设计稿各处。

后果：执行者需要重新登录设计项目才能拿到源码，否则只能凭要点重写，边池、单挑盲注这类细节容易与原型不一致。

建议在实施前把 `poker.js` 存进 `design-source/`。

### F9【低】几项已核对的机制，方案可以用上

- `generate` 支持 `activeTools` 和 `toolChoice: 'required'`（`reference-agents-generate.md` 第 87、175 行）。闲聊模式裁剪工具可以直接用 `activeTools`，不需要第二个 Agent。决策调用可以考虑用 `toolChoice` 提高 `act` 的调用率，应对 §10 里“小模型不稳定调用 act”的风险。“教学牌局至少 hint”目前只靠提示词保证。
- 应用不做代码签名，Electron `safeStorage` 在 macOS 上依赖钥匙串。重新构建后签名身份会变，已保存的 key 可能弹出授权或读不出来。建议把这一项放进首个验证任务，并定好读不出时的行为（提示重新输入 key）。

## 已核实、成立的部分

- 动态模型：`Agent.model` 是 `DynamicArgument<MastraModelConfig>`，`OpenAICompatibleConfig` 支持 `{id, url?, apiKey?}` 和 `{providerId, modelId, url?, apiKey?}`（`llm/model/shared.types.d.ts` 第 24–37 行）。
- 动态 instructions 和 tools：`agent/types.d.ts` 第 541、608 行都是 `DynamicArgument`。
- `stopWhen`：类型是 AI SDK 的 `StopCondition`（`loop/types.d.ts` 第 28、192 行），可以写自定义条件。`maxSteps`、`abortSignal`、`onAbort` 都存在。
- 工具隔离：身份来自 TableRunner 设置的 `requestContext`，模型无法篡改。对手 thread 按 persona 分开，历史里只有自己的底牌。`TableView` 不下发未摊牌的底牌。`recent_hands` 用的是原型 `rec` 结构，只有摊牌时才保留他人底牌。在这些前提下，按身份裁剪能挡住跨身份泄牌。剩下的漏洞来自 F2（工具生效时机），不来自数据可见性。
- 不用 Workflow 的理由成立：没有需要离线编排的多步流程。
- 页面与交互逐项对照设计稿：大厅预设和选人、牌桌快捷键、下注预设和步进、收起公屏和最后一条预览、重新买入、自动下一手、暂停遮罩和“我看完了，继续”、教练人设切换、讲解深度、快捷提问、硬核模式、AI 对手页（编辑、重置、加入下一桌）、回放与复盘、统计（6 项 KPI 和最近 40 手柱状图）、设置、5 页引导。除 F5、F6 提到的几处外，没有发现遗漏。

- 以上 Mastra 结论来自文档、类型和 dist 源码阅读，没有实际运行，也没有在 Electron 里验证。并发丢更新是按源码逻辑推出来的，没有复现。
- 没有读到 `poker.js` 原文，引擎规则只能按 note 和设计稿里的调用来判断。
- 项目目录、首发 macOS、ADR-001 仍待用户确认。这几项不影响上面的发现，但 ADR-001 如果改成子进程方案，F1 里“进程内 mutex”的前提需要重新核对。
