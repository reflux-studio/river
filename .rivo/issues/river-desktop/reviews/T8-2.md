## 探针做法

执行者没有真正触发乱序和失败分支，所以本轮自己构造。仓库没有 jsdom，也不想动 T7 正在用的 Electron 实例（9337 端口），于是：

- 在 scratchpad 里起一个独立的 headless Chrome for Testing（自己的 profile、CDP 端口 9555），打开正在运行的 vite dev 服务（`localhost:5173`）同源下的一个静态地址。
- 在页面里装好 react-refresh 的 preamble，把 `window.river` 换成 mock：每次 `invoke` 都挂起成一个 deferred，由脚本决定先后顺序和 resolve/reject；`on` 用一个 Set 记录监听，脚本可以直接派发 `hands:changed`。把 sonner 的 `toast.error` 换成记录函数。
- 从 dev 服务直接 import 真实的 `/src/pages/Stats.tsx`、`/src/pages/Replays.tsx`，用和 `main.tsx` 相同的预打包 React，以 `StrictMode` 挂载（与应用一致，挂载时 effect 会跑两次，正好也是一次“连续加载”）。

完成后已关闭这个 Chrome。

## F1：已解决

两页的做法相同：`seq` 是一个 ref，每次加载先 `++seq.current` 并记下编号 n；成功和失败的回调都先判断 `n === seq.current`，不等就什么也不做。失败时 `setFailed(true)` 并 `toastError`，已有数据不清空。

```
 load#1 ──────────────────────────────┐ (慢)
 load#2 ─────┐                         │
             ▼ n=2==seq ✓ setH(新)     ▼ n=1≠seq ✗ 丢弃（成功或失败都不动 state、不 toast）
```

| 场景 | 过程 | 结果 |

`hands:changed` 刷新与选中：`useEvent` 用 ref 保存最新回调，`loadList`/`load` 每次渲染重建也只依赖 `seq` 这个 ref，没有过期闭包问题。`selId` 的推导和详情 effect（带 `live` 守卫）没有改动，R1、R2、R5 的结果与第 1 轮核对的行为一致。

## 观察（不影响通过）

### O1 卸载后失败的请求仍会弹 toast

S4 中，统计页卸载后才失败的加载仍然调用了 `toastError`（seq 只防乱序，不防卸载）。错误是真实的，用户已离开页面时多看到一条提示，影响很小。若要避免，可以在卸载时 `seq.current++` 让在途请求全部作废，一行即可；不改也可以。

### O2 首次加载中与重试中没有进度提示

统计页 H 为 null 且未失败时是空白（第 1 轮已有）。点“重试”后，在途期间按钮仍显示“加载失败，重试”（S2 记录的文本），重复点击只会用新请求取代旧请求，不会出错。数据是本地库，通常很快，可以不改。

### O3 回放页详情读取失败时右侧空白

不属于 F1，也不是本轮改动引入的：`hands.get` 失败时只 toast，`detail.id !== selId`，右侧为空白，没有重试入口。用户点别的手再点回来可以重试。可以留到之后一起处理。
