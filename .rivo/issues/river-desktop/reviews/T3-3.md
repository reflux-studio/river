## 结论：通过（有 2 个次要发现，建议在交付前顺手修掉，或明确转交 T5）

R1 已解决。我独立复现了执行者的两个关键结论：
- libsql 0.18 的连接在一次写入得到 BUSY 后会“静默丢写”；
- 业务层与 Mastra 各建 client、并在 BUSY 后重建 client 再重试，数据能正确落库。

另外补充了一点：被污染的连接一旦又执行过写入，即使 `close()` 也不会释放写锁。所以“BUSY 后在下一次写入之前关闭 client”这个顺序是方案成立的关键。当前实现满足这一点：业务写入经写队列串行执行，关闭发生在同一个 catch 里。

缓存重载的主路径正确：最终失败的写入之后，缓存会回到库中的值；后续写入成功时缓存也与库一致。事件循环不会被阻塞。

两个次要发现：
- **F1**：BUSY 触发关闭 client 的那一刻，同一轮微任务里正在进行的读会收到 `CLIENT_CLOSED`。
- **F2**：写入还在退避时调用 `closeDb`/`initDb`，旧写入会重试到新库上，写计数也会被打乱，导致缓存与库不一致。只在关闭或重开时触发，生产环境中概率低。

`pnpm test` 34/34 通过，`pnpm typecheck` 无错误。

## 独立复现（探针，已删除）

| 实验 | 步骤 | 结果 |
| --- | --- | --- |
| E1 静默丢写最小复现 | WAL 模式。client B 开 `transaction('write')` 占锁；client A 执行 INSERT，得到 BUSY；B 回滚后，A 在同一 client 上再次 INSERT | A 第一次写得到 `SQLITE_BUSY`；第二次写**成功返回**（rowsAffected 1）。A 自己读得到 1 行，全新连接读到 0 行；A `close()` 之后，新连接仍读到 0 行 |
| E2 丢写后 close 不释放锁 | 接 E1：新连接 C 写入 → 关闭 A → C 再写入 | C 两次都得到 `SQLITE_BUSY`：A 的 `close()` 被 `closeQuietly` 吞掉，连接没有真正释放。**结论：必须在下一次写入之前关闭；写入之后再关闭就来不及了** |
| E3 BUSY 后立即重建 | 与 E1 相同，但 A 得到 BUSY 后马上 `close()` 并新建 client，再写入 | 新 client 写入成功，新连接读得到；C 也能正常写入。之后写 200 行，`wal_checkpoint(TRUNCATE)` 返回 `busy:0`，WAL 被截断为 0，没有残留的读快照占住 WAL |
| E4 被污染连接不关闭时的读取 | A 得到 BUSY 后不关闭；B 提交后，A 读取 | A 读到的仍是 0 行（**旧快照**），但不会挡住其他连接写入。说明关闭除了防止丢写，也能避免读到过期数据 |
| E5 去掉重建的变异 | 复制 `index.ts` 并删掉 `db().close(); client = createClient({ url })`，用 `db-mastra.test.ts` 跑 3 次 | 3/3 失败；未修改的原版 3/3 通过。说明这个测试确实依赖“重建 client” |
| 阅读 `@libsql/client` 0.18 `sqlite3.js` | `ConnectionPool` | 非事务操作都是“借出连接 → 同步执行 → 归还”。`release` 只在 `db.inTransaction` 为真时回滚，BUSY 后留下的隐式读事务不会被发现。`close()` 会同时关闭空闲和借出中的连接，并让排队的请求以 `CLIENT_CLOSED` 失败 |
| 阅读 `@mastra/libsql` 1.23.1 | `LibSQLStore({ url })` | 本地文件会带上 `timeout: 5000` 创建 client，并设置 `journal_mode=WAL`、`busy_timeout`、`synchronous=NORMAL` 等参数。传入 `client` 时跳过这些设置。写入按 client 串行执行（`withClientWriteLock`） |

执行者的推论成立：连接池不能单独淘汰一条连接，只能关闭整个 client；共用 client 时，关闭会打断 Mastra 正在进行的事务。所以“各建 client、共用同一个文件”是唯一可行的组合。Mastra 连接上的 `busy_timeout=5000` 会同步等待，但业务写入都是一次同步调用（`execute` 或 `batch`），不跨 await 持锁，JS 线程上的 Mastra 调用碰不到业务侧持锁的时刻，所以这里的同步等待不会发生。

## 实现安全性

| 项 | 核对 | 判断 |
| --- | --- | --- |
| 写入之间的重建 | 写入经 `writeChain` 串行执行；`fn(db())` 在每次尝试时重新取 client；关闭与重建在同一个 catch 里同步完成，被污染的连接不会再接到写入（满足 E2 的要求） | 正确 |
| 同一轮微任务里正在进行的读 | 探针：锁住库后发起 `updateSettings`，同时在 0–11 层微任务深度并发发起 12 个 `getBankroll()`。**深度 1 的那个读被拒绝，错误为 `CLIENT_CLOSED: The client is closed`**，其余成功。发生在退避期间的读全部成功（用的是新 client） | **F1**，次要 |
| 迁移阶段 | 探针：锁 250 ms 时，`initDb` 在约 309 ms 内经重试成功。锁一直不放时，`initDb` 以 `SQLITE_BUSY` 拒绝，模块停留在“有 client、没有表”的状态，随后写入报 `no such table`；再次调用 `initDb` 可以恢复。迁移的建表语句和 `PRAGMA user_version` 在同一个 batch 里，失败时版本号不会前移 | 正确。T5 必须把 `initDb` 失败当作启动失败处理（见衔接说明） |
| 重建期间排队的写入 | 后续写入排在当前写入的 Promise（包括它的 `finally` 重载）之后，重建期间不会有第二个写入并发 | 正确 |
| `closeDb` 发生在退避期间 | 探针：写入被拒绝，错误为 `db not initialized`（不是 BUSY，所以不会继续重试）。缓存停留在领先库的值；重载也因为 `db()` 抛错而失败，`cacheStale` 保持为 true | 关闭时可以接受 |
| `closeDb`/`initDb` 发生在退避期间，然后打开另一个库 | 探针：库 1 上的写入在退避时关闭并 `initDb(库 2)`。**这次旧写入在库 2 上重试并落库**（库 2 的 settings 出现 `speed:2`）。`initDb` 把 `pendingWrites` 置 0 之后，旧写入结束时又减 1，计数变成 -1。之后在库 2 上：A 最终失败、B 排在 A 后面，计数被判为已清空，于是在 B 执行之前就重载了缓存，结果**缓存 lobby=6，库 lobby=3**，要等下一次失败才会纠正 | **F2**，次要（生产环境只在启动时 `initDb` 一次） |
| 事件循环 | `close()` 与 `createClient()` 都是同步调用，开销很小（打开一个连接并执行 `SELECT 1`）；退避用 `setTimeout`。db.test.ts 中测得的最大间隔小于 100 ms；我的探针里 BUSY 立即返回 | 正确 |
| `isBusy` | 匹配 `SQLITE_BUSY*`、`SQLITE_LOCKED*` 这两类错误码，以及 “database is locked” 这段错误文字；`write` 模式的 batch 在 `BEGIN IMMEDIATE` 时就报 BUSY，属于 `LibsqlError`，会被匹配 | 正确 |

## 最终失败后的缓存重载

| 场景 | 核对 | 判断 |
| --- | --- | --- |
| 全部失败 | db.test.ts：锁一直不放，4 种写入都被拒绝；settings、lobby、providers 回到库中的值 | 正确（M3 变异能检出） |
| A 最终失败，排在它后面的 B 成功 | A 结束时计数大于 0，暂不重载；B 用包含 A 补丁的缓存快照写入并落库；队列清空后再重载，缓存与库一致。探针：A=`speed:2` 失败，B=`hard:true` 成功，最终缓存与库都是 `speed 2, hard true` | 正确。副作用和前轮一样：A 的调用方收到拒绝，但这个补丁已经被 B 带进库里。T5 在界面上不要把拒绝当作“一定没保存” |
| `saveProvider` 失败，之后 `setSupportsRequired` 成功（更新 0 行） | 队列清空后重载，失败时临时加入缓存的提供方被移除 | 正确 |
| 重载的执行时机 | 重载放在失败写入的 `.finally` 里，而 `writeChain` 串在这个 Promise 后面，所以重载期间不会有写入落库，调用方也要等重载完成才收到拒绝 | 正确 |
| 重载期间入队的写入（`pendingWrites > 0` 分支） | 本地 client 的读取只经过微任务（`acquire` 立刻 resolve），重载在一个宏任务内就完成了，IPC 这类宏任务无法插进来，这个分支实际上几乎触发不到。假如真的触发：重载会把 B 的缓存改动覆盖掉，直到 B 落库后第二次重载为止；如果此期间 B 正在退避，第三次写入 C 会从缺少 B 补丁的缓存出发，写入后覆盖 B | 提示，不单独列为发现。触发条件是 loadCaches 中出现真正的异步间隙，将来改为远程 client 时需要重新评估 |

## 发现

| # | 类型 | 位置 | 描述 | 建议 |
| --- | --- | --- | --- | --- |
| F1 | 次要缺陷 | `withRetry` 第 61 行 `db().close()` | 同一轮微任务里并发发起的读，如果已经拿到了旧 client，会以 `CLIENT_CLOSED` 被拒绝（探针复现）。T5 中 `Promise.all([写, 读])`、结算后并发读 `recentHands` 这类写法可能碰到，表现为一次偶发的读取失败。读取本身不需要重试 | 最小修法：先换引用，下一个宏任务再关闭，例如 `const old = db(); client = createClient({ url }); setImmediate(() => old.close())`。同一轮微任务里的读会在旧连接上同步做完，最多读到几微秒前的快照（E4）；写入不会用到旧 client（每次尝试都重新取 `db()`，而且下一次尝试至少在 100 ms 之后）。也可以不改实现，改为在 T5 的衔接说明里写明读取可能偶发 `CLIENT_CLOSED` |
| F2 | 次要缺陷 | `initDb` 第 111–113 行、`closeDb` | 写入在退避中时调用 `closeDb` 再 `initDb`：① 旧写入会用新的全局 client 重试，写进另一个库；② `pendingWrites` 被重置后又被旧写入减 1，变成负数，此后“队列清空才重载”的判断提前触发，缓存与库长期不一致（探针：缓存 lobby=6，库 lobby=3）。生产环境中只在启动时 `initDb` 一次、退出时 `closeDb`，所以概率低；vitest 中反复重开时可能出现，排查会很困难 | 让旧写入感知 client 已被 `closeDb`/`initDb` 替换，不再重试。例如给 client 加一个代数：`closeDb`/`initDb` 时递增，`withRetry` 发现代数变化就直接抛出。或者 `closeDb` 先 `await writeChain` 再关闭，`initDb` 不再重置计数 |
| D1 | 交付项 | T3“结果”、ADR-003 | A1、A2（前轮）以及上表的 5 条衔接约定都没有写进 task/ADR | 交付时写入 T3“结果”；ADR-003“后果”补上“两个 client、libsql 0.18 缺陷、升级后重新验证” |
