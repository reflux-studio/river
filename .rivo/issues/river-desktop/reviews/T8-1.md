## 2. 发牌行、托管标记、玩家行底牌

- **发牌行**：引擎在第 223 行写入 `{street, board: true, label: 公共牌文本}`；`runner.record()` 把它转成 `board: !!x.board, name: ''`。`streetsOf` 遇到 `board` 为真的行就开一个新分组（名称取 `STREET[street]`，副文字为 label），不把它放进胶囊；翻牌前没有发牌行，由 `!out.length` 开出第一个“翻牌前”分组。这和原型第 846 行的逻辑一致。翻牌前全弃的手牌只有一个分组。截图 replays-latest.png 与 hands-dump.json 中 id 4 的 log 对得上。
- **托管标记**：`commitOpponent` 在托管时设置 `g.log[at].autopilot = true`（runner.ts:321），`record()` 只在为真时带上 `autopilot: true`，页面据此在胶囊后加“托管”小标签。链路完整；runner.test.ts:120 覆盖了 log 上的标记，但没有真实托管数据的截图，留给 T9。
- **玩家行底牌**：`record()` 只给玩家本人和摊牌时未弃牌的玩家填 `hole`，其余为 null。页面对 null 按 `folded` 显示“已弃牌”或“未亮牌”，没有别的底牌来源，不会泄露未亮底牌。hands-dump 中 id 3 阿狸（弃牌，hole null）显示“已弃牌”，与截图一致。
- 列表 key：公共牌用牌面（一手内不会重复），玩家行用 `p.id`，都唯一。

## 3. 复盘卡状态与 `review:done`

状态表（`d.review` 为已保存的复盘，`loading` 与 `failed` 是页面内按 handId 记录的集合）：

```
                 ┌──────── 点击（ready 且 !loading）────────┐
                 │                                          ▼
 [无复盘：按钮] ──┘                               [loading：教练正在回看这一手…]
      ▲    ▲                                                │
      │    │   review:done{error} / invoke 抛错             │ review:done{text}
      │    └──── [失败：按钮 + “复盘失败，稍后再试”] ◄──────┤
      │                                                     ▼
 未配置教练：按钮禁用 + “配置教练模型后可用 · 去设置”     [有复盘：显示文本，无按钮]
```

- 与主进程语义一致：`review()` 对未配置、找不到、失败、中止、被拒都会发 `review:done{error}`；成功时先 `saveReview` 再发 `{text}`，所以之后 `hands.get` 一定能读到复盘。页面对 error 一律显示“复盘失败，稍后再试”并保留按钮，可以重试。
- 同一手重复点击：页面用 `reviewing.has(id)` 挡住，加载中也不显示按钮；主进程 `this.reviewing` 同样会忽略。
- 切页后再回来：页面状态丢失，按钮会重新出现。如果此时再次点击，主进程会静默忽略这次请求，但第一次请求结束时仍然会发 `review:done`，新挂载的页面已经注册了监听，会收到并清掉 loading，不会卡住。成功的结果已经落库，重新进入时由 `hands.get` 读出。唯一的损失是：如果失败发生在页面卸载期间，回来后看不到“复盘失败”，只能看到按钮，可以接受。
- 复盘完成时用户正看着另一手：`setDetail` 只在 id 相同时更新；切回那一手时会重新调用 `hands.get`，能读到已保存的复盘。
- `clearHistory` 之后：`river_hands` 使用 AUTOINCREMENT，id 不会复用，旧的 `reviewing`/`failed` 集合不会误伤新手牌。
- 小瑕疵（不单列）：未配置教练且某手曾经失败过时，“配置教练模型后可用”和“复盘失败”会同时出现。这种情况很少，可以不改。

## 4. `hands:changed` 刷新

- 回放页：重新调用 `hands.list`。`picked === null`（跟随最新）时 `selId` 自动切到新的一手并重新读取详情；用户手动选了旧手牌时保持不变。清空记录后列表为空，`selId` 为 null，详情清空。渲染时加了 `detail.id === selId` 判断，不会短暂显示上一手的详情。证据中挂载状态下再打 2 手，列表从 4 条变为 6 条，详情切到最新一手。
- 统计页：每次都重新加载全部手牌，见 F1、F3。

## 5. KPI 与柱状图复算

实现中的公式与原型第 853–866 行逐项对照一致：`pct` 以手数为分母并四舍五入；赢下的手牌按 `net > 0` 计；摊牌胜率以摊牌手数为分母；柱状图取最近 40 手，`mx = max(1, |net|)`，柱高为 `max(2, |net|/mx*76)`，`net >= 0` 时向上画绿柱，否则向下画红柱。`loadAll` 把倒序列表反转成时间正序，`Promise.all` 保持顺序，所以 `slice(-40)` 取的是最近 40 手，柱子从左到右由旧到新。

用 `kpi-after-6-hands.json` 的 6 手数据按原型算法复算（`t8-kpi.mjs`）：

| KPI | 复算 | 界面（证据） |
| --- | --- | --- |
| 已打手数 | 6 | 6 |
| 净盈亏 | −50 | −50 |
| 赢下的手牌 | 50% | 50% |
| VPIP | 33% | 33% |
| PFR | 17% | 17% |
| 摊牌胜率 | 0%（共 3 次） | 0%，共摊牌 3 次 |

柱高按时间顺序为 +50→63.3px、−60→76px、−40→50.7px、−20→25.3px、+10→12.7px、+10→12.7px，与 stats-6-hands.png、stats.png 一致。另外自造了 55 手数据，确认只画 40 根柱；空数据时各比例显示“—”、不画柱。

vpip/pfr 的来源也核对了：`record()` 统计玩家翻前除盲注以外的行动，跟注、加注、全下、下注都算 vpip，加注、全下算 pfr。大盲过牌（hands-dump id 4）不算 vpip，符合常规定义。

## 发现

### F1（小修）统计页连续加载时，晚到的旧结果可能覆盖新结果

`Stats.tsx` 的 `load` 每次触发都会发起一次完整的 `loadAll`，并直接 `setH`。如果 `hands:changed` 连续触发两次（例如清空记录后很快又结束一手），而第一次加载因为手数多反而更晚返回，页面会停在旧数据上，直到下一次变化才纠正。另外 `loadAll` 失败时 H 一直是 null，页面只剩空白，只有一条 toast。

建议：用一个递增序号只接受最后一次加载的结果（几行代码）。失败时显示空态或保留上一次的数据即可。回放页的 `hands.list` 只做一次查询，问题不大，不必改。

### F2（建议）列表里的手号跨桌重复，无法区分

`handNo` 是每张桌子内部的编号，重新入座后又从 1 开始。截图 replays-latest.png 中就有两条“#1”。原型只有一个会话，所以没有这个问题。task 规定的列表格式是“#手号 底牌 ±盈亏”，本任务没有做错。建议交给用户决定：是否在行内加上 `playedAt` 的短时间，或者按桌分组。这不影响本任务通过。

### F3（技术债，当前可接受）统计页逐手调用 `hands.get`

每次加载会发出 1 次 `hands.list` 加 N 次 `hands.get`，每次 `hands.get` 在主进程里执行两条查询（record 和 review）。本机探针用 libsql 文件库、每条记录约 2 KB，结果如下（不含 IPC 往返）：

| 手数 | 一次读出全部记录 | 逐手 2N 条查询（并发） |
| --- | --- | --- |
| 1,000 | 12 ms | 36 ms |
| 5,000 | 59 ms | 159 ms |

再加上 N 次 IPC 往返和结构化克隆，按每次约 0.1 ms 估算，5,000 手时总耗时约在半秒量级。它只在进入统计页和统计页打开期间每结束一手时发生。玩家每手都要自己行动，手牌增长很慢，所以在本期可以接受。代码里的 `ponytail:` 注释已经写明了上限和升级方向。

补充一个更省事的升级办法：`listHands()` 本来就会对每行 `JSON.parse(record)`，只要在 `HandSummary` 里加上 `vpip`、`pfr` 两个字段，统计页就能只调用 `hands.list`，N+1 查询随之消失，也不需要新增主进程聚合命令。这需要修改 T3 的共享类型，按约定要在 task 里记录，所以不在本任务内做。建议 T9 或之后遇到变慢时再处理。
