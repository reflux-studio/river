## 结论：需修改

前轮 9 条发现都有对应修订，其中 7 条已充分处理（F2、F3、F5、F6、F7、F8、F9）。F1 和 F4 的主干已经补上，但各留下一条契约没写清，见 N3 和 N4。

需要修改，是因为第 2 轮新加的机制之间有三处对不上。这三处都关系到用户明确提出的要求：拟人记忆、“限一层”、超时托管。

1. `activeTools` 按工具名做白名单。方案给闲聊模式列的是 `read_chat, say`，这样 Mastra 自动注入的 `updateWorkingMemory` 就被排除在外了。决策模式没有列出工具清单。结果是 agent 能不能写记忆，要由执行者去猜（N1）。
2. `depth` 规则本身前后不一致。闲聊中的发言既被列为触发源，又被定为 depth 1。决策时顺带说的回应是 depth 0，会再引出一层回应。赢家发言和托管台词的 depth 没有定义（N2）。
3. 熔断没有定义哪些失败计入。`toolChoice: 'required'` 在部分提供方那里会直接报错，可能一开桌就触发熔断（N3）。

```
主要场景与本轮发现的位置
 startHand ─► AI 行动 ───────────► 玩家回合 ─────────► 公屏发言 ─────────► 结束
              │ N1 决策可用工具     │ （教练：通过）      │ N2 depth 自洽     │ N2 赢家发言 depth
              │ N3 toolChoice/熔断  │                    │ N1 闲聊不能写记忆 │ N5 写 thread 在队列外
              │ N6 4 步预算         │                    │                   │
 失败场景：连续超时 → N3 计数口径 │ 闲聊中轮到行动 → N4 中止后未等待结束
```

## 新发现（按严重程度）

### N1【中高】`activeTools` 会把 working memory 工具排除在外：闲聊模式写不了记忆，决策模式的工具清单没写

证据：
- Mastra 按工具名过滤 `activeTools`：`core/dist/agent-DwtTO5Px.js` 第 161 行，`Object.entries(tools).filter(([name]) => activeTools.includes(name))`。
- working memory 工具由 `Memory.listTools()` 注入同一个工具表，名字是 `updateWorkingMemory`（`memory/dist/src-zTE4189S.js` 第 23316 行、第 32474–32481 行）。
- §5.2 第 137 行把闲聊模式写成 `activeTools: read_chat, say`。照这样实现，闲聊时 agent 看不到 `updateWorkingMemory`。
- §5.1 说“不同模式用 `activeTools` 限定可用工具”，但没有列出决策模式的清单。执行者如果只写表中的 6 个工具，决策时也没法写记忆。
- 决策模式同时开了 `toolChoice: 'required'`，并且在 `act` 调用后停止。即使 `updateWorkingMemory` 在白名单里，模型也只能在 `act` 之前的步骤里写，或者和 `act` 在同一步并行写。方案没有说明这个时机。

后果：用户要求“尽量拟人”，并列出三项记忆，其中“心情”“被抓过的诈唬”要靠 agent 自己写入 working memory（ADR-002 的理由也是这个）。闲聊恰恰是心情最该变化的场合（被调侃、赢牌后发言），按现在的写法却完全不能写。决策模式能不能写，要由执行者自己判断。

方案需要定下的契约：每种模式的完整工具白名单，包括是否包含 `updateWorkingMemory`。如果闲聊有意设为只读，需要写明理由，也要说明心情只在决策时更新是否仍符合用户意图。

### N2【中高】`depth` 规则前后不一致，“限一层”的实际层数取决于执行者怎么理解

证据：§5.2 第 136–139 行。
- 触发源写的是“玩家发言，或对手在决策/闲聊中说出的话”。紧接着一句又说“由回应产生的发言不再触发新回应（只有 depth 0 触发）”。闲聊本身就是回应（depth 1），所以“闲聊中说出的话”到底算不算触发源，两句话是矛盾的。
- 决策时“通过 `read_chat` 看到最近发言，可以顺带 `say`”，这句发言往往是在回应玩家，但按规则它是 depth 0，会再引出一轮抽样闲聊。实际链路是：玩家说话 → A 在决策时回应（depth 0）→ B 闲聊回应（depth 1）。对玩家的发言来说，这已经是两层回应。
- 有三类发言没有定义 depth：赢家在手牌结束时的发言、托管时的预设台词、熔断后的托管台词。如果托管台词算 depth 0，熔断后本地台词仍会引发 LLM 闲聊调用。
- 用户原话是“玩家和对手发言都可能引起回应，限一层”（§1 第 21 行）。

后果：两种实现都说得通。一种每个触发源只回一层，另一种会出现两层链路，而且托管台词也会触发调用。这会同时影响用户看到的公屏节奏和调用量（§10 第一条风险）。这是核心规则，不能留给执行者猜。

方案需要定下的内容：列出每一种发言来源的 depth，至少包括：玩家、决策中顺带发言、闲聊、赢家发言、托管预设台词。“决策中回应玩家的发言”算第几层，需要用户确认是否符合“限一层”。

### N3【中】熔断没有定义计入哪些失败；`toolChoice: 'required'` 在部分提供方可能导致一开桌就熔断

证据：
- §4 第 92 行只写了“连续失败 3 次”，没有说明以下几种情况是否计入：闲聊或赢家发言超时（8 秒）；因轮到行动而被主动中止的闲聊；决策中“未调用 `act`”或动作非法（这是模型能力问题，不是连通性问题）；教练的主动判断在玩家行动后返回而被丢弃。
- 熔断后，闲聊、赢家发言、`hand_history` 结果写入这些调用是否还继续发起，也没有写。§4 只说了“对手全部托管”。
- 已核实 `toolChoice` 在 1.69.0 中确实存在（`agent/agent.types.d.ts` 第 570 行，`reference-agents-generate.md` 第 175–183 行），并由 AI SDK 透传给提供方。有些 OpenAI 兼容接口或推理模型不支持 `tool_choice: "required"`，会直接报错。§6 的“测试连接”没说要测带 `required` 的工具调用。

后果：
- 如果中止或未调用 `act` 也计入，弱模型或话多的桌会很快触发熔断，整桌退回本地引擎。用户看到的是“模型连续失败”，可实际上网络是通的。
- 如果不计入闲聊失败，断网时闲聊调用仍会不断发出，每次都要等满 8 秒。
- 用户如果选了不支持 `required` 的提供方，每次决策都会报错，第一圈就熔断。

方案需要定下的内容：计入熔断的失败类型；熔断后停止哪些调用；“测试连接”要验证什么（至少包括一次 `toolChoice: 'required'` 的工具调用），以及不支持 `required` 时怎么处理。

### N4【中】“立即中止闲聊再发起决策”没有要求等被中止的调用结束，working memory 仍可能丢更新

证据：
- §4.1 第 97 行写的是：闲聊还在进行时轮到该对手行动，就“立即中止该闲聊（`abortSignal`），再发起决策”。
- `abortSignal` 只能阻止后续的步骤，不能撤回已经开始执行的 `updateWorkingMemory`。前轮核实过，这个工具在 `execute` 里直接写 storage，而 Markdown 模板是整份替换。
- 如果中止后马上发起决策，决策开始时读到的是旧的 working memory，闲聊晚到的写入随后覆盖上去；也可能反过来，决策的写入被闲聊覆盖。这正是串行队列要防止的读-改-写竞争。§9 第 192 行把“working memory 不被覆盖”列为验证项，但方案正文没有给出能让这项验证通过的规则。
- 教练的“提问中止主动判断”（第 98 行）也有同样的问题。

后果：竞态窗口很小，但会触发的情形恰好是本轮要修的 F1 场景。

方案需要补一句契约：中止后，要等被中止的调用真正结束（promise 完成）再发起下一个调用。如果选择不等待，就要说明为什么这样也不会丢更新。另外还要说明被中止的调用算不算熔断里的失败（与 N3 相关）。

### N5【低】手牌结束写 thread 在串行队列之外，消息顺序可能交错

证据：
- §5.2 第 130 行规定“直接写 memory，不调用 LLM”。已核实 `Memory.saveMessages({ messages: MastraDBMessage[] })` 存在（`memory/dist/index.d.ts` 第 231 行；`docs-memory-message-history.md` 第 118 行）。这个 API 可以用。
- `@mastra/libsql` 的 `saveMessages` 不检查 thread 是否存在（`libsql/dist/index.js` 第 8289 行起，直接 INSERT，再 UPDATE thread）。每条消息必须带 `threadId` 和 `resourceId`，否则会抛错。
- 这次写入不在 §4.1 的队列里。如果写入时该对手正有闲聊调用在进行（比如赢家发言），那次调用的消息要到调用结束时才保存（默认 `savePerStep: false`），thread 里的顺序就会变成“闲聊输入 → 本手结果 → 闲聊输出”。这不影响 working memory，只影响消息历史的可读性。
- 赢家发言的输入里已经带了本手结果，thread 里又写了一次，内容重复。

后果：不影响正确性。建议写明这次写入走不走队列，以及第一手前 thread 不存在时是否要先 `createThread`。

### N6【低】决策模式最多 4 步，工具有 7 个（含记忆），加上 `toolChoice: 'required'` 后预算偏紧

证据：§4 第 89 行规定 `maxSteps` 为 4。已核实 `maxSteps` 与自定义 `stopWhen` 会同时生效（`agent-DwtTO5Px.js` 第 29861–29864 行：`[stepCountIs(maxSteps), ...userConditions]`），这一点方案写得对。可是决策时可用的工具有：`view_table`、`estimate_equity`、`read_chat`、`hand_history`、`say`、`updateWorkingMemory`、`act`。模型如果每步只调一个工具，第 4 步之前还没调 `act` 就会被托管。

后果：托管率上升。叠加 N3 后，可能触发熔断。这属于实施时的调参问题，不阻塞，建议在首个验证任务里观察。

### N7【低】其他未定细节

- 同一次调用里出现多个 `hint`、`pause_game` 或 `say` 时，取第一个、全部还是最后一个（§4.1 只规定了 `act`）。
- 赢家发言是否受 10 秒冷却限制；失败时是静默还是改用预设台词。
- “教学牌局要求至少 hint”仍然只靠提示词。§5.1 的 `toolChoice: 'required'` 只用于决策模式，所以和“教练不调工具即静默”不冲突。但如果执行者想给教学局也用 `required` 来保证至少一次 hint，就会和“静默”规则冲突，而且没有终止工具，会一直调用到 `maxSteps`。建议写明教练的主动判断使用 `toolChoice: 'auto'`。
- `hand_history(n)` 取哪些手：该角色参与过的全部牌桌，还是仅本桌。

## 已核实、成立的部分

- `activeTools` 和 `toolChoice` 是 1.69.0 `generate`/`stream` 的真实选项：`agent/agent.types.d.ts` 第 546、570 行；`reference-agents-generate.md` 第 87、175–183 行。`toolChoice` 可以取 `'auto' | 'none' | 'required' | { type: 'tool', toolName }`。
- `maxSteps` 与 `stopWhen` 可以同时使用，其中任一条件满足就停止（见 N6 的依据）。
- 可以直接向 thread 写消息：`Memory.saveMessages`（见 N5 的依据）。
- `toolChoice: 'required'` 与“教练不调工具即静默”不冲突，前提是 `required` 只用于对手决策模式（§5.1 原文就是这样写的）。
- 意图收集器加上返回后校验（§4.1）解决了前轮 F2 的问题：即使工具并行执行（默认 `toolCallConcurrency` 为 10），也不会直接改动牌局。
- 串行队列的前提（进程内、单一 TableRunner）与已接受的 ADR-001 一致。§9 第 194 行也写明了改用子进程时要重新核对这个前提。
- 主要场景里教练这一段是自洽的：主动判断和提问互斥，复盘排队，晚到的 `pause` 靠 `heroKey` 丢弃。

## 证据限制

- 所有 Mastra 结论都来自阅读文档、类型和 dist 源码，没有实际运行。N4 的竞态是从“中止不撤回正在执行的工具”推出来的，没有核实 Mastra 中止时会不会等待正在执行的工具，也没有复现。
- 哪些提供方不支持 `tool_choice: "required"`，没有逐一核实。N3 的判断依据是这些接口普遍存在的差异，需要在首个验证任务里用用户实际配置的提供方测一次。
- 仍然没有读到 `poker.js` 原文，所以引擎规则、托管台词的原型行为，都是依据设计稿里的调用和 note 来判断的。
- 调用量只做了定性判断（N2 会影响层数），没有按健谈度初值做定量估算。
