| 场景 | 操作 | 结果 |

修复成立的原因：每个写函数都在同一个同步段内更新缓存并把写操作排进链（`setKv` 虽然是 async，但它在第一个 `await` 之前就同步调用了 `write()`），所以写链的顺序和缓存的更新顺序一致。settings 与 lobby 每次写的都是完整快照，库中最后的状态等于缓存中最后的状态。

## 新写链检查

| 项 | 核对 | 判断 |
| --- | --- | --- |
| 错误传播 | `write()` 把原始 Promise 返回给调用方（调用方能拿到拒绝），链本身接的是 `p.catch(() => {})`，一次失败不会阻塞后续写。探针：删掉 `river_kv` 后 `updateSettings` 被拒绝，之后 `updateLobby` 正常写入 | 正确。与 `@mastra/libsql` 的 `withClientWriteLock` 是同一个模式 |
| `initDb` 重置 | `writeChain = Promise.resolve()`。探针：有写入挂起时 `closeDb`，挂起的写因为捕获的是旧 client 而得到 `CLIENT_CLOSED` 拒绝；重新 `initDb` 后新写不会排在旧链后面 | 正确。迁移不经过写链，这没问题：此时还不会有其他写 |
| `write()` 在调用时捕获 client | `const c = db()` 同步取值，未初始化时会同步抛出；它发生在 async 函数里，调用方收到的是拒绝 | 正确。副作用：未初始化时调用 `updateSettings`，缓存会先被改掉（探针：speed 1→42）。这只可能是编程错误，T5 在启动时先 `initDb`，不需要处理 |
| `getLobby` 改为同步 | task/plan 只有 `app.bootstrap` 汇总 lobby、`lobby.update` 返回 Lobby，没有规定 get 必须是 Promise；`await` 同步值照样可用（旧测试第 59 行仍然通过）；`ipcMain.handle` 也接受同步返回 | 不破坏契约。与 `getSettings` 一致 |
| 直接查库的读函数不经过写链 | `getBankroll`、`listHands` 等在写入还没落库时可能读到旧值。调用方 `await` 了写再读就不受影响 | 可以接受。唯一需要注意的是 T5 结算余额（`setBankroll(await getBankroll() + net)`）必须保证同一时刻只有一次结算，按一手一结算的流程本来就是这样。记给 T5 |
| 复用的缓存对象可以原地修改 | `getSettings`/`getLobby` 返回缓存本身 | 与前轮相同，风险低，不单列 |

## 写失败后缓存与库不一致：现在是否要处理

现状：先改缓存再写库，写库失败时缓存领先于库。

| 数据 | 失败后的表现 |
| --- | --- |
| settings、lobby | 下一次任何成功的更新都会把完整快照写进去，失败的补丁会一起落库（探针：`speed:7` 写入失败，随后 `hard:true` 写入成功，重开后是 `speed 7, hard true`）。如果之后没有写入就退出，这次改动在重启后丢失 |
| providers | `saveProvider` 失败后，缓存里多出一个库中没有的提供方（或者是修改后的版本），本次运行中 `listProviders`/`resolveModel` 都能用到它，重启后消失；`deleteProvider` 失败则相反 |
| 其余 | 没有缓存，不会不一致 |

失败来源比前轮估计的更现实（R1）：`@mastra/libsql` 与业务表共用一个文件，它在 `deleteMessages`、`updateThreadResourceId`、观察记忆、工作流状态等约 25 处路径上使用交互式 `transaction('write')`，事务跨越多个 `await` 一直持有写锁。探针：外部连接开着写事务时，`updateSettings` 在 **0 ms 内**被拒绝，错误为 `SQLITE_BUSY`（我们的 client 没有设置 `timeout`）。另外实测，即使设置 `createClient({timeout})` 也没用：libsql 在主线程里同步等待忙锁，同一进程里持锁的事务在等待期间无法推进，结果是主线程卡住整个 timeout 时长，然后照样 `SQLITE_BUSY`。

判断：**不需要在 T3 处理**。理由：调用方能收到拒绝；settings/lobby 会自愈；提供方的幽灵状态只到重启为止；是否回滚要看 T5 的 IPC 错误如何呈现。不过 T5 需要做出明确选择，不能默认忽略。最省事的办法是在 `write()` 失败时从库重新加载该项缓存（或者直接重建全部缓存），这样可以放进 T3 的 `write()`，所有写路径一次覆盖。另一个方向是让 Mastra 用独立的文件，从根上消除跨库锁竞争，但这会改变 plan 中“同一文件”的约定，需要重新决策。
