## 判断

### 需求与契约

| T1 要求 | 实现与断言 | 能否区分通过和失败 |
| --- | --- | --- |
| 主进程 ESM 加载 Mastra | `"type":"module"`，main 输出 ESM，`import.meta.dirname` | 加载失败时 import 就会抛错，应用无法启动（hoisted 布局下已经出现过这种失败，commands.md 有记录） |
| LibSQLStore + 带 Memory（resource 作用域 working memory）的 Agent | spike.ts 69–96 | `workingMemoryWritten`：用 `memory.getWorkingMemory` 读回 `spike ok`，读不回就失败 |
| model 为函数，按 RequestContext 解析 | 90–93，`resolvedFor` | `modelFnGotRequestContext` 比较 `modelId==='spike'` |
| createTool 工具被执行 | `record`，`recorded` | `toolExecuted` 比较 `note==='hello'` |
| activeTools 含 `updateWorkingMemory` | 106 | 工具被过滤掉时 working memory 不会被写入，间接覆盖 |
| stopWhen 自定义条件 | 107–108；mock 首步调用工具，之后只回文本 | `model.calls===1`：如果 stopWhen 没生效，maxSteps=5 会让模型被调用第 2 次，检查失败 |
| abortSignal | 首次调用传入未触发的 signal；另外用已中止的 signal 调一次 | `abortedFinishReason==='aborted'`；如果抛错会进入 catch 并写入 `error`，pass=false |
| `updateWorkingMemory` 工具名 | `agent.getMemory().listTools()` | `includes('updateWorkingMemory')` |
| `mastra_` 表在 river.db | 用 `@libsql/client` 查 sqlite_master | `tables.length>0`，实测 44 张，其中有 `mastra_resources`、`mastra_threads` |
| PROVIDER_REGISTRY 可读 | `@mastra/core/llm` | 数量大于 0，实测 208 |
| safeStorage 覆盖安装后解密 | `spike-key.bin`：不存在就加密写入，存在就解密比对 | 按时间线，0.1.0 打包版（17:25:42Z）是 encrypt 模式，说明当时 userData 是干净的；0.1.1 覆盖安装后（17:26:23Z）是 decrypt 模式且 ok=true。这就是“同一份密文跨版本覆盖安装后能还原” |
| dmg arm64、asarUnpack、不签名 | electron-builder.yml：dmg/arm64、`identity: null`、asarUnpack 包含 `@libsql/**` 和 `libsql/**`、`npmRebuild: false` | `app.asar.unpacked/node_modules/@libsql/darwin-arm64/index.node` 在 dist 和已安装的 app 中都存在；codesign 显示 adhoc（linker-signed），不是正式签名 |
| poker.js 写入 design-source | 文件存在（11813 字节） | 没有再次向设计项目核对原文（见 E3） |

另外还满足了：被中止的 `generate` 不抛错（`note.md` 待核实项）；Electron 44 内置的 Node 满足 `AbortSignal.any` 的要求。

### 工程质量

- 配置合理。`contextIsolation: true`、`nodeIntegration: false`；没有显式写 `sandbox`，但 Electron ≥20 默认开启沙箱，preload 输出 `.cjs` 正是为了兼容沙箱（electron.vite.config.ts 的注释说明了原因）。renderer 有严格的 CSP。tsconfig 分为 node 和 web 两份，target 为 ES2022，strict。
- 与简报不一致之处的论证：用 hoisted 时，electron-builder 26 按 `pnpm list` 输出的虚拟仓库路径收集依赖，把 `@ai-sdk/provider` 装错了版本，commands.md 记录了可复现的报错。我核对了打包日志中 `@ai-sdk/provider-v6` 的告警：在 `node_modules/.pnpm` 的所有运行时 js/mjs/cjs 中搜索该别名的 import，结果为 0，与执行者的说法一致。
- 没有超出范围：没有 IPC、业务表或 UI，renderer 只是一个空的 `<div/>`。
- 安全：API key 相关代码尚未出现；spike 用的是固定测试串。见下方发现 Q1、Q2。

### 验收证据

- 开发运行（dev-spike.log）、打包 0.1.0、覆盖安装 0.1.1 三份 JSON 都是 pass，每份都带 `at` 时间戳和 `version`/`packaged` 字段，可以排除误读旧文件。
- 需要说明两点：一是“安装”方式是挂载 dmg 后用 `ditto` 复制到 `~/Applications/River-spike/`，没有装到 `/Applications`，也没有经过 Finder 拖拽或 Gatekeeper 隔离属性，不过对 safeStorage 和 asar 路径的验证没有影响。二是开发环境和打包产物共用同一个 userData，开发运行晚于打包运行，所以没有污染打包验证。
