## 结论：通过

我逐函数对照了移植版和原型，算法、常量、中文文案都一致；原型里 4 处 `Math.random`（`shuffle`、`newGame` 选庄、`equity`、`decide` 的 `r`）全部改为可注入的 rng。对照测试让两边使用同一个种子和同样的调用顺序，逐步比较结果。我另外做了 9 个变异，其中 5 个导致测试失败；没被发现的 4 个里，有 2 个是等价变异或碰不到的分支，剩下 2 个改的是没被比较的字段（`p.last`、`startStack`，见 T1）。验收项全部有对应测试。以下发现都不阻塞，但 A1（类型重复）需要在 T2、T3 合并时处理。

## 判断

### 逐函数对照

| 函数 | 与原型的差异 | 判断 |
| --- | --- | --- |
| 常量 `R/FULL/SYM/CAT`、`rv`、`combos`、`eval5`、`best`、`catOf`、`handName`、`looseCat`、`outs`、`disp`、`txt`、`fmt`、`pot`、`canAct`、`inHand`、`nextIdx`、`put` | 只增加了类型标注；`eval5` 里写成 `cnt[+k]`，与原型 `cnt[k]` 等价 | 一致 |
| `shuffle` | 多一个 `rng` 参数 | 一致（注入点 1） |
| `equity` | 第 5 个参数 `rng = Math.random`；洗牌方式（部分 Fisher–Yates，只洗前 `need` 张）、`iters` 默认 300、平局按 `1/(1+ties)` 计，都与原型相同 | 一致（注入点 3） |
| `newGame` | 增加 `rng` 参数，选庄用 `rng()`；补了 `sbI/bbI/deck/toAct/currentBet/minRaise/winners/showdown/runout` 的初值，玩家默认值里加了 `startStack`；`rng` 存进 `g.rng` | 选庄一致（注入点 2）。初值都会被 `startHand` 覆盖，不影响行为 |
| `startHand` | `shuffle(FULL.slice(), g.rng)` | 一致 |
| `legal`、`apply`、`dealStreet`、`progress`、`runoutStep`、`showdown` | `apply` 里写成 `g.street as Street`；其余只加了非空断言 `!` | 一致；文案“弃牌/过牌/跟注 x/加注至 x/下注 x/全下 x/小盲/大盲”逐字相同 |
| `decide` | `rng = g.rng`，同时用于 `equity(..., 160, rng)` 和 `r = rng()`；系数 0.4/0.55/0.22/0.3/0.5/0.7/1.6/0.85/1.05/0.45/0.07/0.8 都相同 | 一致（注入点 4）。默认用 `g.rng` 而不是 `Math.random`，与原型“整局共用一个随机流”的消耗顺序一致，这正是对照测试能逐步对齐的前提 |
| 导出 | 原型的 15 个导出，加上 `progress/dealStreet/showdown/best`，都已导出 | 符合 T2“输入输出” |

`Player/Game/LogEntry/Legal/Action/Profile` 的字段与 T2 表格一致。`Game` 多了 `rng`，`street` 多了 `'idle'`（原型 `newGame` 就是这样设的），另外新增了 `Winner/SeatConfig/GameConfig`。

### 对照测试是否真能发现偏差

- **同一随机序列**：原型在 `vm.createContext` 里加载，`Math.random = rng` 替换的是这个上下文自己的 `Math`，不会影响宿主；两边各用一个同种子的 `mulberry32(seed)` 实例。原型里所有消耗随机数的地方（newGame、startHand、decide→equity、decide 的 `r`）在移植版中调用顺序相同。测试脚本自己的随机数来自另一个独立的 `script` 流，不会打乱这两条序列。我把 `decide` 的 `r` 改回 `Math.random()` 做了变异验证：有 2 个测试失败，说明两边的序列确实是逐步对齐的，并非碰巧相等。
- **比较是否充分**：开手时比较底牌和 dealer/sbI/bbI/toAct；每一步比较 toAct、legal、decide、apply 标签、board、log，以及每位玩家的 outs/handName/disp；手结束时比较 winners、showdown 和全部筹码。30% 的随机动作会走到纠正路径和任意 `to`。执行者统计：94 手摊牌，其中 50 手有边池，72 手出现全下。覆盖面足够。
- **没有比较的内容**：玩家的 `last`、`startStack`、`acted`、`contrib`、`handName/score`，以及 `g.minRaise/currentBet/runout`。其中大部分会通过 legal/log/winners 间接暴露出来，但 `last` 和 `startStack` 不会（见 T1）。

### 独立变异检查（在 scratchpad 副本上进行，未改动仓库）

| 变异 | 结果 |
| --- | --- |
| `decide` 虚张系数 0.07→0.08 | 被发现 |
| `equity` 公共牌切片错一位 | 被发现 |
| 皇家同花顺判定 14→13 | 被发现 |
| `decide` 改用 `Math.random()` | 被发现（2 个测试） |
| `outs` 去掉 `nc > looseCat(nb)` | 被发现 |
| 加注后不清其他人的 `acted` | 没被发现；这是等价变异：其他在手玩家此时 `bet < currentBet`，`progress` 仍会轮到他们 |
| 删除 `elig` 兜底 | 没被发现；这个分支要求“弃牌者投入多于所有在手者”，正常下注流程中基本到不了 |
| 去掉 `progress` 中换街时清 `p.last` | **没被发现**（T1） |
| 不在 `startHand` 更新 `startStack` | **没被发现**（T1） |

加上执行者报告的 4 个变异，结论是：核心算法和常量有测试保护，只有展示用的玩家字段没有。

### 工程质量

- 注释只有两条：文件头说明“须与原型保持一致”，`newGame` 说明为什么要补初值。两条都是在讲“为什么”，符合规则。
- 没有多余的抽象。`Winner/SeatConfig/GameConfig` 是签名本身需要的类型。
- `LogEntry.street` 用 `as Street`：只有在 `startHand` 之前调用 `apply` 时才会写入 `'idle'`，这属于调用方误用，TableRunner 不会这样调用。可以接受。
- 对照测试的超时设为 120s，实际耗时约 12s。偏宽，不影响结果。
