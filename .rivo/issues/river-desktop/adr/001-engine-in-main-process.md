# 001：牌局引擎与唯一状态放在 Electron 主进程

状态：接受（用户于 2026-09-23 确认）
日期与依据：2026-09-23；用户决定采用 Electron，并要求对手与教练是带独立 tool call 的智能体。

## 背景与问题

原型把牌局状态放在前端组件里，LLM 调用时把局面拼成文本快照发出去。改为 agent 后，对手和教练要通过工具主动读取局面、计算胜率、提交行动，工具执行在 Mastra 所在的 Node 环境。需要决定牌局状态放在哪里、谁能修改。

## 可行选项

| 选项 | 行为 | 代价 |
| --- | --- | --- |
| A. Renderer 持有状态，工具通过 IPC 回查 | 每次工具调用都要跨进程查询渲染层 | 状态在 UI 进程，工具与 UI 双向耦合；渲染层刷新或卸载即丢局 |
| B. 主进程持有状态（TableRunner 唯一写入） | 工具在同进程直接读引擎；Renderer 只收裁剪后的视图并发命令 | 需要设计 IPC 命令与视图推送 |
| C. 每次调用前把完整快照塞进 requestContext | 工具读 context | 快照随行动过期；`act` 仍需回写到某处 |

## 决定与理由

推荐 B。工具、超时托管、暂停挂起都需要一个可靠的状态拥有者；主进程与 Mastra 同处一个 Node 运行时，信息隔离也可以在工具层用代码保证（按 `requestContext` 中的座位裁剪）。Renderer 收到的视图同样经过裁剪，未摊牌的对手底牌不会到达 UI 进程。

## 后果与重新考虑条件

收益：单一写入者，状态一致；工具实现简单；信息隔离可测试。
代价：多一层 IPC 契约；UI 响应依赖主进程推送。
重新考虑：若 Mastra 在 Electron 主进程无法稳定运行（首个验证任务），改为独立 Node 子进程承载 TableRunner 与 Mastra，本决定的职责划分不变。
