# 方案审阅 design-1：统一牌桌 Agent 与本地数值

- 对象：`.rivo/issues/unified-agent/discussion.md`（2026-09-25 版，首轮），以及工作区未提交改动（位置修复、教练讲解重试、过渡用的教练 history）
- 基线：`main` @ 3ba346c + 未提交 diff
- 结论：**需修改**。方向承接用户原话，偏离 ADR-004 的地方已讲明并计划写 ADR-006；但 thread 的核心契约（异步赛后发言与新一手压缩的先后、失败调用是否入 thread、行动消息怎么表示）没写清，前缀缓存这条理由的几个前提在现有代码里也不成立。「改进牌」的新口径照字面实现会出错。

## 发现

### F1【阻塞】异步赛后发言与「新一手开始时压缩」的先后没有约定

依据：自由局由玩家点「下一手」触发 `nextHand()`（ipc `table.nextHand`），不会等赛后发言。方案有三条规则：一手结束时对手 thread 追加「公开结果 → 赛后发言」；新一手开始时压缩上一手，压缩内容包含「自己的想法与发言」；该对手行动时若发言仍未返回，就中止并丢弃。

反例：第 N 手结束，对手 X 的发言调用已发出。玩家 1 秒后点下一手，代码压缩第 N 手。3 秒后 X 的发言返回，此时 X 还没轮到行动。这条发言要么追加到「第 N 手摘要」之后、第 N+1 手消息之前（这违反「只追加」），要么追加到末尾而与时间线错位，要么被丢掉。方案对这三种都没有选。另外「压缩内容含发言」与「发言可能在压缩之后才到」本身互相矛盾。

后果：执行者只能自己选一种顺序，而这正是 thread 只追加、缓存和测试所依赖的核心契约。

需要写明：压缩发生在什么时点（新一手开始时，还是该 Agent 下一次调用前），以及压缩之后才返回的发言怎么处理（丢弃，还是只上公屏、不进 thread）。

### F2【重要】失败、中止、跳过、丢弃的调用是否入 thread，以及消息角色交替规则，都没有定义

现有行为：
- 对手 `act` 失败时牌局停下，`retry()` 会重算局面再调用（runner.ts 279–307）。
- 讲解可以被「不等了」中止，只流出一部分文字；失败后可以重试（357–379、419–427）。
- 赛后发言可以被丢弃，方案也允许它为空。

方案只写了成功路径的 user → assistant。它没有说明以下几点：
- user 消息是先追加，还是等成功后与 assistant 一起追加。如果先追加，重试时同一轮会出现两条 user。
- 被丢弃的赛后发言，其「公开结果」user 消息还保不保留。
- 空发言要不要生成一条空的 assistant 消息。有的 OpenAI 兼容端点会拒绝空 content；如果 Mastra 丢掉空消息，又会出现连续两条 user。
- 往手压缩后以什么角色、放在哪里：一条独立的 user，还是并进本手第一条 user？独立的 user 后面紧跟本手的局面，也会形成连续两条 user。
- 被中止讲解已经流出的部分文字，要不要进 thread。用户看到了这段话，追问时教练却不知道自己说过。

证据限制：DeepSeek 当前各模型是否接受连续同角色消息，本轮没有实测。早期 deepseek-reasoner 曾拒绝这种消息。
后果：不定义清楚的话，重试和丢弃路径可能产生 400 错误，或留下重复的上下文。验证清单里也缺这些路径的测试。

### F3【重要】「system 固定、只追加，所以前缀缓存命中率最高」这条理由有四处与现状冲突

1. 长期印象在 system 里：`memoryOf(pid)` 每次调用都读（runner.ts 267），而一手结束时 `addMemory` 会写入新的 note（541）。所以只要本手有人记了 note，下一手的 system 就变了。教练也一样：复盘的 note 会写进 `hero` 档案（470）。方案没说入座时对 memory 做快照。
2. 教练的 system 按用途变化：`system(extra, memory)` 中 extra 在讲解（又分引导、非引导）、问答、复盘三种场景下各不相同（coach.ts）。这些场景说明要搬到 user 消息里，system 才能固定，方案没提。
3. 工具集按调用变化：`callModel` 只在传入 `tool` 时注册工具（llm.ts 63–75）。复盘带 recap 工具、讲解不带；对手的 act 带工具、赛后发言大概率不带。工具定义通常排在消息前面（证据限制：DeepSeek 服务端的拼接顺序没有查到公开说明）。如果工具集不同，前缀在最前面就断了。
4. 滑动窗口约 5 手：每手丢掉最早一手，整个前缀在每手的第一次调用都会失效。所以缓存只在同一手内才能命中。

后果：3、4 两点不影响功能，但方案拿缓存作为「system 不放局面」的主要理由，成本也会因此比预期高：每次调用都带着约 5 手摘要加本手全部局面，未缓存部分可能是现在单次调用的几倍。

建议：验证清单加一项，实机检查 `river_usage.cached`（这一列已存在）。

### F4【重要】act 结果写回 thread 时怎么表示，没有定

`Msg` 只有字符串 content（llm.ts 29–32）。`maxSteps: 1` 时，act 的结果是一次工具调用，不是正文。如果写成 assistant 工具调用消息，OpenAI 协议要求后面紧跟一条 tool 结果消息，现有接口不支持。实际上只能由代码把 think、行动、say 拼成文本。

另有一个风险：`supportsRequired=false` 的提供方会用 `toolChoice: 'auto'`（llm.ts 86）。当历史里全是纯文本的 assistant 行动时，模型更容易模仿历史、直接回文字而不调用工具。现有代码把这种情况判为「模型没有调用 act」，牌局会停下（runner.ts 282）。

需要写明表示格式，并把 auto 退路下的行为列入验证。另外 think 应放在 schema 的第一个字段，模型才会先想后出行动，这是实施细节。

### F5【重要】「改进牌」的新口径照字面实现会算错

方案原文：「下一张牌能让『我的牌型』超过『公共牌自身牌型』的牌数」。

反例：手牌 7♠7♦，翻牌 K♣9♥2♠。我已经是一对，公共牌是高牌。按字面，任意一张空白牌之后「我的牌型 > 公共牌牌型」都成立，结果约为 47 张。

现有 `outs()`（eval.ts 83–92）同时要求 `nc > cur`（大类升级）和 `nc > looseCat(nb)`（超过公共牌）。所以新口径要么与现有实现等价（隐含「升级」条件），要么丢了这个条件而出错。方案没有说清它相对现状改了什么，也没说明原来「不准」的具体表现，比如四张同花的公共牌加一张单花补成同花、中对听暗三这类情况。

后果：执行者无法判断要改什么；验证清单里的「新的出路口径」测试也没有判定标准。

### F6【建议】胜率「误差 ±1%」口径未定，主进程阻塞需列入实测

本地实测（Apple Silicon，`equity(['As','Kd'], …, 10000)`）：1 个对手 231 ms，3 个 315 ms，5 个 387 ms，翻牌后 3 个对手 284 ms。

- 按 95% 置信 ±1% 计算，最坏情况（p≈0.5）约需 9600 次，也就是每次轮到玩家时同步阻塞主进程 0.3–0.4 秒，较慢的机器会接近 1 秒。
- 按 1σ ±1% 计算，只需约 2500 次（约 80 ms）。

方案写了「实测性能后定」，但没有说用哪种误差口径，也没有定可接受的阻塞上限，以及超出后怎么处理（降次数、分片让出事件循环，或放进 worker）。

### F7【建议】赛后发言的若干细节待定（不改变结构）

- 「入过池」的定义没给：大盲只过牌算不算？翻牌前主动投入后又弃牌的算不算？现有 `vpip` 只统计玩家，而且只看翻牌前。
- 快节奏下丢弃会很频繁：翻牌前靠前位置的对手在新一手的几秒内就要行动，赛后发言大多会被丢弃，实机可能「看不到发言」。建议在实机验证里观察丢弃比例。
- 用量统计：赛后发言用哪个 `purpose` 没写。`Purpose` 是闭合联合类型，`Stats.tsx` 的 `PURPOSE` 是 `Record<Purpose, …>`，`prices.ts` 按 `PURPOSES` 逐项统计。新增 purpose 需要同时改这三处；如果沿用 `decide`，「AI 决策」一项就会混进闲聊。
- 赛后发言是纯文本还是工具调用，能不能附带 note，「为空」由模型怎么表达：都没写。
- 并发：一手结束时最多 5 个对手同时发起调用，还会与下一手的决策调用叠加。对有速率限制的提供方，可能触发 429 并消耗重试次数。

### F8【建议】「他人底牌」的措辞需要与摊牌公开牌区分

`publicHandResult` 会给出摊牌时亮出的牌，这是公开信息，应当进入对手 thread。方案原话「对手 thread 里绝不能出现别人的底牌，包括教练局一手结束时亮出的底牌」，而 `heroHandSummary` 也把 `holeAfter` 叫作「一手结束亮出的底牌」，执行者容易把摊牌牌也过滤掉。

建议改成：「不得出现未摊牌者的底牌（含 `holeAfter`）；摊牌亮出的照常」。

另外，对手在赛后发言里如实报出自己底牌，这是允许的（发言可真可假），它经公屏进入他人 thread 不算违反隔离。可以写一句说明，以免测试把这种情况误判为泄露。

### F9【建议】删掉「跟注 ±EV」文字后，进度条仍在比较这两个数

`ProbPanel` 有两处比较胜率与所需胜率：进度条 `width = eq`，以及 `need` 的刻度线（CoachPanel.tsx 31–33）；标题「胜率 vs 所需胜率」和颜色 `good = eq >= need` 也在比较（19、24）。方案认为这两个数口径不一致，因此删掉 ±EV 文字；但只删文字的话，进度条和颜色表达的仍是同一个结论。需要一起定下是否保留这种对比。

另外，「所需胜率照常写进提示词」没说清对手是否也拿到这个数。现在只有教练的 `heroSituation` 里有它，对手的局面里只有底池和需跟注。

### F10【建议】影响面与验证缺项

- `AgentDeps` 的签名会变（对手需要带 thread，赛后发言是新入口），runner.test.ts 中约 10 处替身要改写。影响面没有列 `test/`。
- 回放页复盘：`coachRecap` 如果改为读 thread，回放路径要保留无 thread 的签名；复盘提示词中「结合对手倾向」一句在回放场景下没有依据。方案说回放页仍按单手摘要调用，这是对的，还要写明提示词在两条路径上如何区分。
- `.rivo/knowledge/README.md` 描述的仍是 v1（working memory、AgentQueue、`leak.ts` 等），已与代码不符。本次写 ADR-006 时建议顺带标注这份文档已过时，否则会误导后续执行者。
- 离桌：内存 thread 在 `resetTable` 中清空。赛后发言的回调除了检查 `runId`，还要用每个座位自己的 AbortController，才能在轮到该对手时单独中止。方案的规则成立，这里只提醒验证清单加上「离桌时赛后发言返回，不写入新桌」一项。

## 已核对、没有问题的部分

- ADR-004：存储决定不变。「对手不带会话历史」由 ADR-006 修订，方案已讲明；`Agent.generate/stream` 接受消息数组，ADR-004 已核实（@mastra/core 1.69.0）。
- 信息隔离主路径：`situation()` 只放该座位自己的底牌；`publicHandResult` 不读 `holeAfter`。对手 thread 只由这两处加公屏组成，加上 F8 的措辞修正后可以成立。
- 教练的问答、讲解、复盘由 `coachBusy` 互斥；提问会暂停牌局；教练局复盘阻塞「下一手」而对手发言不阻塞，两者作用在不同的 Agent 和 thread 上，没有交叉。
- 已有改动：`positions()` 的位置命名在 2–6 人桌上正确；讲解重试只在同一决策点可用，与 `speakRetryKey` 一致。

## 证据限制

- DeepSeek 的前缀缓存细节（工具定义在前缀中的位置、Mastra 是否在 system 注入可变内容）和连续同角色消息的兼容性都没有实测，只按代码和常见协议推断。
- 胜率耗时只在本机测了一次，没有覆盖较慢的 Windows 机器。
- 没有运行实机牌局，也没有跑测试套件。
