## 本轮核对

### 并发与触发点（F1 修订是否成立）

- **对手**：同一对手在本桌的调用只有两种，决策（act）和赛后发言（talk）。
  - 决策由 `loop()` 串行驱动，同一对手不会有两个决策同时进行。
  - 赛后发言与该对手下一次决策之间，由「第一次调用时先中止发言」隔开。所以同一条 thread 不会被并发写入。
  - 前提是中止后返回的那个结果，必须按「代际或手号已变」丢弃。这与现有 `rid` 检查的写法同类，属于实施细节。
- **教练**：讲解、问答、复盘由 `coachBusy` 互斥（`ask` 和 `retryCoach` 在 busy 时直接返回；讲解只在 `coachBusy === null` 时触发；复盘在提问结束后才补跑）。教练没有异步的 talk。所以教练 thread 也是串行写入。
- **教练的惰性压缩触发点**：
  - 新一手里第一次讲解（玩家第一次决策时），或更早的一次提问，触发压缩。
  - 两手之间（复盘完成后、点下一手前）的提问，`t.handNumber()` 仍是上一手，不会触发压缩，归属也正确。
  - 复盘失败或跳过后可以直接进入下一手；这时复盘没有写入 thread，也不会补跑（`resetHand` 会把 recap 置为 none）。前后一致。
- **离桌**：thread 清空，在途调用由 `leaveCtrl` 中止并按 `rid` 丢弃，没有变化。

### F5 改进牌场景核对（按 `eval.ts` 的 `looseCat`：少于 5 张时只看点数重复，5 张及以上按完整牌型评估）

| 场景 | 结果 | 评价 |
|---|---|---|
| 同花听牌：A♥5♥ / K♥9♥2♠ | 9 张红桃（rel 0→5），A、5 共 6 张（0→1），合计 15 张 | 合理 |
| 两头顺听牌：8♠7♦ / 6♣5♥K♠ | 9、4 共 8 张（0→4），8、7 共 6 张（0→1） | 合理 |
| 转牌上公共牌三张同花、自己一张同花：A♥5♦ / K♥9♥2♠7♥ | 河牌红桃：公共牌只有 4 张红桃，仍是高牌，我成同花，0→5，算 | 合理 |
| 公共牌已有四张同花、自己没有该花色：2♣3♦ / K♥9♥5♥7♥ | 河牌红桃让公共牌自己成同花，rel 0→0，不算 | 合理：排除了「公共牌自带」的牌 |
| 公共牌已有四张同花、自己有一张小的：2♥3♦ / K♥9♥5♥7♥ | 我已是同花，rel=5；河牌红桃让公共牌也成同花，rel 5→0，不算 | 合理 |
| 暗三遇公共牌成对：7♠7♦ / 7♣K♥2♠，发出 K | 葫芦 6 − 一对 1 = 5 > 3，算 | 合理 |
| 口袋对遇公共牌成对：5♥5♦ / 9♣9♦2♠，发出 2 | 两对对两对，rel 1→0，不算；发出 5 或 9 算 | 合理 |

局限：这个口径只看牌型大类，所以同一类里的强弱不区分。例如 A♥5♥ 例中发出 5 与发出 A 都算改进；四张同花的公共牌上，拿一张小同花的河牌也算。这符合「改进牌」这个名字，不叫「出路」也不代表能赢；而且它不写进提示词，只在面板上展示。**不阻塞**，面板的说明文字写清是「按牌型大类」即可。

### 新增要求：当前牌型写进 `situation()`

- 与信息隔离一致：`handName` 只用该座位自己的底牌和公共牌。对手拿到的是自己的牌型，教练拿到的是玩家的牌型，不涉及他人底牌。
- 与 B 节不冲突：B 节说的是「当前牌型」在面板上保留，从未说过它不进提示词；修订第 99 行的解释成立。
- 小风险（建议）：`handName` 只给出大类。公共牌成对时，玩家本人也会显示「一对」，模型可能误以为自己有对子。公共牌已经在局面里，模型能自己判断，所以只建议写法上加上「最佳五张」或「含公共牌」这样的限定，不作要求。

## 本轮发现

### N1【重要】「只写成功调用」与讲解被跳过、中途失败时界面已显示的部分文字不一致，需要用户决定

现状：讲解是流式输出，`patchCoach` 把增量实时推到界面。用户点「不等了」时，条目状态变为 skipped，但已经显示的文字会保留（runner.ts 368、373）。流式输出中途失败时也一样。按修订后的 F2，这些调用都不写入 thread。

后果：用户看到教练说了半句「先看赔率，这里对手…」，接着追问「你说的对手怎么了」，教练的 thread 里却没有这句话。这正是用户原诉求 2 说的「教练对话会丢上下文」，只是换了个触发条件。

可选做法（由用户决定，不替用户选）：
- a. 被跳过或中途失败、但已有文字的讲解，也成对写入 thread，assistant 内容加「（被打断）」标记。
- b. 维持「只写成功调用」，并把已显示的部分文字从界面上清掉或折叠，让界面与 thread 一致。
- c. 接受这种不一致，在方案里写明。

对手没有这个问题：act 不是流式的，失败时界面上没有内容。

### N2【建议】memory 快照会改变本桌内「新印象立即生效」的现有行为，应告知用户

现状：对手每次决策都会重新读 `memoryOf(pid)`（runner.ts 267）。本手的 note 在一手结束时写入，从下一手起就会出现在 system 里。修订后，本桌写下的 note 要到下一桌才生效。

- thread 里拼接的文本是「想法｜行动｜说」，不含 note；而窗口只保留约 5 手，所以长时间坐同一桌时，对手在本桌学到的东西在 5 手之后就看不到了。教练的学员档案（复盘 note）也一样。
- 「长期印象保持不变」是用户认可过的内容，这次是 AI 为了缓存做的取舍。缓存已经降为附带收益，这项代价是否值得，建议向用户说明一句。也可以在拼接文本里带上 note，让它在窗口内可见。

### N3【建议】正文与修订节不一致，写成正式方案时需要合并

- 第 54 行表格仍写「新一手开始」时压缩，这与 F1 的惰性压缩矛盾。
- 第 70、94 行仍是「对手 thread 里绝不能出现别人的底牌」这种旧措辞（F8）。
- 第 78 行「误差不超过 ±1%」对应修订后的 1σ 口径（N4）。
- F1 写的是「压缩它的上一手」，应改为「压缩所有未压缩的往手」。大盲遇到全员弃牌、自己没有行动时，这一手它没有被调用，下一手要一起压缩两手。
- 第 92–95 行的验证清单没有随修订更新。建议补上以下测试：
  - 失败、中止的调用不写入；
  - 惰性压缩后 thread 的形状（第一条 user 含往手回顾，其后严格 user / assistant 交替）；
  - 赛后发言在该对手首次调用时被中止，返回结果被丢弃；
  - 往手摘要中不含 `holeAfter`；
  - 新改进牌口径的上表各例。

### N4【建议】胜率的「±1%」实际是 1σ，最好向用户明示

2500 次在胜率 50% 附近的标准误约为 ±1.0%，按 95% 置信约为 ±2%。修订写了「标准误」，技术上准确，但用户原先的决定是「误差不超过 ±1%」。建议在方案里用一句话说明，大约三分之一的时候偏差会超过 1 个百分点，由用户确认可以接受。性能上 2500 次约 80 ms，属于可以接受的主进程阻塞。

### N5【建议】赛后发言在公屏上缺少所属手号

发言是异步出现的，常常落在下一手进行中。其他对手按「上次之后的新公屏」读到它时，可能把它当成针对本手的话。建议给公屏文本或它在 thread 中的呈现加上「[第 N 手赛后]」前缀。另外，底池赔率在面板上改名为「底池赔率」，但它的值仍是「所需胜率」百分比；惯用说法里「底池赔率」通常指 3:1 这类比值。这只是命名问题。
