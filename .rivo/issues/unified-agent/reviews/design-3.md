## 本轮查证

- **Mastra 透传行为**（在仓库里临时写了一个 vitest 用例，跑完已删除）：
  - Agent **不注册任何工具**，messages 里含 assistant `tool-call` 和 `tool` `tool-result`：`stream` 不报错，两种消息原样进入模型的 prompt。Mastra 只额外给 part 加了 `providerOptions.mastra.createdAt`，并给 tool-result 补了 `input`。`sanitizeV5UIMessages`（message-list-BXFBqJQD.js）只丢弃未完成的工具 part，已有结果的保留，与当次是否注册工具无关。
  - 注册工具但传 `toolChoice: 'none'`：到模型那一层，`tools` 为空、`toolChoice` 为 `{type:'none'}`。所以对提供方来说，「注册工具 + none」和「不注册工具」一样，都是历史里有工具调用、当次请求没有工具定义。
  - 结论：Mastra 层没有障碍。能否成功，完全取决于提供方接不接受「历史里有 tool 消息、请求里没有 tools」。
- **用户本地配置**（只读查看 `~/Library/Application Support/River{,-dev}/river.db`）：两个库里都只有一个提供方，`kind = deepseek`（内置类型，不是 openai-compatible），`supports_required = 0`。教练和对手只能都用它，也就是说**教练复盘在用户这里走的也是 auto 模式**。
- **快捷键**：`hotkeys.ts` 的 `typing()` 在焦点位于 INPUT、TEXTAREA、SELECT 或 contentEditable 时，直接忽略所有牌桌快捷键，而 `useHotkeys` 只在 `ActionBar` 里用到。

## 发现

### M1【重要】教练复盘和对手赛后发言在 thread 里如何表示没有规定；按用户本地配置，两种写法各有失败路径

第 3 轮只规定了对手的 `act` 写成 tool-call + tool-result。方案 A 节说「对手和教练用同一套上下文机制」，但下面两处没有规定：

1. **教练复盘**。它也是工具调用（`recap` 工具）。现有的过渡实现是把复盘渲染成文本写入历史（runner.ts 466 `remember(...)`）。
   - **如果保持文本**：用户的教练走的是 auto 模式（见上文查证）。教练 thread 里全是纯文本的 assistant 消息，前几手的复盘也是文本。这正是 F4 当初担心的「模型模仿历史直接回文本、不调用工具」。一旦发生，`coachRecap` 会判为「教练没有给出复盘」（coach.ts 86），复盘失败。对手那边用 tool-call 历史规避了这个风险，教练却原样保留着，而且用户的实际配置就走这条路径。
   - **如果改成 tool-call**：讲解（speak）和提问（ask）不注册工具，它们的历史里就会出现 `recap` 的 tool-call。Mastra 会原样透传（见上文查证），提供方是否接受要看提供方：OpenAI 风格的接口通常接受；有些提供方（例如 Anthropic）要求请求里有 tool_use 或 tool_result 时必须定义 tools，否则拒绝。App 支持多种提供方，不只是 DeepSeek。
2. **对手赛后发言（talk）**。它是不带工具的文本调用，历史里却是 `act` 的 tool-call，所以面对的是上面第 2 种情况的同一个问题。它也不能注册 `act` 来规避，否则模型可能在赛后「出牌」；用 `none` 也一样，见上文查证。

后果：不写清楚的话，实施者只能自己选。选文本，用户的复盘可能间歇失败；选 tool-call，换到另一些提供方时，讲解、提问、赛后发言可能全部报错。

可选做法（由用户决定）：
- a. thread 里始终保存结构化的 tool-call。发给**不带工具的调用**（讲解、提问、赛后发言）时，由 `callModel` 临时把历史里的 tool-call / tool-result 渲染成文本，thread 本身不变。这样三类调用的历史表示统一，也不依赖提供方是否接受；代价是同一条 thread 会有两种发送形态，而这一手内的缓存前缀本来就没有保证。
- b. 教练复盘也写成 tool-call，不转换。把「DeepSeek 在不带 tools 的请求里接受 tool 历史」列为实机验证项，其他提供方的兼容性作为已知限制写进方案。
- c. 教练复盘保持文本（沿用过渡实现）。把「auto 模式下复盘是否稳定调用 recap」加入实机验证，失败时依靠现有的重试入口。

无论选哪种，验证清单第 178 行都应该扩展为同时覆盖：带工具历史的**文本调用**（讲解、提问、赛后发言）和教练复盘。

### M2【建议】「三条一组」没有覆盖赛后发言，「（没说话）」规则的适用范围随之改变

- 第 161 行写「F2 的『成对写入』对对手来说改为三条一组」。但对手的赛后发言不是工具调用，仍然是 user + assistant 文本两条。验证项「其后严格按组交替」需要定义清楚：决策是三条一组，赛后发言是两条一组，讲解、提问、复盘按 M1 的决定。
- F2 的「空发言记为『（没说话）』」现在只适用于赛后发言。决策时 `say` 为空，就只是 tool-call 参数里一个空字段，不需要占位文本。

### M3【建议】正文 F2、F3、F4 与第 3 轮决定直接矛盾，没有标注已被取代

- 第 108 行 F2 写「失败、中止、跳过……都不写」，与 N1「被打断但已有文字的讲解要写入」矛盾；第 108–109 行「一次写入一对」与「三条一组」矛盾。
- 第 116 行 F3 写「长期印象在入座时取一份快照」，与 N2「取消快照」矛盾。
- 第 122 行 F4 写「由代码拼成文本」，与第 157 行「写成真实的工具调用」矛盾。
- 第 51 行表格里，对手的 assistant 写的是「想法 + 行动 + 说的话」，没有反映出后面还有一条 tool 消息。

第 170 行说「正文中的旧措辞已经同步」，但只同步了 design-2 N3 点名的几处。写正式方案时，应把这三节合并或加上「已被第 3 轮取代」的标注，否则实施者照着 F4 做，结果正好相反。

### M4【建议】N1 的规则只覆盖了讲解；提问同样会留下半截文字

- 提问也是流式输出。中途失败或超时（45s）时，runner.ts 403 只把状态标为 failed，已经显示的文字留在界面上。这与 N1 描述的是同一种「界面有、thread 没有」，用户紧接着追问就会接不上。建议对提问用同样的规则（有文字就写入，并加「（被打断）」）。
- 讲解失败后重试：按 N1，被打断的那一对已经写进 thread，重试会再追加一对完整的讲解；但重试时界面会把旧文字清空（runner.ts 360）。结果是 thread 里多出半句界面上看不到的话。影响很小，写明接受即可。

### M5【建议】加注输入框：回车后焦点仍在输入框，牌桌快捷键会全部失效

- 「输入框聚焦时不触发牌桌快捷键」是 `typing()` 现成的行为，不需要额外实现。但这也意味着：回车确认后如果焦点还留在输入框，F、C、R 都不响应。用户输入金额、回车、再按 R，什么也不会发生。需要规定回车后的焦点：确认并失焦，或者回车直接执行加注，二选一。另外建议规定 Esc 放弃输入并失焦。
- 不能加注时要禁用输入框：现有的 `ctrl` 只设了 `pointer-events-none`（ActionBar.tsx 64），用 Tab 仍然可以聚焦进去。
- 解析：显示值由 `fmt` 带千分位（如 `1,200`），解析时要去掉逗号；非数字或空输入时回退到原值。
- 新决策点会把 `raiseTo` 重置（ActionBar.tsx 38–40），输入框里的草稿也要一起重置。
- 越界时的夹取与主进程 `heroAct` 的夹取一致（runner.ts 318），没有冲突。

### M6【建议】tool-result 的内容与下一条 user 消息里的公屏重复或不一致

- `say` 在公屏上被截到 40 字（runner.ts 292），tool-call 参数里却是原文。建议 tool-result 除了「实际」行动，也写上公屏实际显示的发言，与「让模型看到规范化后的真实结果」这个理由一致。
- 下一条 user 消息里的「上次之后的新公屏」会包含该对手自己刚说的话，与 tool-call 重复。建议排除自己的发言，或者接受重复。实施细节，不阻塞。

## 其它核对（无问题）

- **tool-call 历史、当次工具选择与 think**：决策时注册 `act`，按 `supportsRequired` 选 required 或 auto。历史里有 tool-call，只会让 auto 模式更倾向于调用工具，与 F4 的风险方向一致。`think` 放在 schema 的第一个字段，模型会先写想法再给行动。它只出现在该对手自己的 tool-call 里，压缩时并入「自己的想法」。信息隔离不受影响。
- **tool-result 的生成时机**：要在 `normalize` 和 `actionTaken` 之后写入（runner.ts 289 之后），而在它之前的 `sleep(wait)` 期间，已经有 `rid`、`handLog` 检查兜住离桌和状态变化。顺序可行。
- **压缩后改写为文本**：每一手的第一次调用时历史里没有 tool-call 示例，等同于现状下无历史的 auto 调用，而现状下这种调用是能用的。不引入新风险。
- **`Msg` 扩展**：`llm.ts` 目前按角色把消息映射成判别联合（第 88 行），需要加上 tool 角色和数组形式的 content，还要生成 `toolCallId` 并让两条消息对应上。`test/mock-model.ts` 的 `calls` 目前只记录消息条数，验证清单第 176 行要求检查 tool-call 的形态，所以 mock 需要记录 prompt 内容。都是实施细节。

## 证据限制

- 没有调用真实提供方。「不带 tools 的请求里有 tool 历史」时，DeepSeek 的内置接口、OpenAI、Anthropic 各自是什么反应，都没有实测。M1 中关于 Anthropic 的说法来自对其 API 限制的已知信息，可能已经随版本变化。
- DeepSeek 的思考模式在多轮工具调用时，对 `reasoning_content` 有回传要求。本方案的每组都以新的 user 消息结束，通常不受影响，但没有实测；`deepseek-flash` 是否属于思考模式也没有核实。
- Mastra 的行为只在 1.69.0 上用 mock 模型验证过。临时测试文件已删除，工作区没有留下改动。
- 用户本地数据库只做了只读查询。
