## 用户追加「本手共投入 X」与 plan 的关系

- **与 plan 不冲突**。`Table.seats()` 确实返回 `totalIn`（`engine/table.ts:270`）。`put()` 在加 `bet` 的同时加 `totalIn`（第 389 行），无人跟注的退回也会同步扣减（第 412 行），所以决策时看到的是准确的公开数额。它是公开信息，不影响信息隔离；和 plan「给模型精确事实」的目标一致；对 `lastSituation` 的比较也没有影响。

## 发现

### U-1（重要）T1、T3 会改变 rng 消耗，发出的牌随之改变；迁移后的信息隔离测试会跨手误报

- **证据**：
  - runner 的 `this.rng` 同时用于发牌（`new Table(..., this.rng)`，`table.ts:97` 用它洗牌）和胜率模拟（`equityFor` → `equity(..., this.rng)`）。
  - T1 把玩家的模拟次数从 400 改为 2500（`runner.ts:348`），T3 删掉对手决策时 150 次的 `equityFor`。这两处改动都会改变 `seeded(1)` 下之后每一手发的牌。
  - 第二条隔离测试（`runner.test.ts:317-338`）检查的是：第 1 手弃牌者的底牌字符串，不出现在第 2、3 手对手的全部输入里。但每一手都会重新洗牌，第 2、3 手里观察者自己的底牌、公共牌，完全可能正好是同一张牌。现在这条测试能通过，只是 seed 1 下碰巧没有撞上。粗略估计，每次观察撞上的概率在一成以上。
  - T3 迁移后，要检查的范围从一条 situation 扩大到整条 thread（包括往手回顾、各组 tool-call），第 228 行又写成「任何消息都不包含」，撞上的机会更多。
- **后果**：T1 或 T3 完成后，隔离测试可能在代码完全正确的情况下失败。实施者可能误以为有泄露去改实现，也可能换一个「碰巧能过」的 seed，那样这条测试就没有区分能力了。其他依赖具体牌面的 runner 测试也可能因为发牌变化而失败，而 task 没有说这是预期内的。
- **建议**：
  1. 在 T1 和 T3 写明：模拟次数变化会改变发牌序列，runner 测试因此失败时，要把测试改成不依赖具体牌面，不能靠换 seed 解决。
  2. 第 228 行的断言改为只检查由第 N 手产生的内容：往手回顾里「[第 N 手]」那一段、第 N 手的 talk 观察、写入的 summary。或者检查带上下文的字符串（比如「亮出 X」、底牌列表），不要做全文的裸牌面匹配。
  3. 第 227 行的第二条同样处理。「例外：该对手自己的底牌」要写明指的是第 N 手的底牌。

### U-2（建议）「本手共投入」没有记录在 plan 和 discussion 里，含义和验证也不够明确

- **证据**：
  - `plan.md` 第 75–92 行的输出示例只有「本轮已下」，discussion 里也没有这项决定。
  - task 第 5 行说依据是 plan。
  - 验证（第 98 行）只要求「带『本手共投入』」这几个字。
- **后果**：
  - 以后按 plan 核对时，这一行会被当成偏离。
  - 翻牌前的小盲会显示「本轮已下 50，本手共投入 50」，模型可能把两项加起来，理解成投入了 100。
  - 数值写错（比如错写成 `bet` 或 `stack`）时，测试照样通过。
- **建议**：
  - 在 discussion 里记下这项用户决定，并更新 plan 的示例。
  - 文案写成「本手共投入 X（含本轮）」，或者只在它不等于本轮已下时显示。
  - 验证改为断言具体数值，比如翻牌后某个跟注者的投入额；并断言 `totalIn` 为 0 的座位不出现这一项。

### U-3（建议）对手摘要的命名规则没有测试，位置行也没写对手自己怎么称呼

- **证据**：
  - 第 189–190 行规定，行动行里座位 0 写「玩家」，对手自己写「你」。但位置行只规定「玩家本人写作『玩家』」，没说对手自己写作什么。
  - T3 验证（第 218–229 行）里没有 `opponentSummary` 的断言。
- **后果**：
  - 位置行如果照搬公开名，同一段摘要里对手自己一会儿是「你」，一会儿是自己的名字。
  - T-2 指出的混淆（把玩家的行动当成自己的）如果以后回归，也没有测试能发现。
- **建议**：
  - 位置行也按「座位 0 写『玩家』、对手自己写『你』、其他人写公开名」处理。
  - 在 T3 验证里加一条 `opponentSummary` 的单元测试，断言玩家的动作写成「玩家…」，对手自己的动作写成「你…」。

### U-4（建议）T1 新加的 situation 断言写在替身的旧输入上，T3、T4 没有说要迁移

- **证据**：T1 验证（第 99 行）让测试从 `coachSpeak` 或 `opponentAct` 替身读 `situation` 字段。T3 和 T4 之后，这两个输入改成了 `messages`，但 T3 第 227 行只提到迁移两条隔离测试，T4 没有提到迁移。
- **后果**：实施者可能在类型报错时直接删掉这条断言，「位置、牌型、所需胜率进入提示词」这一点就没有测试覆盖了。
- **建议**：在 T3、T4 的验证里写一句：T1 新加的 situation 断言迁移为读最后一条 user 消息。

### U-5（建议）T4 没有重申 observation 必须取 `messagesFor` 返回的最后一条 user 内容

- **证据**：
  - T3 明确要求 `obsWithRecap` 直接从 `messagesFor` 的返回值里取（第 185 行）。
  - T4 的 `pushText(hand, obs, …)`、`pushTool(hand, obs, 'recap', …)` 用的是「obs」，而 T4 表格里的 obs 是 runner 拼出来的原始文本，不含往手回顾。
  - 典型场景：教练局里玩家是大盲，其他人全部弃牌，玩家这一手没有决策点，复盘就是教练 thread 这一手的第一组。
- **后果**：如果照 T4 的字面实现，往手回顾不会被写进 thread，这一手后面的提问就看不到往手，前缀缓存也会失效。共同约定第 40 行虽然要求 observation 必须和 `messagesFor` 里用的一致，但 T4 的写法容易让人忽略这一点。
- **建议**：在 T4 的 runner 改动里写明：讲解、提问、复盘写入时，都用 `messagesFor` 返回的最后一条 user 内容，和 T3 一样。验证里再加一条：玩家这一手没有决策点时，复盘之后提问，thread 的第一组包含【往手回顾】。

### U-6（建议）`chatSeen` 推进到哪一条，写得有歧义

- **证据**：第 176 行说推进到「本次观察所用的最后一条消息」。如果过滤后没有新消息（全是 sys 或它自己的发言），`chatSeen` 就一直停在旧的 id 上；等这个 id 被 `MAX_CHAT` 截掉以后，就会退回到「从头取最后 8 条」，把已经看过的公屏重新给它一遍。
- **后果**：影响很小，只在长局里偶尔重复出现几条公屏。
- **建议**：写成「推进到观察时 `this.chat` 最后一条消息的 id（不管是否被过滤）」。

## 已核实无问题的点

- 公共接口（`Msg`、`Thread` 的签名和语义）与 plan 一致。`setSummary` 在四种 `hand` 状态下都有定义。压缩即中止的两个中止点，以及离桌时的中止，都有对应的实现步骤和验证。
- `AgentDeps` / `realAgents` 在 `runner.ts` 中，`tsconfig.node.json` 包含 `test/**/*`。加上 `opponentTalk` 之后，漏改替身会在类型检查时报错。
- 教练的 `setSummary` 放在 `onHandEnd`，复盘时 `hand` 仍是这一手，不会触发压缩。玩家这一手没有决策点时，`setSummary` 也能正确推进 `hand`。
- 入过池的判定（preflop 有 call/bet/raise，或者看到了翻牌、而且不是 preflop 弃牌）与 plan、discussion 第 137 行一致。
- `Nums.sugg` 只在 `view.ts`、`types.ts`、`CoachPanel.tsx` 三处使用，都在 T1 的修改位置里。
- T1 暂时保留对手的 `equityFor` 调用不会导致类型检查失败（没有开启 `noUnusedLocals`）。
