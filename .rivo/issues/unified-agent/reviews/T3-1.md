## 发现

### F1（中）两条中止与写入的场景没有测试，已有的中止测试区分不出对错

- **证据**：
  - `runner.test.ts`「还在进行的赛后发言：该对手下一手首次被调用时中止…」用的是 `free3`，玩家一直跟注，每个对手每手都会行动，所以中止总是先由 `messagesFor` 触发。
    - 单独删掉 `opponentTurn` 里的 `onCompress`：下一手结束时 `setSummary` 也会中止，`aborted > 0` 仍然成立。
    - 单独删掉 `setSummary` 的 `onCompress`：测试仍然通过。
    - 替身在 abort 时返回 `ok: false`，所以删掉 `talkCtrl.get(pid) !== ctrl` 这项核对，「不写入」也仍然成立。
  - task 的验证要求「玩家点下一手、该对手还没被调用时返回的发言照常写入」没有测试。「一手结束…」那条用例里 talk 是立即返回的，在下一手开始前就写完了。如果把过期判定写错成看牌桌手号，这条用例仍然通过。
  - task 的验证要求「下一手结束写 `setSummary` 触发压缩，这条发言也被中止（它在第 N+1 手没被调用）」没有测试。
- **后果**：plan「写入契约」里最容易写错的两点，一是按 `thread.hand` 而不是牌桌手号判定过期，二是 `setSummary` 这个中止点。现在的测试都守不住。
- **建议**：
  - 写入场景：talk 替身返回一个手动控制的 deferred。第 1 手结束后调用 `nextHand()`，让该对手在第 2 手还没被调用（或者先 resolve 再推进），然后 resolve 并返回 `say`。断言公屏出现 `[第 1 手赛后]`，而且该对手在第 2 手第一次观察的往手回顾里有「赛后说：」。
  - 中止场景：安排第 N+1 手里该对手不会被调用。例如三人桌里他坐大盲，玩家和另一个对手都弃牌（可以选合适的 seed 或按钮位置），或者直接用 deferred 保持在途，并记录替身收到的 `signal`。断言在第 N+1 手的 `hands:changed` 之后 `signal.aborted === true`，而且在这之前该对手的 `opponentAct` 没有被调用。
  - 另加一种替身：忽略 signal、延迟后返回 `ok: true`。用它锁住「中止后返回的结果不写入」，这样 ctrl 核对才真正被测到。

### F2（中）talk 的 note 落库没有测试

- **证据**：task 验证清单写的是「talk 成功：…note 写入 `memory`」。runner.test 的 T3 用例里没有一条断言 `db.memoryOf`（第 86 行已经有同类写法，可以照抄）。
- **后果**：如果 `addMemory` 这一行被删掉或者条件写错，测试都发现不了。
- **建议**：在「一手结束后入过池的对手赛后发言」这条用例里，让替身返回 `note`，事后断言 `await db.memoryOf(pid)` 包含这条 note（注意 `addMemory` 是 `void` 调用，要先 `tick` 一下）。

### F3（低）runner 层没有断言翻牌前弃牌的对手不发言

- **证据**：只有 `enteredPot` 的纯函数测试。task 要求的是「一手结束后，入过池的对手调用了 talk，翻牌前直接弃牌的对手没调用」。`onHandEnd` 里用没用 `enteredPot` 过滤，没有测试覆盖。
- **后果**：如果 `if (enteredPot(...))` 被误删，所有对手都会发言，测试仍然通过。
- **建议**：一个对手的 `opponentAct` 在翻牌前固定弃牌，另一个跟注。断言 `talks` 里第 1 手只有跟注的那个对手。

### F4（低）`opponentSummary` 的称呼没有直接测试

- **证据**：task 要求验证「对玩家写『玩家』，对自己写『你』，其他人用公开名，并且不出现『你』指代玩家的情况」。仓库里没有任何测试引用 `opponentSummary`。现有的 runner 断言只覆盖了 `situation` 的座位行（`- 玩家（…`）。
- **后果**：实现现在是对的，但称呼规则分散在 `nameOf`、`publicHandResult` 两处，以后改动很容易让「你」又指向玩家。
- **建议**：构造一个 `HandRecord`（玩家在 seat 0、名字是「你」，对手 A、B），对 A 调用 `opponentSummary(rec, 'A')`，断言含「玩家（…）」「你（…）」「B（…）」、「玩家加注至」「你跟注」这样的片段，并断言不匹配 `/你(加注|跟注|弃牌|过牌|下注|全下|小盲|大盲)/` 出现在玩家那一行。再构造一个教练局记录，断言不出现 `holeAfter` 里的牌。

### F5（低）两条已有用例少了关键断言

- **证据**：
  - 「赛后发言失败：牌局照常…」只断言了 `stalled === null` 和公屏里没有「赛后」，没有断言 thread 没写入。task 写的是「thread 没有写入」。
  - 「…别的对手下次观察能读到」断言的是 `later.some(...)`，没有断言对手看不到自己的赛后发言。把 `newChat` 里的 `m.from !== self` 删掉，这条用例仍然通过。
- **建议**：失败用例里记录 `opponentAct` 的 messages，断言任何一次都不含 `toolName: 'talk'` 和「赛后说」「赛后没说话」。新发言用例里，对每次调用 `c`，断言它的「新发言」段里不含 `${c.name}：` 开头的行。

### F6（低）`talk()` 的异常没有兜底

- **证据**：`void this.talk(...)`（runner.ts 约第 557 行）。`talk` 里的 `await memoryOf(pid)` 如果因为数据库错误而 reject，就会变成未处理的 Promise 拒绝，`talkCtrl` 里也会留下这条 ctrl。
- **后果**：不影响牌局，下一次 `abortTalk` 会把它清掉。但主进程会打出 unhandledRejection 警告。赛后发言按定义可有可无，不应该留下这类噪音。`opponentTurn` 也有同样的写法，那是原有代码。
- **建议**：改成 `void this.talk(...).catch((e) => console.error('talk failed', e))`，与 `addMemory` 的写法一致。

### F7（信息）两处与字面约定的出入，不需要改

- 约定写的是「如果该座位还在桌上就 `bubble`」，实现是无条件 `bubble`。本应用的座位在整桌期间是固定的（破产后重新买入，不会离座），所以没有实际差别。
- 往手条目里同时出现「你本手 +300」（来自 `publicHandResult` 的净输赢）和「你本手：跟注…」（digest），措辞重复。格式是 plan 定的，可以留到 T7 实机观察模型会不会混淆时再决定。
