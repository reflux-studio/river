# River 跨端事件架构：讨论草案

负责人：Codex。来源：2026-11-02 用户架构说明；实际实现基线 `55198dd`，依据见 [现状调查](research/current-architecture.md)。本文是已确认方向的讨论背景。当前技术方案与实际协议定义见 plan.md 及其登记附件，本文不再作为第二份实施契约。

核心方向：本地身份与记录、轻量权威房间服务、Electron 本地 Agent，以及共用的命令/事件协议和前端应用。这里的“本地身份”意味着没有中心账号，不意味着多端分别维护同一张牌桌的权威状态。

## 运行位置

| 场景 | 权威牌局 runtime | 客户端传输 | Agent | 长期记录 |
| --- | --- | --- | --- | --- |
| Electron 本地单人 | 本机 Node 主进程 | IPC | 本机 Node | 本机 SQLite |
| Electron 好友联机 | 公共 WS Node 服务 | WS；可由主进程统一连接并通过 IPC 接 renderer | Electron 主进程的 AI 控制端 | 各玩家本机 |
| Web 真人建房/入房 | 公共 WS Node 服务 | 浏览器 WS | 无本地 Agent；可授权 Electron 参与者提供 AI | 浏览器 IndexedDB |

用户原话两次写“对于 web 端”，结合上下文将第一处理解为 Electron 的本机 Node，第二处为 Web 连接的远程 WS Node。用户后续认可分析方向，沿用此运行位置理解。

“Web 不创建 AI”是本项目采用本地 Node Agent 与本地 Key 的产品/技术边界，不是浏览器在所有技术路线下绝对无法调用模型。公共服务完全不加载 agents 包，也不接收模型 Key。

## 包职责建议

以下是目标职责；包名可按实际抽取调整。共享声明先定义领域能力，不创建一个无边界的通用工具包。

| 包/应用 | 负责 | 不应依赖 |
| --- | --- | --- |
| @river/engine（现有） | 纯规则、牌型、筹码、洗牌与座位行动 | Electron、WS、React、数据库、Agent |
| @river/protocol（新增） | 命令、公开/私有事件、快照、错误码与运行时 schema | 具体宿主与数据库 |
| @river/runtime（新增） | 房间内权威状态、命令校验、推进时序、投影视图、决策任务 | React、Electron、模型 SDK、玩家资料库 |
| @river/client（新增） | 连接生命周期、命令确认、快照/事件归并、可订阅状态、本地记录编排 | Electron API、具体数据库 |
| @river/storage（新增） | PlayerProfile、偏好、手牌/对局记录和统计的异步接口、schema 版本约定 | SQLite、IndexedDB、Electron |
| @river/agents（抽取） | 观察转提示词、AI 决策、教练、thread、模型调用 | 权威 Table 对象、UI、公共房间服务 |
| @river/app（抽取） | 共用页面、房间流程、响应式布局、操作栏与状态展示 | 直接 window.river、具体持久化、模型 Key |
| @river/ui、@river/i18n（现有） | 纯展示与固定内容 | 网络、存储、Agent |
| apps/desktop | 组装 IPC/WS、SQLite、safeStorage、本地 runtime 和 Agent 控制端 | 不复制牌局与页面规则 |
| apps/web | 组装浏览器 WS、IndexedDB、浏览器宿主能力 | Node 模型 SDK、Electron |
| apps/server | 组装 WS、房间注册表、runtime 和连接清理 | 用户中心、个人长期数据、模型 SDK |

依赖方向：engine/protocol 在底层；runtime 依赖它们。client 依赖 protocol 和 storage 接口；app 使用 client 与 ui/i18n。Agent 以裁剪后的观察和决策请求为输入，通过 protocol 提交命令。各 app 是组合入口。

前端只消费事件与渲染仍包括状态归并、输入处理、响应式布局、网络状态、本地记录、动画音效及错误展示；它不重新裁判行动、不独立计算权威结算。模型提示词格式化不是规则裁决，可留在 agents 中。

## 命令、事件和快照

客户端发的是意图，例如 createRoom、joinRoom、act、rebuy。runtime 验证后改变状态，再输出已成立的事实，例如 playerJoined、actionApplied、boardDealt、handSettled。客户端发出 raise 不等于加注成功，必须收到结果后更新权威显示。

事件驱动用于解耦与推送，不等于要求全系统事件溯源。runtime 仍维护当前状态；快照用于首次进入、重连或发现版本缺口后恢复。动画音效是可跳过的展示效果，重连不重播历史发牌。

| 数据 | 接收者 |
| --- | --- |
| 公共牌、筹码、行动、公开聊天、合法公开亮牌 | 房间参与者 |
| 某座位底牌、该座位合法动作与决策请求 | 该座位控制端 |
| 教练观察与输出 | 已授权的辅导接收者；规则待确定 |
| 模型 Key、私有推理与本地长期记忆 | Electron 本地 |
| 完整牌堆与未授权底牌 | 仅权威 runtime |

禁止把所有底牌广播后靠 UI 隐藏。公开事件流与每个私有接收流可以有各自连续序号，或使用完整的按接收者版本视图；不能因过滤私有事件造成误判丢包。最终序号设计见 Q8。

建议 act 携带 commandId、roomId、handId、decisionId；身份和座位从连接绑定中取。房间串行处理动作、超时和断线，验证决策仍有效，并以 commandId 去重。重连凭证有不同的 controllerId 与 seatId 语义，本地 playerId 只用于资料关联。

## 一次真人行动

1. 玩家在共享 app 点击加注；client 通过 IPC 或 WS 发送 act 意图。
2. runtime 校验发送端座位、轮次、金额、决策标识与重复请求，再调用 engine。
3. runtime 输出公开 actionApplied，分别输出各接收者私有视图，必要时发布下一个 decisionRequested。
4. client 归并确认后的状态，app 渲染；每手结算后将获授权记录保存到本地 storage。

## 一次 Electron 托管 AI 行动

1. Electron 房主创建 AI 座位；房间记录该座位由指定 AI controller 控制，控制权限不由客户端自行声明覆盖。
2. 轮到 AI 时，runtime 向该 controller 发决策请求，包含此 AI 底牌、公开信息、合法动作与 decisionId。
3. 本机 Agent 使用本地 Key 调用模型，返回动作与可公开台词；内部推理和 Key 不上传。
4. controller 像真人一样发送 act；runtime 做同样的合法性与时效校验，然后广播结果。

AI 不一定需要每个角色建立一个物理 WS，可在一个连接里复用多个被授权的 controller。Electron 本地单人使用相同决策请求/动作契约，经进程内通道执行，不需公共服务。

本地 Agent 无法保证房主机器看不到它托管 AI 的私有观察。多 AI 同机也无法提供相互间硬隔离；软件应逐 AI 裁剪，但电脑所有者仍可检查进程。用户已明确接受这项娱乐局取舍。按 AI 裁剪观察仍需保留，但不再把宿主访问自身托管 AI 底牌作为阻碍方向的待决风险。

## 本地存储边界

建议定义按领域命名的异步接口，如 ProfileStore、PreferencesStore、HandHistoryStore、StatsStore；Electron 使用 SQLite，Web 使用 IndexedDB。模型凭证另设桌面专用 SecretStore，避免共享 app 假定 Web 存在模型 Key 能力。

本地 playerId 是设备资料标识，可重建或修改。服务端接收昵称和期望买入后按房间规则确认，当前牌局筹码由 runtime 维护。不再维护长期余额或全局资金账户，各端只累计个人战绩、场次买入/取回和收益趋势。

记录以 roomId + handId + playerId 幂等写入；手牌记录和统计更新需原子提交，或以不可变手牌记录派生统计。不要让重连重放累加两次胜负。每个接收者只存其被授权的信息；客户端无权读取别人的隐藏底牌来做完整回放。

IndexedDB、SQLite 的迁移、批量写入及失败语义应由接口明确约定，不能只用一组 CRUD 方法声称跨端一致。首版不要求跨设备同步。断线漏掉的结算需在房间存活期间可补取；补取保留期限与服务重启语义需要决定。

## 轻量服务的必要边界

公共服务维护 roomId → runtime、实体与连接绑定、恢复状态及未领取结算信息。不需要注册登录、中心玩家表或长期战绩服务。建议随机控制/重连凭证限制连接能控制的实体；房主权能绑定当前 hostId，不能成为不可转交的唯一秘密。服务端已决定本地持久化房间，见 ADR-004。

房主控制权、牌局裁决、Agent 控制端是独立职责。Player.role 为 human 或 agent，hostId 是房间管理授权，seatId 是入座关系；不把 host 作为第三种玩家类型。真人客户端与 Agent 控制端独立连接/心跳，真人离线不推导 Agent 离线。即使底层复用一条物理连接，也必须按独立实体处理状态；同一物理链路断开可以令各相关实体分别离线，不执行“房主掉线所以移除其全部 AI”的业务联动。

## 筹码即时变化与本地记账

有效下注即时消耗可用筹码，退出或掉线不撤回有效投入。事件驱动传播变化，正确性来自 runtime 权威更新与客户端幂等处理，不能把 WS 成功发送当作下注已成立。

建议 actionApplied 或其配套私有状态携带行动增量、行动后 stack/bet/totalIn 和版本。本轮已投入 100，再 raiseTo 300，新增扣款是 200。动画可延迟收筹码，但权威状态已更新，视觉收池时不能再扣一次。

已决定取消长期钱包：买入是本场新增资金流，下注从 stack 转入投入，分池回到赢家 stack，离桌记录取回。收益与总买入按场次汇总，本地持久化按事件 ID 去重，写入失败可重试，不回滚远端行动。不能把买入误计为盈利。

断线不自动退款，也不立即等同弃牌。真人轮到行动仍按真人计时处理；已全下者断线仍保留争池资格。移除阻塞 AI 按管理性弃牌处理，保留投入；全下者无需决策，离座延后到结算。无人跟注超额的正常退回仍执行。

服务崩溃由服务端本地房间存储恢复，已由 ADR-004 确认。不能只依赖玩家各自保存的快照；剩余牌堆、行动权、筹码及命令结果需作为一致的权威状态保存。

## 2–10 人跨端容量

最大 10 人，真人与 AI 合计占座。建议统一 MAX_SEATS 与运行时校验，拒绝第 11 个入座请求。房间容量、已占座位和本手参赛人数分开；玩家离开不重排稳定 seatId。

engine 的动态座位数组具有扩展基础，但仍须验证 10 人发牌、轮转、盲注、边池和筹码守恒。视图可围绕本人座位旋转，所有动画沿同一映射消费，不能改变实际座位标识。

现有 UI 按极坐标均分位置，座位卡片与气泡宽度固定，不能据此认定 10 人小屏可用。需要设计紧凑座位、稳定的本人操作区及可展开公屏/详情，实际检查电脑、平板与手机横竖屏。当前内置 AI 人设仅 8 个，一真人九 AI 需要额外角色或独立实例规则；不能静默缩桌。

## 新增多人交互如何进入同一架构

以下是基于已确认功能范围的技术建议，动作名称与字段尚未定稿。牌局规则、房间政策和客户端显示继续分层：engine 计算结算；runtime 决定展示、截止时间和预约执行；client/app 负责交互与渲染。

### 每手结束自主亮牌

采用“手牌结算 → 有限展示阶段 → 下一手”的运行生命周期。弃牌后不立刻允许亮牌，避免在本手仍有行动时提供额外信息。每个座位可提交 revealHole(handId, cardIndexes)，runtime 验证控制权、手号、展示阶段与卡槽，再从自己保存的牌面产生 holeRevealed；客户端不能自行提交牌面作为事实。

已公开的底牌不能撤回；结算规定的摊牌与自愿亮牌分别处理。现有自由局固定公开所有未弃牌者，教学局公开全部底牌，这些是当前视图策略，不能直接代替新的可见性政策。自愿单张亮牌已确认支持；是否允许输家在摊牌阶段 muck 仍需产品规则确认。

AI 可使用同名语义的 show_cards 工具，经本地 controller 提交 revealHole；工具只接受卡槽，不接受任意手牌或其他人的座位。可与原有赛后 talk 一次模型调用返回多个可选行为，避免仅为亮牌额外强制调用。AI 未返回、宿主离线或超出展示窗口，默认不主动亮牌，不阻塞下一手；已由规则公开的牌除外。用户已确认支持任意单张与两张，工具与 UI 都按卡槽表达。

晚到亮牌也会影响回放和 AI 已接收的公开观察。因此先结算时保存记录，再以公开揭示事件增量更新该手的可见信息；净收益不重算、手数不重复累计。展示窗口后的请求拒绝，下一手发牌前应完成公开观察的顺序归并。

### 真人行动计时与 Agent 调用超时

真人座位由 runtime 为每个决策发布 decisionId 与 deadlineAt，以注入的时钟执行截止处理；Node 不依赖浏览器定时器继续推进。客户端通过握手/往返时间估计服务端时间差显示剩余时间，显示归零不是结算依据。建议默认 30 秒、房主建房可调，超时合法 check，否则 fold，具体参数仍待定。

手动动作、预约动作和真人超时进入同一个串行处理路径；以 runtime 实际接受时点判定截止，截止前后谁先执行不能造成双重落子。runtime 在处理新消息时也核对截止时间，不能因 Node 定时器延迟而接纳已经超时的动作。

AI 座位不创建真人行动截止时间，由本地 Agent 调用层负责 timeout。当前对手决策代码固定为 45 秒、允许两次重试；Settings 类型和设置页没有可调整调用时限的配置。本次不把“记得有全局设置”当作已实现能力；若需要用户可调，应新增 Electron 本地设置，而非房间真人计时字段。

AI controller 上报 decisionFailed，runtime 验证它对应当前决策与调用尝试，进入 decisionBlocked 并通知所有玩家。房主可发 retryDecision 或 removeAi，其他玩家只看到等待房主处理。重试生成新的 attemptId，并作废旧尝试；runtime 保留 handId/decisionId 校验，防止已重试或移除后的旧模型结果落子。Agent 自带的有限自动重试可以保留，仍需区分它与房主点击的显式重试。

建议移除 AI 时发管理命令：结束本手争夺资格、保留已投入底池、不退回有效下注，结算后移除座位并处理剩余筹码；不能直接对运行中 Table 调 standUp。现有 engine 在 toCall 为零时不提供普通 fold，因此“移除即弃牌”需要专门的管理性弃牌语义，而不是伪造一个不合法的普通 fold。该细则仍需整体确认。已有全下资格不能随意撤销，AI 全下无需模型决策，手中请求移除应延后到结算。

runtime 不读取 Agent Key 或调用配置。区分 Agent 在线但决策失败与控制端离线：前者等待房主重试/移除，后者按统一的实体掉线期限和移除流程处理，不因房主在线与否改变。human 在掉线期限内轮到行动仍按真人计时 check/fold；掉线期限到达移除，若它是房主则转移管理权。已有全下者保留本手资格至结算。可选聊天、赛后亮牌调用失败不会进入阻塞状态。

### 预约操作

建议由 runtime 保存座位的私有 PreAction 意图，客户端发 setPreAction/cancelPreAction，并展示服务端确认的预约状态。这样页面切后台或短暂断线时，已确认预约仍可执行；客户端重新加载时能从私有快照恢复。断线清不清除预约需作为明示规则。

预约绑定 roomId、handId、street 和一次性版本。轮到该座位时，runtime 根据当时 legalActions 重新检查条件。check 需 toCall 为零；fold 需出现在合法动作中；checkOrFold 可 check 则 check，否则合法 fold。条件失效则取消并进入普通计时，不能变成 call。执行后清除，跨街/跨手默认清除；不添加未经用户要求的预约跟注或自动加注。

手动 act、取消预约、修改预约与轮到执行都串行化并有确认结果。服务端已经执行的动作无法通过晚到取消撤回。预约内容仅属于该座位，不提前广播给对手；执行后只广播普通 actionApplied，可在本人记录中注明来源。预操作触发只针对最新决策一次，避免同一队列递归无限推进。

### 盈亏与结算

engine 已有每座位 stack、startStack 与 pot winners；runtime 在结算时为所有参与者产生 handNet，而非固定 hero。含重买入的一整场收益可取已结算 handNet 之和，并与现金流核对：离桌取回加桌上余额减所有买入。

本地历史统计按 handId 去重。手牌结算与后续亮牌更新分开，重买入只记资金流，不记为获利。零和校验面向整张桌所有参与者，包括 AI 和已离桌玩家；无抽水场景一手净收益之和应为零。获底池、净盈利、负收益和平手不是同一个指标，统计定义待产品确认。

### 自由公屏

新增 chat.send，发送者由连接绑定确定，runtime 输出带 messageId、时间与作者 seat/controller 标识的 chat.message。真人和 AI 都可走这一契约，独立于下注轮；规则日志与公屏文本保持不同事件类型，不能用聊天文本冒充加注或亮牌事实。

复用现有消息列表与最近发言 UI，增加输入框与移动端面板。真人自由发言无需触发每个 AI 立刻回答；Agent 在它的决策/赛后上下文中按已消费游标获得新公开消息，避免一条消息导致多次模型调用。聊天是参与者内容，不改变 runtime 的规则和 Agent 工具权限。消息限长、频率和短期保留属于轻量房间运行边界。

## 本轮新增结构边界

### 本地房间持久化

推荐单实例 Node 加本地 SQLite，给 runtime 注入独立 RoomStore；不将 Electron 玩家资料库复制到公共服务。显式导出/导入可版本化的完整状态，包括剩余牌堆、私有底牌、筹码层、行动状态与房间政策。当前 engine/Deck 没有这一恢复接口，需要实现，不宜直接 JSON.stringify 类实例假定可恢复。

一次命令在房间串行队列中验证、计算候选新状态，将新状态、命令结果与待发事件一致提交，再对外确认并发布。提交失败不能留下已改变但未持久化的内存状态。重连依快照和命令结果去重，处理已提交但未发送的结果；无需引入外部分布式消息队列。

服务重启后恢复房间，但旧连接与未完成模型调用不直接复活。Agent 用新 attemptId 恢复或重新请求；真人/Agent 获得明确的重连阶段，暂停和剩余计时按选定政策恢复。这是可控的单机恢复工作，不等于只加几个落库调用，也不包含多实例高可用。

### 私有教练旁路

房间决定 coachAllowed，Electron 本地玩家在收到自己的 decisionRequested 时触发教练 hook。教练只能消费与该玩家相同的私有视图和已授权历史，不引用完整权威 Table。输出进入本地教练面板，不广播、不占用回合或延长计时；玩家行动后取消/标记过期讲解。单人引导是否保留显式教学节奏可作为本地 UI 策略，不写进多人规则运行核心。

当前 runner 将教练 busy/spokenKey 与 heroCanAct 绑定，提取时需要解除。coachAllowed 与 revealAllAfterHand 已确认为独立开关，多人默认均关闭；可见信息扩展后教练自然获得同样扩展，无额外越权通道。

### 观战透视与胜率

已确定纳入首版，娱乐房默认开启。viewMode 独立于 Player.role，按当前手是否仍有争池资格授权；已弃牌、待上桌及观战者可获得透视，全下者仍在争池不能当作场下。看过透视数据者本手不可重新入局。

运行时为观战者生成额外私有投影，只给其可见的底牌与牌面胜率；正常争池玩家不接收这些数据。手后自愿亮牌成为公共信息，与观战中的私有透视分开，历史记录也保留接收者权限。房间是否允许即时透视在入房前明确展示；朋友间已接受的信任边界不再扩展为反作弊系统。

现有 equity(hole, board, nOpp) 将对手手牌随机化，不能当作已知全体手牌的比赛转播胜率。需新增基于已知底牌、已知死牌和未知公共牌的多玩家计算，禁止使用未来牌堆顺序。展示应说明是赢牌概率还是平局分摊权益；边池金额不同，不能把一个百分比直接当预期赢钱占比。计算应异步/缓存，不阻塞权威行动队列；只在已授权的观战投影中提供。

### 全局暂停与手后展示

用户确定手后约 5–10 秒展示且房主可跳过，并增加全局暂停。建议默认 10 秒。暂停建议是独立的房间状态，冻结出牌推进、真人行动剩余时间和手后展示时间，聊天、重连及管理权处理继续。Agent 本地调用可继续，结果在 runtime 缓存，恢复后仍经同一决策有效性校验；若调用失败则保留阻塞状态。

暂停语义已获用户确认：连接清理和管理权处理继续，改变牌局的移除延后至恢复。持久化保存剩余时间与暂停状态，不能恢复时把旧 deadlineAt 当成刚刚超时。建议暂停期间买入可登记待处理，但不改变当前决策已缓存的合法动作，恢复后先处理资金变动再重新校验并生成决策版本；细节随买入资格确定。

### 手中追加买入

已确定允许手中追加买入，不建立玩家之间欠款账。一次买入是独立命令与现金流事件，增加可用 stack，不直接增加 totalIn，也不计为盈利；随后加注仍走正常 act 校验。快照恢复与场次统计必须包含手中资金流，不能继续假设一手 startStack 到结算期间只有输赢变化。

按用户最新修正，买入/卖出独立于本人回合，可在手中任意时点登记，不重置行动计时。卖出只能取回尚未投入的可用筹码，不能动 bet/totalIn。已全下者的新买入留待下一手，不取消 allIn 或倒改争池资格。资金变化会使此前的 maxRaise 等合法范围过期，应重新发布决策版本并使相关旧 Agent 尝试失效；不能通过重复资金操作无限延长回合。

本手净收益需扣除本手新增买入并加回本手取回，不能简单使用 endStack - startStack。允许手中卖出是本娱乐局明确采用的资金规则，engine 的 setStack 当前只允许两手之间使用，需新增领域入口。资金操作本身不算一次下注，不重开加注权，不令弃牌者复活，也不把卖光筹码自动冒充已执行的 all-in 行动；零可用筹码时仍需在合法决策路径买入、check/fold 或确认本手投入上限，避免无行动地改变争池资格。

## 未闭合场景

当前主要产品选择均有答复，进入完整做法确认。协议字段、运行时校验与恢复契约由开发在方案落实，发现新的核心取舍再回到讨论。部署环境与容量在实际部署前核对，不以静态设计宣称线上能力。

## 当前运行默认值与关闭终态

真人每回合 30 秒，实体掉线宽限 60 秒，手后展示 10 秒，均作为房间配置。房主启动首手，中途加入者下手入局；预约一次性且本街有效，短暂断线保留已确认预约。单手净收益正/负/零定义胜/负/平，同一房间内离桌再入场归同一场统计。

最后一名真人主动退出或掉线宽限结束被移除后，房间立即关闭，不让剩余 AI 独立续房，也不保留等待玩家回来的休眠房间。尚在宽限期内的断线玩家不等于已经退出。持久化区分仍存续房间与已关闭房间，服务重启不复活后者。

关闭前提交终态和可交付的个人记录；已经结算的成绩保留，中途终止手标为 terminated，保留实际资金流与未结算投入，不伪造赢家或将其计为正常胜负。有效下注不因关闭回滚。没有长期钱包，不存在退款到全局账户的路径。记录的短期交付保留与本地归档分开，房间已关闭不意味着立即删除全部结算证据。

## 设计走查（未执行运行验证）

| 场景 | 预期路径 |
| --- | --- |
| Electron 本地单人 | 本地 runtime、IPC 与本地 Agent，复用规则和客户端，无远端依赖 |
| Web 房主、Electron 提供 AI | Web 建房，房主授权独立 Agent controller，Key 留提供者机器 |
| 手机/平板十人混合桌 | 稳定 seatId 与本地显示映射、私有视图及紧凑 UI；需后续视觉与性能验证 |
| 回合中买入/卖出 | 独立资金命令持久化、广播余额、重算相关合法动作，计时不重置 |
| 全下后买入 | 资金留待下手，不恢复本手行动，不改变已确立底池上限 |
| 真人/房主掉线 | 各实体独立判断；真人按回合超时处理，60 秒后移除，仍有人时转让管理 |
| Agent 在线报错或独立离线 | 前者房主重试/移除；后者统一掉线流程，不依赖房主连接状态 |
| 暂停与新 AI 结果 | 牌局计时冻结，聊天/连接管理继续；恢复后校验缓存结果与排队移除 |
| 观战后下手入场 | 本手无争池者获得透视；本手不再入局，下手清理透视权限后正常发牌 |
| 服务重启与重连 | 恢复一致牌堆/筹码/命令状态，仅重建存续房间，新尝试拒绝旧回包 |
| 所有真人退出 | 提交关闭终态，取消计时与 Agent 请求，记录已结算与中止部分，不等待回房 |

后续验证应覆盖本地与远程同一命令序列、重连不重复结算、过期 AI 回包被拒、预约取消与计时竞态、底牌不进入公共事件、赛后亮牌补入历史以及聊天不中断轮次。本轮仅静态核对与设计，未执行这些验证。
